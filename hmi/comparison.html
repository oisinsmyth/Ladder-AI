Where these came from

The source was a research screen drawn for a 1280×800 panel. The target is 800×480 — about a third of the area. Every one of the 24 research pages failed the bounds check outright, from 11 items off-canvas on the simplest to 65 on this one.

So the six screens below were re-authored, not rescaled. The information hierarchy changed; sub-captions, tile descriptions and the unacknowledged-count badge were dropped rather than shrunk.

Round trip

The loop that ran, per screen: check → emit → import → hmi-compile → export → compare. The comparison pairs objects by name, because TIA reassigns element IDs on import.

The comparator was wrong until an hour ago. It compared only type and the bounding rectangle, so a changed label round-tripped as identical — while its own “ignored” line claimed it skipped nothing but element IDs. It was caught by deliberately mutating one character and re-running, not by reading it. It now compares every attribute, text payload and font, and the counts above are the widened figures.

Invariance

PropertyStatusEvidence
Emitter is deterministic Established Same source emitted twice, 6/6 byte-identical
TIA preserves what was emitted Established 1,838 fields across 6 screens, 0 changed, 0 dropped
Stable across a second import Established Re-imported and re-exported: 642 fields, 0 changed
Reverse path — panel back to HTML Does not exist No SimaticML → IR reader for screens; the pipeline is one-way by construction

So the converter is not invariant in the ladder sense — and cannot be. On the PLC side, invariance means export → IR → export returns the original. Here there is no reader, so no such loop can be run. What is proven instead is one-directional: the emitter is deterministic, and everything it states survives TIA unchanged through two import cycles.

The second-import test matters more than it looks. This project has a recorded case of an attribute silently reverting on the second import while every gate stayed green. That does not happen here — but it had never been checked before today.

What these screens are not

GapWhy
The alarm areas are placeholders An alarm view cannot be authored on Classic at all — not by file, not by API. Two screens carry a marked box and a hand-off checklist entry instead.
No tags are bound Every value is static text. Binding needs tags that will not be invented, and the preflight check that would verify them is not built.
One type size throughout The emitter hard-codes the font, so a type scale would look correct in the browser and vanish on the panel. Hierarchy is carried by position and boxes instead.
No regeneration guard Re-running the loop replaces the screen. The moment someone adds a real alarm view by hand, regenerating destroys it. Treat these as generate-once.
Nothing here has been reviewed for whether it is the right screen. Every figure above is tool output over a stated denominator; whether an operator would act correctly on these at 3 a.m. is a question none of it measured.
