# IR format specification

**Status: v1 — decided per ADR-0001 (2026-07-11), against real S7-1200 G2 SimaticML exports.**
Grammar details not yet exercised by a real converter (this is a spec, not an implementation)
may still shift when `src/converter/` is built and run against the golden suite (S1 overall
plan items 4–7) — anything marked **[converter-verify]** below is a contract, not a guarantee.

## Requirements (fixed)

- Vendor-neutral, PLCopen-XML-compatible in semantics; no Siemens-ism leaks above the converter.
- Text-first, diff-friendly. Primary reader/writer is Claude Code round-tripping through it
  (`TIA → converter → IR → AI → IR → converter → TIA`); human review of the diff is the second
  audience, not the design driver — don't sacrifice mechanical clarity for prose-like prettiness,
  but don't produce something unreadable either (ADR-0001).
- One file per block. Extension: `.ir`.
- Lossless round-trip: SimaticML → IR → SimaticML with no semantic diff (golden-tested).
- IR self-stability: parse → re-serialize is byte-identical.
- Unknown source elements are hard errors, never best-effort (design philosophy #10).
- Round-trip metadata TIA needs but humans/AI don't (UIds, geometry) lives in a sidecar section,
  machine-owned — regenerated by the converter on every `to-ir`, never hand-edited.

## File shape

```
BLOCK <FB|FC|OB> <Name>
  NUMBER <n>
  LANGUAGE <LAD>                    # LAD only ever appears here — converter refuses anything else (CLAUDE.md hard rule 1)
  COMMENT "<block header comment>"  # omitted entirely if empty

  INTERFACE
    INPUT   <name> : <Type>
    OUTPUT  <name> : <Type>
    INOUT   <name> : <Type>
    TEMP    <name> : <Type>
    RETURN  <name> : <Type>         # matches the source's own Section names (Input/Output/InOut/Temp/Return)

  NETWORK <n> "<title>"
    <body — see Network body below>

  NETWORK <n+1> "<title>"
    <body>

SIDECAR
  <machine-owned round-trip data — see Sidecar below>
```

DBs and UDTs use a different, simpler top-level shape — see Tag tables/UDTs/DBs below.

## Network body

Two forms. The converter always attempts the readable form first; it falls back to the explicit
form only for a network whose wiring graph doesn't reduce to clean series/parallel structure —
this is a per-network fallback, not a file-wide or project-wide mode, and it's not a "best
effort" degradation: the explicit form is exactly as lossless and exact as the readable form,
just more verbose. **[converter-verify]** how often the fallback actually triggers against real
site-convention logic (ADR-0001 predicts rare, per C-101/C-114).

### Readable form (default)

Boolean/comparison/logic instructions map to native expression syntax — this *is* the vendor↔neutral
instruction table for that whole class of instruction, expressed structurally rather than as a
lookup table entry:

| Source (`Part Name`) | IR syntax |
|---|---|
| `Contact` | bare tag reference, e.g. `Sensor1.Ok` |
| `Contact` (negated) **[converter-verify exact source attribute]** | `NOT Sensor1.Ok` |
| `Coil` | `COIL <tag> := <expr>` |
| `Eq` / `Ne` / `Ge` / `Le` / `Gt` / `Lt` | `=`  `<>`  `>=`  `<=`  `>`  `<` as infix operators |
| `O` (OR-merge) | `OR` |
| `A` (AND-merge) **[converter-verify part name]** | `AND` |

Stateful and boxed instructions (timers, MOVE, block calls — anything with named ports beyond a
single boolean in/out) use call syntax, with a small maintained vendor↔neutral name table for the
box name itself (e.g. `MOVE_BLK_VARIANT` → `MOVE`), owned by the converter, grown as new
instruction types are met in the wild — not exhaustively listed here (05-architecture.md's
portability strategy: the table is what makes a future non-Siemens converter possible without
touching the IR or its readers):

```
NETWORK 3 "Conveyor Run Permissive"
  timer := TON(Conveyor1.RunEnableDelay,
               IN := (Settings.Mode = 2),
               PT := Settings.RunDelay)
  COIL Conveyor1.Permissive :=
    (Sensor1.Ok OR Sensor2.Ok) AND (timer.Q OR Override.Active)

  CALL FC_Scale(Input := RawValue, Output_Min := 0.0, Output_Max := 100.0, Result => ScaledValue)
```

- A stateful instruction's own instance/instance-DB reference is its first positional argument
  (`Conveyor1.RunEnableDelay` above) — inline at the point of use, matching the source
  (`<Instance>` element), never a separate declaration elsewhere in the file.
- A named intermediate result (`timer :=`) is available for later expressions in the same network
  to reference — this is IR-level convenience, not a source concept; the sidecar maps it back to
  the real wire UIds it stands for.
- `CALL` sites list only the block name and wired arguments (`:=` for inputs, `=>` for outputs) —
  no inline parameter-interface snapshot (ADR-0001). The callee's own `.ir` file is the source of
  truth for its interface; a call site that doesn't match it is a converter/compile-time error,
  not something re-derived from the snapshot.

### Explicit form (fallback, per-network)

Used only when a network's graph doesn't reduce to the readable form. Same information, laid out
as named nodes and explicit wires instead of a nested expression:

```
NETWORK 7 "Cross-coupled interlock" [explicit]
  NODE c1 = CONTACT(SensorA)
  NODE c2 = CONTACT(SensorB)
  NODE m  = OR(c1, c2)
  WIRE RAIL -> c1.in, c2.in
  WIRE c1.out, c2.out -> m.in1, m.in2
  WIRE m.out -> COIL(Output1)
```

`[explicit]` on the `NETWORK` line marks the form so a reader (human or AI) knows not to expect
the usual expression shape without opening it. Node/wire naming, `RAIL`, and unconnected pins
(source had `OpenCon`) follow the same primitives as the source graph — this form is close to a
direct textual projection of `<Parts>`/`<Wires>`, deliberately, since generality matters more
than prose here.

## Tag tables, UDTs, DBs

Simpler tabular sub-format — no wiring, so the network grammar above doesn't apply:

```
UDT <Name>
  <member> : <Type>
  <member> : <Type>

DB <Name>
  KIND <Global|Instance|Array>
  RETENTIVE <true|false>
  MEMBERS
    <member> : <Type> [= <start value>]
    <member> : <Type> [= <start value>]
```

Instance DBs (`DB KIND Instance`) additionally reference the FB they instantiate — exact
attribute TBD when the converter is built against a real instance DB export
**[converter-verify]**. Nested UDT-typed members inside a DB reference the UDT by name rather
than inlining its members, mirroring how the source and the site's own conventions (C-302) treat
UDTs as the reusable unit.

## Comment/title placement

- Block header comment: `COMMENT "..."` near the top of the file, immediately under `LANGUAGE`.
  Omitted (not an empty string) when the source comment is empty — absence means empty,
  unambiguous on both read and regenerate.
- Network title/comment: the quoted string directly after `NETWORK <n>`. Every network has one in
  practice per site convention (C-201) — the grammar doesn't forbid an empty one, but the
  convention-review capability (S4) is where that gets flagged, not the IR format itself.
- Both use the same source shape (`MultilingualText`/`Culture`/`Text`) — only `en-US` is expected
  per site convention (C-006, English only); other cultures are a hard error if encountered
  (design philosophy #10 — don't silently drop a language TIA actually has data for), not
  silently multiplexed into some IR multi-language construct that doesn't otherwise exist yet.

## Sidecar

Machine-owned, appended once per file, never hand-edited by a human or the AI. Purpose: let the
converter regenerate the exact source UIds and any other volatile-but-required-for-import
identifiers on `to-xml`, so `SimaticML'' ≡ SimaticML` after normalization
(`08-testing-strategy.md`). Maps every part/wire in the source graph — including the ones that
don't get an explicit name in the readable expression form (e.g. an anonymous `OR` merge) — back
to its original UId, via a structural path into the network body (not by name, since not every
node has one). Exact addressing syntax is a converter-implementation decision, finalized when
`src/converter/` is built and proven against the golden suite (S1 item 4) — this section is the
contract (must exist, must be sufficient for exact regeneration, must never be needed to
*understand* the logic) not the final micro-syntax.

Geometry/layout data is deliberately **not** listed as sidecar content yet — whether TIA's own
re-layout-on-import is good enough to skip storing it, or specific cases need it preserved, is an
empirical question for the golden-file harness, not decided here (05-architecture.md's open
question, left open on purpose rather than guessed).

## Open items carried into converter work (S1 items 4–7)

- Exact source attribute for negated contacts.
- Exact `Part Name` for an AND-merge (only `O`/OR was directly observed; site convention C-114's
  chained-permissive style may mean AND-merges are rare in practice, similar to the non-reducible
  network case).
- Instance-DB representation detail (FB reference attribute).
- Sidecar addressing micro-syntax.
- How often the explicit-form fallback actually triggers.
