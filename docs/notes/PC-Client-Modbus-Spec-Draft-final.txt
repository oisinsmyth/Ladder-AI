0. THE REVERSAL THAT SHAPES EVERYTHING
--------------------------------------------------------------------------------

Drafts 00 and 01 were built on "downloading stops the CPU, therefore batch". That is
BACKWARDS. Siemens, verbatim [R]: ***"STEP 7 always tries to download in RUN first. If you
do not want this to happen, you must put the CPU into STOP."***

On an S7-1200 V4 a new FB/FC/DB/UDT, a deleted one, an FB/FC code change, an OB code change
and an FB/FC interface change are ALL downloadable in RUN [R].

*** THE RISK IS NOT THAT DOWNLOADS HALT THE WAVE. IT IS THAT THEY DO NOT, AND SILENTLY
    REINITIALISE STATE. BUILD A CHANGE CLASSIFIER, NOT A BATCH LOCK. ***

And: **the download option you pass does not decide STOP/RUN** [R]. "Software (all)" and
"Software (only changes)" are not rows in Siemens' table — the Engineering System computes
the verdict from the change classes inside the delta, plus a size limit. You cannot choose a
safe option; you can only control what is IN the delta.

--------------------------------------------------------------------------------
1. THE LOOPS
--------------------------------------------------------------------------------

Three nested loops and two download queues. This section is the heart of the document.

................................................................................
1.1  LOOP 1 — one block, authored by one lad-coder
................................................................................

    author IR
      -> compile
      -> REVIEW SKILLS (conventions, simplicity)
      -> changes from skills
           +---------------------------------------------------+
           |  compile -> FUNCTIONAL REVIEW (the test) -> iterate |
           +---------------------------------------------------+
      -> REVIEW SKILLS again
      -> changes from skills
      -> one last test cycle if needed

*** WHY THE TEST LOOP IS BRACKETED BY TWO REVIEW PASSES. *** Fixing for FUNCTION can break
FORM, and fixing for FORM can break FUNCTION. Reviews before the bracket kill cheap defects
before they cost rig time. Reviews after catch what the functional fixes did to readability
and conventions. The final test cycle catches what those review-driven edits did to
behaviour. *** WITHOUT THAT LAST STEP THE BLOCK SHIPS IN A STATE THAT WAS NEVER VERIFIED —
its last verified state would not be its final state. ***

CONSEQUENCE, stated plainly: the test sits INSIDE loop 1, so a lad-coder's iteration rate is
capped by WAVE CADENCE, not by its own speed. That is accepted; at a minute or two per
boundary it is not the bottleneck (§8).

................................................................................
1.2  LOOP 2 — admission
................................................................................

A block enters the TEST project only after passing preflight and COMPILING CLEAN IN
ISOLATION.

Not bureaucracy: Openness cannot download a selection [M] — every download is
whole-software — so THE WHOLE PROJECT MUST COMPILE BEFORE ANYONE'S DOWNLOAD. Without
admission control one agent's broken block blocks every agent. A failing block is simply not
in the next batch.

................................................................................
1.3  LOOP 3 — the wave
................................................................................

    collect admitted SUBMISSIONS (DB-9 — atomic: vectors + observability + target blocks)
      -> PACK INTO TENSORS (DB-13 — colour the conflict graph; this fixes the wave's duration)
      -> derive map, generate copy layer / models / mirror
      -> batch into <=20 DEPENDENCY-CLOSED objects
      -> harness goes inert, DISCONNECTS
      -> download
      -> reconnect -> READ VERSION REGISTER -> confirm stable
      -> RUN THE WAVE:
             for each tensor, in order:
                 establish INERT for THIS tensor       (D33 — its start state, dynamics
                                                        untriggered, resets held, latches
                                                        released, nothing recorded)
                                                       [CORRECTED 2026-08-12: this read "for
                                                        the NEXT tensor", which inside a
                                                        for-each-tensor loop leaves tensor[0]
                                                        with no inert phase at all and runs
                                                        every tensor from its SUCCESSOR's
                                                        start state. D33's "computed per
                                                        boundary from tensor[k+1]" is right
                                                        because there the boundary FOLLOWS
                                                        tensor[k]; transcribed into this loop
                                                        it becomes THIS.]
                 VERIFY inert                          (D33 — two checks: start conditions
                                                        established AND dynamics quiescent)
                 raise the START BOOLS                 (D37 — on a LATER scan, never the same
                                                        one; this edge is the tests' T=0)
                 observe until the tensor completes    (tests within a tensor run CONCURRENTLY)
         -> unconditionally, pass or fail (D34) — a failing test never diverts the sequence
      -> distribute results (DB-8's package, including the co-running log slice, §2.4)

*** THE SHAPE TO HOLD ON TO: inert -> tensor[0] -> inert -> tensor[1] -> ... *** Tensors are
SEQUENTIAL; the tests inside one are PARALLEL. Wave duration is therefore set by TENSOR COUNT,
not test count, and each tensor costs its LONGEST member rather than the sum (D26, §8).

................................................................................
1.4  THE TWO DOWNLOAD QUEUES  *** the routing rule ***
................................................................................

Changes are ROUTED, not merely predicted:

  RUN-CLASS  — new/edited FB, FC, DB, UDT; code changes; new PLC tags.
               Flow through normal wave boundaries. Cheap, non-disruptive.

  STOP-CLASS — OB add/delete, OB property change, hardware configuration, retentivity
               settings, text lists.
               *** DO NOT flow through wave boundaries. They ACCUMULATE IN A DEFERRED
               QUEUE. ***

The deferred queue is drained when TESTING CANNOT PROGRESS (D24). At that point the
disruptive download happens, and testing resumes.

*** THIS MAKES DB-1 A ROUTER, NOT JUST A PREDICTOR *** — deciding which queue a change
belongs in is its primary job, and a better justification for building it than "predict the
outcome".

ACCEPTED CONSEQUENCE: an agent whose work needs a STOP-class change waits longer, because it
cannot be tested until the next disruptive boundary. That delay is unavoidable in any design
and is not treated as a problem.

--------------------------------------------------------------------------------
2. HOW lad-coder INTERACTS WITH THE TEST ENVIRONMENT
--------------------------------------------------------------------------------

2.1  WHAT IT OWNS, AND WHAT IT DOES NOT

lad-coder authors PLANT LOGIC — blocks, IR, the things that implement requirements.

THE COORDINATOR GENERATES EVERYTHING ELSE: the %MW mirror, the copy layer with its latches
and scan-stamps, the block-enable bitmask, OB80, the register map. Per D13 instrumentation is
a property of the COPY LAYER, not of the blocks under test, so lad-coder never writes
observability code, and per D8 it never sees a register number — it speaks TAG NAMES.

2.2  WHAT IT NEVER DOES

  - *** IT DOES NOT WRITE ITS OWN TEST VECTORS *** (D6). An agent authoring both a block and
    its tests encodes its MISREADING into both, and the wave returns green having verified
    only self-consistency. This is the PlantAutoControl failure exactly.
  - *** IT DOES NOT TOUCH THE TEST PROJECT. *** The coordinator is its sole writer, which is
    what makes `SoftwareOnlyChanges` safe (DB-5): that option carries WHATEVER DIFFERS,
    decided by TIA, so an agent writing there could ship another agent's half-finished work.
  - *** IT DOES NOT TAKE THE PROJECT ONLINE. *** An Openness download is REFUSED in online
    mode [M, measured 2026-08-12]. One agent going online blocks the whole wave loop.
  - *** IT DOES NOT REVISE A SHARED UDT MID-WAVE-SET *** (D16). A modified UDT is
    `RUN (Init)` for EVERY DB built on it [R] — the widest blast radius available.

2.3  WHAT DOES NOT APPLY TO IT, so it is not over-generalised

The memory-layout revert on re-import [M, measured three times] bites STANDARD-ACCESS blocks,
which are coordinator-owned mirror scaffolding. lad-coder's ordinary plant blocks are
optimized and unaffected.

2.4  WHAT COMES BACK

Per-vector pass/fail with OBSERVED VERSUS EXPECTED, never a bare verdict — plus:

*** THE CO-RUNNING LOG. *** Results carry a slice of the wave's TIMELINE: what else ran, and
when. This exists because computed disjointness (D9) will sometimes miss coupling that is not
a code reference the graph can see — plant-model state being the obvious case. When agent A
opens a valve, the model raises a level, and agent B's level-alarm test fails, B's own code is
innocent and B would otherwise hunt a phantom. INTERMITTENTLY, which is worse than always.
The log does not prevent interference; it makes it DIAGNOSABLE.

Design implication: the wave must record a timeline, and each agent's results carry the
relevant slice.

*** HOW A FAILING VECTOR MUST BE READ. *** A failure is evidence the block disagrees with a
SPEC-DERIVED expectation. Fix the block against THE SPECIFICATION, not against the vector. An
agent that starts inferring requirements from test data turns the vector into the spec — and
since a different agent wrote it from the same source, that re-creates the correlated check
by the back door.

2.5  THE BLACKLIST

lad-coder, or whoever designs the tests, may name other blocks that must NOT run concurrently
with a given test.

*** GUARDRAIL: A BLACKLIST MAY ONLY EVER ADD EXCLUSIONS, NEVER REMOVE THEM. *** An agent must
not be able to declare itself compatible with something the reference graph says it conflicts
with. Computed disjointness (D9) is the FLOOR; the blacklist sits on top for what the graph
cannot see.

FAILURE MODE TO WATCH: defensive over-blacklisting. If agents exclude everything whenever a
test looks flaky, concurrency collapses toward serial and nobody notices, because it still
WORKS. A recorded reason per entry makes that visible.

2.6  DESIGN-FOR-TESTABILITY — a future skill

Some designs are UNOBSERVABLE. A condition true for one scan is roughly ten times below the
sampling floor; a same-scan coincidence is unobservable at any rate (§12). The copy layer can
latch and scan-stamp — but ONLY IF DECLARED IN THE MAP BEFORE THE DOWNLOAD that generates it,
and that declaration is frozen for the wave set.

So a block whose only evidence of correct behaviour is a one-scan pulse may be untestable in
that wave, and the runner will correctly REFUSE the vector rather than return a meaningless
green.

*** THE SECOND UNTESTABLE SHAPE, FROM D37: A BLOCK WITH NO DISCOVERABLE START CONDITION. ***
D37's start bool binds to a command signal the block ALREADY has, found via
`converter candidate-scan --direction command` — never to a test-only input, because an input
added for the harness is scaffolding inside the block under test and DB-5 forbids exactly that
(what ships would no longer be what was tested). A purely reactive block needs no start gate
and is held inert by its inputs alone, which is fine. What is NOT fine is a block that is
neither: it has sequencing to trigger, but nothing external triggers it. *** THAT IS A
REPORTABLE FINDING ABOUT THE BLOCK, not a harness gap to be worked around by adding an input
to it *** — and it is the design-for-testability lesson most likely to recur, because nothing
in ordinary authoring pushes back on it.

    THE THIRD, FROM DB-12: TIMER PRESETS AS LITERALS. A block whose dwell is a literal cannot
    be time-compressed, so any test longer than the wave budget is unrunnable against it. Check
    C-122 (dwell-timer PT-home) first — the house style may already require the preset to live
    in a DB member, in which case conforming blocks are compressible for free.

*** THIS BELONGS IN A NEW SKILL *** for lad-coder or the test designer, carrying the test-
environment contract: the vector format and its `Basis` requirement (now citing clause AND
assertion, §7), the observability declaration, the start-bool binding and what to do when no
start condition exists, timer presets as data, the blacklist mechanism and its reason field,
how to read results including the co-running log, and the constraint set in §2.2. Premature to write until the environment
exists — named now so the environment is built with a teachable contract rather than one
reverse-engineered later.

3. DECISIONS
--------------------------------------------------------------------------------

D1.  (Superseded by D9; retained for numbering continuity.)
D2.  The register map is authored PC-SIDE and is authoritative. The PLC works off it.
D3.  Identity comes from the PLC. Program-published, with the weakening recorded.
D4.  A test vector may PARAMETRISE a PLC-side model rather than drive raw values.
D5.  Tests are returned to a known INERT state between them, and the reset is VERIFIED.
D6.  The block author does NOT author its own test vectors.
D7.  (Superseded by D15.)
D8.  Agents speak TAG NAMES and never see a register number.
D9.  Independent means NON-OVERLAPPING REACHABLE STATE — the transitive closure through each
     block's call tree, COMPUTED from the reference graph, not declared.
D10. Isolation is structural: PER-TEST INSTANCE DBs.
D11. Execution is CONCURRENT. The enable bitmask survives as a DIAGNOSTIC (bisect, reproduce
     in isolation), not as the execution model.
     *** CLARIFIED IN DRAFT 04 — "CONCURRENT" MEANS WITHIN A TENSOR, AND ONLY THERE. *** As
     written it reads as "all tests in a wave run at once", which is not the design. Tensors
     are SEQUENTIAL, separated by a verified inert reset; the tests inside one are concurrent.
     D26 is the authoritative statement of the structure and this line is subordinate to it.
D12. Models MUST support time compression; vectors declare the factor they need.
     *** BOUNDED, NOT FREE — AMENDED 2026-08-12 BY AUDIT (§16.4, X-D). *** A vector may DECLARE
     a factor but may not have it: compression shortens the REAL-TIME separation of the events
     being observed, so past a point it pushes the assertion below §12's sampling floor and
     every check reports green having sampled nothing. The admissible factor is computed from
     the observability of the assertions in that vector, and an over-declared factor is
     REFUSED. Latching raises the ceiling; sampling does not.
D13. Instrumentation is a property of the COPY LAYER, not of the blocks under test.
D14. Post-download verification is a PROGRAM-VERSION CONSTANT read over Modbus, not an
     upload (§9).
D15. The map is FROZEN for a wave set; changes land only at a download boundary.
D16. Shared UDTs are FROZEN for a wave set; a revision lands only at a boundary and
     invalidates every result for every DB built on it.
D17. Stop-class refusals are TWO-STAGE — static ones in preflight, baseline-relative ones at
     admission (R3).
D18. The harness DISCONNECTS across a download. Reconnect plus version check is the NORMAL
     path, not error handling (§10).
D19. TIME COMPRESSION is the throughput lever, not download batching (§8).

--- the loop and queue structure (D20-D25) ---

D20. *** LOOP 1 BRACKETS THE TEST LOOP BETWEEN TWO REVIEW PASSES, and ends with a final test
     cycle if the second review changed anything *** (§1.1).
D21. *** RESULTS CARRY A CO-RUNNING LOG *** — a slice of the wave timeline, so interference
     the graph could not predict is diagnosable (§2.4).
D22. *** A BLACKLIST MAY ONLY ADD EXCLUSIONS, NEVER REMOVE THEM *** (§2.5).
D23. *** CHANGES ARE ROUTED INTO TWO QUEUES: RUN-class flows through wave boundaries;
     STOP-class ACCUMULATES IN A DEFERRED QUEUE *** (§1.4).
D24. *** THE DEFERRED QUEUE DRAINS WHEN NO TEST CAN MAKE PROGRESS. *** Chosen over "all
     queued tests complete" because the deferred queue holds other dependencies too, so in
     practice the two conditions converge.
D25. *** ANY DOWNLOAD THAT REQUIRES TESTING TO STOP MUST BE A FULL DOWNLOAD, NEVER A
     DIFFERENTIAL ONE. *** If the disruption is being paid for, it buys a known state rather
     than an unknown mixture. SEE R8 — THIS ENTAILS SOMETHING THAT MUST NOT BE MISSED.

--- the wave structure, and what follows from it (D26-D31) ---

D26. *** A WAVE IS A SEQUENCE OF TENSORS; A TENSOR IS A BATCH OF TESTS THAT RUN IN PARALLEL. ***

         inert -> tensor[0] -> inert -> tensor[1] -> inert -> tensor[2] -> ...

     Tensors are SEQUENTIAL and separated by a verified inert reset (D5). The tests WITHIN one
     tensor are CONCURRENT (D11, as clarified). Therefore:

         wave = download boundary
              + SUM over tensors ( inert reset + MAX test duration in that tensor )

     *** WAVE DURATION IS SET BY TENSOR COUNT, NOT BY TEST COUNT, AND A TENSOR COSTS ITS
     LONGEST MEMBER, NOT THE SUM OF ITS MEMBERS. ***

     Recorded this explicitly because it was got wrong in both directions before it was got
     right, and the error was worth an order of magnitude (§8). Neither wrong reading was
     obviously wrong from D11's wording, which is the actual defect being repaired here.

D27. *** TENSOR PACKING IS A GRAPH COLOURING OVER THE CONFLICT GRAPH. *** Pack the submitted
     tests into the FEWEST tensors such that no two tests in a tensor conflict. Nodes are
     tests, edges are conflicts, colours are tensors (DB-13). Greedy colouring is sufficient —
     this does not need to be optimal and the graph is small.

D28. *** MODELS ARE INSTANCED PER TEST, NOT SHARED — this EXTENDS D10 from instance DBs to the
     models. *** The reason is D27 and it is the sharpest consequence in this draft: a model
     shared by every test of one piece of equipment places a conflict edge between EVERY PAIR
     of those tests, the graph goes complete, the colouring degenerates to one test per tensor,
     and the wave collapses to the serial case. *** THE MODEL, NOT THE INSTANCE DB, IS WHERE
     THE SHARING ACTUALLY BITES — instancing only the iDBs does not buy the packing. ***

D29. *** TENSOR WIDTH IS BOUNDED ABOVE BY CONFLICT-FREEDOM AND CAPPED BY POLL BANDWIDTH. ***
     Widening a tensor cuts the tensor count and so the wave — but every test in a tensor must
     be observed within the SAME poll cycle, so it is TENSOR WIDTH, not total test count, that
     the K x RTT arithmetic constrains (O11 and modbus-tcp-client-spec.md — NOT §12, corrected
     2026-08-12: §12 is the observability floor and contains no batching arithmetic at all).
     The two constraints bound one design
     variable from opposite sides and must be solved together.

D30. *** THE FEEDBACK-LATENCY LEVER IS INFORMATION DENSITY PER WAVE, NOT WAVE DURATION. ***
     Under D26 a wave is order-of-a-minute, so duration is not what damages IR development —
     ITERATION COUNT is. Three guessing rounds at a minute each still cost three rounds of an
     agent editing correct code. This is why DB-8 is the first of the new blocks to build and
     DB-10/DB-11 are the last.

D31. *** SUBMISSION IS ATOMIC AND PRECEDES PACKING (DB-9). *** Two independent load-bearing
     reasons: observability declarations must be complete BEFORE the download that generates
     the copy layer (D15 + §2.6 — NOT D13, corrected 2026-08-12: D13 says where instrumentation
     LIVES, not when it must be DECLARED), AND the packer needs the whole submission set to colour the
     graph well — trickled submissions yield a worse colouring, hence more tensors, hence a
     longer wave for the same tests.

--- fault handling, inert, and coverage (D32-D37) ---

D32. *** EVERY UNHANDLED CONFIGURATION ABORTS THE DOWNLOAD, AND WE ABORT IT — NOT TIA
     (O9 RULED). *** The escalation ladder, in order:

       1. ABORT FROM THE DELEGATE (a throw). Ours, so it is distinguishable from one TIA
          caused — the same separation as FailedToApply versus RefusedByPolicy.
       2. LOG: the configuration, every selection it offered, and that we refused it.
       3. *** PAUSE TESTING. *** Not optional even though an abort means the program was not
          changed: an aborted download leaves a state Siemens does not document (G4), so
          resumption goes through the version register (§9) first, never on assumption.
       4. ATTRIBUTE — ask DB-1 which submitted change entails the configuration raised.
       5. IF ATTRIBUTABLE: *** EXCISE THAT IR BLOCK FROM THE WAVE SET, ROUTE IT TO THE
          DEFERRED QUEUE (D23), AND RE-DOWNLOAD WITHOUT IT. *** An ordinary boundary; no
          disruption is spent.
       6. IF NOT ATTRIBUTABLE: a disruptive FULL download (D25, never a differential) —
          *** BUT ONLY FOR CLASS A BELOW. For classes B and C step 6 is futile and step 7
          is immediate. ***
       7. TERMINAL: *** TOTAL TEST ABORT — NOT JUST THE WAVE — AND WAIT FOR A HUMAN. ***

     *** CAVEAT 1 — ATTRIBUTION IS STRUCTURALLY IMPOSSIBLE FOR SOME CONFIGURATIONS, AND THAT
     IS NOT A LOCATOR BUG. *** `DataBlockReinitialization` and `StopModules` ARE attributable:
     DB-1's change classes already map onto them. `UserManagementDownload` and
     `OverwriteSystemData` are PROJECT-LEVEL — no block entails them, so there is nothing to
     excise and step 6 is the only rung that exists. THE LOG MUST DISTINGUISH "no block is
     responsible" FROM "the locator failed to find one": they take the same branch but call
     for opposite fixes, and a log that conflates them will send a fix wave after a locator
     that was working correctly.

     *** CAVEAT 2 — THE LADDER HAS NO TERMINAL RUNG AND CAN LOOP; RULED 2026-08-12. *** If the
     step-6 disruptive download ALSO raises an unhandled configuration, step 1 fires again
     against an unchanged situation and the ladder restarts. Unattended that is an abort loop
     that consumes the night. *** RULED: THAT IS A TOTAL TEST ABORT — the whole test session,
     not merely the wave — AND IT WAITS FOR HUMAN INTERVENTION. *** Recorded as its own
     outcome class, because it is the case that generates a fix wave and the one thing in this
     ladder a person must see. NEVER RETRY A DISRUPTIVE DOWNLOAD THAT ABORTED ON A
     CONFIGURATION.

     *** CAVEAT 3 — AND IT DECIDES WHETHER STEP 6 IS PROGRESS OR A WASTED BOUNDARY. *** "If we
     cannot attribute it we have no choice but a full download" is right for ONE class of
     configuration and FUTILE for two others, because a full download has a LARGER delta than
     a differential and therefore raises MORE configurations, never fewer. It cannot make an
     unwanted configuration go away. What it can do is let us ANSWER one we were only refusing
     because we were in non-disruptive mode. So the class decides the rung:

       CLASS A — REFUSED ONLY BECAUSE THE MODE IS NON-DISRUPTIVE.
                 `StopModules`, `DataBlockReinitialization`, `StartModules` — the
                 --disruptive allowance list. Each is a consequence the chosen download option
                 ALREADY entails. *** STEP 6 GENUINELY RESOLVES THESE: the disruptive download
                 ANSWERS them rather than hoping they do not appear. This is the only class
                 for which spending a disruptive boundary buys anything. ***
       CLASS B — NEVER PERMITTED IN ANY MODE.
                 `ResetModule -> DeleteAll`, `InitializeMemory -> AcceptAll` — the deny list.
                 These destroy BEYOND what the option entails, so a disruptive download refuses
                 them exactly as a normal one does and aborts identically. *** GO STRAIGHT TO
                 STEP 7. Spending a full download here buys nothing and costs a stop. ***
       CLASS C — UNKNOWN, OR NO `NoAction` AND NOT ON EITHER LIST.
                 The `SelectiveDeleteDownload` shape (`AcceptAll | DeleteSelected`), and every
                 configuration nobody has seen yet — which, given that each of the last three
                 runs produced one, is the case that matters. We cannot know what it entails,
                 and guessing is the thing this whole policy exists to forbid.
                 *** GO STRAIGHT TO STEP 7. ***

     SO THE HONEST SHAPE OF THE LADDER: excise-and-continue is the only rung that makes
     progress cheaply, the disruptive download is a narrow second rung serving Class A alone,
     and everything else is a human. THE CLASSIFICATION MUST BE EXPLICIT IN THE LOG — "went
     to step 7 without attempting a download, because Class B" is a materially different
     record from "attempted the full download and it aborted too".

D33. *** INERT IS THE START STATE OF THE NEXT TEST, WITH DYNAMICS NOT TRIGGERED AND RESETS
     HELD (O12 RULED). *** Not "everything idle". Precisely:

       - the NEXT test's START CONDITIONS are established;
       - NO DYNAMICS ARE TRIGGERED — models sit AT the start condition, not running toward it;
       - *** RESETS ARE HELD ASSERTED for the whole inert period — a LEVEL, not an edge or a
         pulse *** — and released at test start;
       - LATCHES ARE RELEASED, and the release must COMPLETE before the first scan of the test;
       - *** OUTPUTS ARE NOT RECORDED DURING INERT. *** Establishing a start state moves
         outputs; recording that would put spurious activity in front of every single test.

     CONSEQUENCE 1: *** INERT IS PARAMETRISED BY WHAT COMES NEXT *** — it is not a canned
     routine but is computed per boundary from tensor[k+1]'s vectors.

     CONSEQUENCE 2, AND IT STRENGTHENS D27: one inert phase must establish the start state for
     EVERY test in the next tensor at once, and that is only WELL-DEFINED because the tests in
     a tensor are conflict-free — non-overlapping reachable state (D9) means their start
     conditions CANNOT CONTRADICT. *** So conflict-freedom is not only about interference
     during a test; it is what makes a shared inert phase constructible at all. *** Two tests
     needing contradictory start states are, by that fact alone, in different tensors.

     CONSEQUENCE 3: D5's "the reset is VERIFIED" now has TWO distinct checks — start
     conditions established, AND dynamics quiescent. A model sitting at the right value while
     still integrating toward another is not inert, and only the second check catches it.

D34. *** THE WAVE ALTERNATES INERT / TEST UNCONDITIONALLY, PASS OR FAIL (O6 RULED). *** A
     failing test does not abort the wave and does not change what follows it. This RESOLVES
     O6 by REMOVING THE NEED FOR A FAILURE POLICY rather than by choosing one: the inert phase
     (D33) is what contains a bad state, so the wave never has to reason about whether the
     previous test left one. Abort-loses-information and complete-risks-cascading were the two
     horns; establishing the next start state unconditionally takes neither.

     WHAT IS STILL OWED, AND IT IS SMALL: the case where *** INERT ITSELF CANNOT BE
     ESTABLISHED *** — a block latched in a fault that will not reset. That is NOT a test
     failure, it is a WAVE-BLOCKING condition, and the natural treatment is D32's: excise the
     offending block to the deferred queue and continue the wave without it. Recorded as O6's
     residual rather than quietly assumed.

D35. *** COVERAGE IS COUNTED PER ASSERTION, NOT PER CLAUSE, AND EVERY VECTOR DECLARES THE
     ASSERTION IT TARGETS (O13 RULED). *** Many vectors per clause is the expected shape and
     is entirely fine — *** but only if the denominator is assertions. *** Against §7's
     `clause x instance` denominator, five vectors on a two-assertion clause all tick the same
     box, and the second assertion reads as covered while nothing ever tested it. That is this
     project's own correlated-check failure wearing coverage clothing.

     *** THE ASSERTION SET IS ENUMERATED FROM THE SPECIFICATION, NEVER FROM THE TEST SUITE. ***
     Decomposing a clause into its atomic assertions is a SPEC-SIDE operation, complete before
     any vector exists; a vector CITES into that enumeration and cannot extend it. This
     qualifier is load-bearing, not decoration — a denominator defined by what somebody wrote a
     vector for is always 100%, and §7 rejects it by name.
     [CORRECTED 2026-08-12 BY AUDIT. This paragraph previously said that where clauses are NOT
     atomic "the declaration is exactly what makes the gap visible", which describes discovery
     AT THE VECTOR — the very mechanism §7 forbids. The headline stands; the justification was
     describing the rejected alternative.]

     WHY THIS FORM RATHER THAN "MAKE CLAUSES ATOMIC": it is correct WHETHER OR NOT clauses turn
     out to be atomic. If rung B/C already emits atomic clauses the citation is trivially the
     clause itself and costs nothing; if it does not, the spec-side decomposition is where the
     extra assertions appear. *** So the original O13 question — are clauses already atomic? —
     stops being load-bearing, which is why it can be closed without answering it. ***

D36. *** THE POLL-WIDTH CAP (O11) AND CONFLICT DENSITY (O14) ARE PARAMETERS TO BE MEASURED
     ONCE THE DESIGN BLOCKS EXIST — NEVER CONSTANTS ASSUMED NOW. *** Both deferred
     deliberately, so that the design blocks can be adapted to what is measured rather than
     the measurement being predicted. THE OBLIGATION THE DEFERRAL CARRIES: DB-13's colouring
     takes MAX TENSOR WIDTH as an explicit input with no default that could be mistaken for a
     measurement, and nothing anywhere assumes unlimited width or a particular packing.

     *** ONE THING MUST NOT BE DEFERRED ALONGSIDE THEM: AUTHOR MODELS INSTANCED PER TEST FROM
     THE START (D28). *** Deferring the MEASUREMENT is right; defaulting to SHARED models
     while it is deferred is not. Instancing is nearly free while the models are being
     written and is a rewrite of every model afterwards — and if O14 comes back "packs 1-2
     wide", shared models are precisely the cause it will name. BE WRONG IN THE CHEAP
     DIRECTION.

D37. *** EACH VECTOR CARRIES A START BOOL, AND IT GATES THE BLOCK'S START CONDITION — NOT THE
     BLOCK'S EXECUTION. *** This is the MECHANISM for D33's "dynamics not triggered", which
     until now described a state with no stated means of reaching it.

     *** THE BLOCK IS CALLED EVERY SCAN, INCLUDING THROUGHOUT INERT. *** The tempting reading —
     gate the CALL, so the block does not run during inert — is WRONG, and D33 is what rules it
     out: resets are HELD ASSERTED during inert, and a reset is processed BY THE BLOCK. A block
     that is not called never processes its reset, so gating the call produces a block that is
     neither running nor reset, holding whatever its statics happened to contain. That is the
     opposite of inert.

     WHAT THE BOOL BINDS TO — AND THE CONSTRAINT THAT MATTERS:

       *** IT BINDS TO THE BLOCK'S EXISTING START CONDITION, DISCOVERED, NEVER TO A TEST-ONLY
       INPUT ADDED FOR THE PURPOSE. *** A test-only input is scaffolding inside the block under
       test, which is exactly what DB-5 forbids: what ships would then not be what was tested.
       The discovery tool already exists — `converter candidate-scan --direction command`
       computes command-versus-status FROM THE USAGE GRAPH rather than from the interface
       section, which is the right question here.

       *** NOT EVERY BLOCK HAS ONE, AND THE ABSENCE IS MEANINGFUL RATHER THAN A DEFAULT. *** A
       purely reactive block — a comparator, a level alarm, anything that is always processing —
       has no start gate, and for those inert is established BY THE INPUT VALUES ALONE (put the
       level below the threshold). So the field is OPTIONAL PER VECTOR, and a vector that omits
       it is asserting "this block has no start gate", which is a claim the harness can check
       rather than a blank it fills in.

     ORDERING, AND IT IS A RACE IF LEFT UNSTATED: release the latches, VERIFY quiescent (D33's
     second check), and only THEN raise the start bool — ON A LATER SCAN, never the same one.
     Releasing a reset and starting in one scan makes the outcome depend on rung order inside
     the block, which is not something a test should be sensitive to.

     PER TEST, NOT GLOBAL. Tests in a tensor hold independent start bools. Simultaneous start
     is the normal case; independence is what permits a staggered one without redesign.

     *** AND IT SUPPLIES SOMETHING THE DESIGN WAS MISSING: A DEFINED T=0. *** The rising edge
     of the start bool IS the test's time origin. §12 offers EVENT SCAN-STAMPS to answer "when,
     relative to what" — and until now there was no stated "what". Stamps become differences
     from the start edge, in scans, which is exactly the unit the observability floor argues in.

     DESIGN-FOR-TESTABILITY CONSEQUENCE, for the skill the owner has flagged as needed: a block
     with NO discoverable start condition and no way to be held inert by its inputs is HARD TO
     TEST — and that is a finding ABOUT THE BLOCK, reportable as such, not a gap in the harness
     to be worked around by adding a test input to it.

4. THE DESIGN BLOCKS
--------------------------------------------------------------------------------

Six were proposed; they collapse into about four components. DB-1 and DB-2 are one graph
problem, DB-3 and DB-4 are one scheduler, DB-5 is structural, DB-6 is a client invariant.

DB-1 — CHANGE TRACKER *** AND ROUTER ***
  Three outputs: WHICH objects changed (for the <=20 budget), WHAT CLASS each change is
  (for routing per D23 and for STOP / RUN (Init) prediction), and BLAST RADIUS (a UDT change
  is one object plus every DB built on it).

  Change classes [R, Siemens' own RUN-download table, S7-1200 V4 column]:
    FB/FC code change ............................ RUN, nothing disturbed
    New / deleted FB, FC, DB, UDT ................ RUN
    New / deleted OB, or OB property change ...... STOP
    DB interface change (no memory reserve) ...... RUN (Init) - resets, retentives included
    Modified UDT ................................. RUN (Init) on EVERY DB built on it
    Modified retentivity settings ................ STOP
    New / revised text lists ..................... STOP
    Hardware configuration ....................... STOP
    Comments, new PLC tags ....................... RUN

  Existing tooling: `converter ir-hash` (cheap has-it-changed, immune to SIDECAR/UId churn),
  `converter diff` (changed networks, rest provably identical), `converter cross-check`
  (reference graph for blast radius).

  RESOLVED GAP: a local ledger desynchronises from the device. Reconciliation via
  `openness-cli export-all` + `converter drift-check --complete` is a periodic OBLIGATION.
  *** CAVEAT [M]: export-all reads the OFFLINE PROJECT, not the controller *** — Openness has
  no upload path — so that reconciliation compares IR-on-disk to the TIA project. The VERSION
  REGISTER (§9) is the only thing that verifies the DEVICE.

DB-2 — TEST / BLOCK DEPENDENCY
  Same graph, different query. A test can be invalidated by a block it does NOT target: if B
  writes a global A reads, B's change invalidates A's PASSING RESULT though A changed nothing.
  Dependency is transitive over the reference graph.

  Results carry a VALIDITY STAMP: (program version, map version). Without it the system will
  report a green obtained BEFORE the change that invalidated it.

DB-3 — DOWNLOAD TRACKING AND DURATION
  "Affected tests" means ALL tests — Openness cannot download a selection, so every download
  is whole-software.

  SETTLING WINDOW after "finished": `RUN (<21)` integrates across several scan cycles, during
  which the program runs as a MIXTURE of old and new blocks [R]. Results from that window are
  meaningless. The version register (§9) makes the window observable rather than guessed.

  FAILURE HANDLING: an aborted download leaves the device in a state Siemens does not
  document (external gap G4). NEVER resume on the assumption it worked — read the version
  register first.

  Inert-state-before-download stands, for a stronger reason than throughput: if a DB
  reinitialises during the download, there is no state to corrupt if you went inert first.

DB-4 — THE 20-OBJECT LIMIT
  More than 20 changed objects cannot be integrated consistently in one program cycle [R].

  *** CORRECTED 2026-08-12 BY AUDIT: THE BUDGET IS BIMODAL, AND THE OLD "3 OBJECTS PER AGENT,
  SO ROUGHLY SIX AGENTS PER DOWNLOAD" WAS THE STEADY-STATE CASE PRESENTED AS THE ONLY ONE. ***
  It counted an agent's FB, UDT and iDB and forgot that D10 creates an instance DB PER TEST and
  D28 a model instance PER TEST — both of which are objects, and neither of which existed as
  decisions when that figure was written.

    INTRODUCTION WAVE — an agent's test set appears for the first time:
        FB + UDT + iDB .................................  3
        per-test instance DBs   (D10, 5 vectors) .......  5
        per-test model instances (D28, >=1 each) ....... >=5
        ------------------------------------------------------
        per agent ...................................... >=13   => ONE agent per download,
                                                                   not six. 6 agents x 5
                                                                   vectors ~ 78 objects ~ 4
                                                                   downloads.

    STEADY-STATE ITERATION — the agent edits its block and re-runs existing tests:
        the FB, sometimes a UDT ........................ 1-2    => the original ~6 agents per
                                                                   download HOLDS here, because
                                                                   the per-test objects already
                                                                   exist unchanged and are not
                                                                   in the delta.

  *** THE REFINEMENT THE AUDIT DID NOT MAKE, AND IT IS THE REASON D30 SURVIVES: PER-TEST
  OBJECTS ARE CREATED ONCE AND PERSIST. *** They are only in a delta on the wave that
  introduces them. So the heavy case is real but NON-RECURRING per test set, and iteration —
  which is what actually dominates a lad-coder's loop (D30) — stays cheap.

  WHAT THIS DOES CHANGE: an introduction wave carries roughly 4 download boundaries rather than
  1, so at the corrected ~20-25 s per boundary (§8) it front-loads about 80-100 s. "A wave is
  order-of-a-minute" survives, but only just, and only because the boundary cost was also
  corrected downward. Both corrections came from the same audit and they pull in opposite
  directions — do not apply one without the other.

  AND IT SHARPENS DB-7: objects accumulate at ~10 per agent per introduction, while cleanup
  fires only at a drain boundary (D24). The budget is consumed by ACCUMULATION, not by change.

  Batches must be DEPENDENCY-CLOSED, not arbitrary slices — an FB, its instance DB and its
  UDT must land together or the program is inconsistent between downloads.

  The whole project must compile before ANY download, so admission control (§1.2) is the fix
  for one broken block blocking everyone.

DB-5 — TWO PROJECTS: IR DEV, AND TEST ENVIRONMENT
  The coordinator OWNS the test project, so `SoftwareOnlyChanges` — "the objects that differ
  online and offline", decided by TIA, not your edit list [M] — can only carry what the
  coordinator put there. The folder-download-deletes-online-only-blocks footgun [R] is
  contained for the same reason. Concurrent Openness sessions on DIFFERENT projects are
  supported and verified here.

  *** Harness scaffolding never contaminates the deliverable *** — MB_SERVER, the models, the
  latches and the mirror exist only in the test project.

  NAMED COST: what is tested is then not what ships. Extra code, extra scan time, different
  timing; a timing-sensitive behaviour could pass in test and fail in the deliverable.

DB-6 — ISOLATION BY CONSTRUCTION
  The research hazards are DATA LOSS, not leakage. The one genuine LEAK is PC-side: if the
  mirror's layout changes and the PC's map does not, agent A's write lands in agent B's
  registers. The protection is client-side and can be by construction:

    1. Layout version register checked before EVERY transaction batch, not only at connect —
       a download can land mid-session.
    2. The map artifact carries a hash; the version register carries the same value. A
       mismatch refuses the whole mirror.
    3. *** The client instance holds only its own region's bounds, so a write outside it is
       UNADDRESSABLE *** — not rejected by a check that could be skipped.

DB-7 — CLEANUP  *** new 2026-08-12 ***
  NOTHING IN THE DESIGN EVER REMOVES ANYTHING, and three things accumulate: per-test instance
  DBs (D10 — one per TEST, not per agent), models, and blocks no longer under test. Left alone
  they consume scan time (M6), object count, and eventually the <=20 batching budget.

  A CLEANUP STAGE runs on a cadence expressed in test cycles or disruptive downloads. What it
  removes: instance DBs for completed tests, models no vector still references, and blocks not
  in any admitted test.

  FOUR RULES, each earned:
    - *** IT RUNS WHEN TESTS ARE DRAINED *** — the same condition as the deferred queue (D24).
      Deleting something a running test depends on is the obvious way to make this dangerous.
    - *** ELIGIBILITY IS GRAPH-PROVEN, NEVER COUNT-BASED. *** "Nothing references this" is a
      computed fact from the reference graph (`converter cross-check`), not an assumption from
      age or from a test having finished. A block can be unreferenced by vectors and still
      called by another block.
    - *** EVERY REMOVAL IS RECORDED — what, why, and on whose authority. *** Otherwise this
      becomes the "a block silently disappeared" failure, which is exactly the shape of the
      folder-download footgun (R5) that we forbade elsewhere.
    - Deletions are ordinary changes: they route through DB-1, count against the <=20 budget,
      and — usefully — deleting an FB/FC/DB/UDT is RUN-class [R], so cleanup does NOT need a
      disruptive boundary of its own.

--------------------------------------------------------------------------------
4a. THE WAVE-STRUCTURE DESIGN BLOCKS  *** new in draft 04 ***
--------------------------------------------------------------------------------

DB-1 to DB-7 answer "what may be downloaded, and when". DB-8 to DB-13 answer a different
question that only appeared once D26 made the wave structure explicit: *** given that a wave
costs about a minute, what actually limits how fast an agent converges on correct IR? ***

BUILD ORDER, AND IT IS NOT THE NUMBERING (D30):

     FIRST      DB-13  tensor packing      — it sets wave duration, and D28 falls out of it
     FIRST      DB-8   the result package  — iterations dominate, so density is the lever
     THEN       DB-9   the submission unit — both DB-13 and D31 depend on it
     LATER      DB-12  time compression    — narrowed; long tests only
     LAST       DB-10  agent scheduling    — at a minute a wave, an agent can simply wait
     LAST       DB-11  the rig pool        — better packing buys the same thing for free

DB-13 — TENSOR PACKING  *** the block that sets wave duration ***
  Pack N submitted tests into the fewest tensors such that no two tests in a tensor conflict
  (D27). The conflict EDGES are not new work — every source is something the design already
  computes:

    - OVERLAPPING REACHABLE STATE (D9) — the transitive closure through each block's call
      tree, from `converter cross-check`. Already the definition of "independent".
    - SHARED MODEL INSTANCES — two tests parametrising the same model of the same equipment.
      See D28; this is the dominant source and the one that is fixable.
    - BLACKLIST ENTRIES (§2.5, D22) — the manual additions, which may only ADD edges.
    - THE POLL-BANDWIDTH CAP (D29) — not a pairwise edge but a width limit on any tensor,
      derived from K x RTT against the observation set the tensor needs.

  MECHANISM. At admission the coordinator holds every submission (DB-9), so it builds the
  graph and colours it BEFORE the download. Greedy is fine. It then reports the tensor count
  and the predicted wave duration back with the plan, so an agent can see what its submission
  cost — a submission that adds one test and one tensor is visibly more expensive than one
  that adds five tests into existing tensors.

  *** THE MEASUREMENT THAT DECIDES WHETHER ANY OF THIS WORKS: THE CONFLICT DENSITY OF A REAL
  SUBMISSION SET. *** If tests pack 6-10 wide, waves are about a minute and feedback latency
  is a non-problem. If they pack 1-2 wide because everything shares a plant model, waves are
  10x longer and instancing the models (D28) is the highest-value change available anywhere in
  this design. *** THIS IS ANSWERABLE FROM THE FIRST REAL SUBMISSION SET, BEFORE ANY OF IT IS
  BUILT *** — it needs the graph, not the rig.

DB-8 — THE RESULT PACKAGE  *** build first alongside DB-13 ***
  The latency lever (D30): make one wave worth three by removing the reasons an agent has to
  guess. What a result carries:

    - OBSERVED VERSUS EXPECTED, per assertion, not a pass/fail for the test.
    - THE BASIS CITATION — which requirement clause and which spec artifact the expectation
      came from, so a disagreement is traceable to a source rather than argued from the code.
    - THE FIDELITY DECLARATION of every model involved (M3/M4, §11). A failure against a model
      declared as approximate is a different fact from one against a model declared exact.
    - *** THE STIMULUS CHECK *** — evidence the input actually arrived and the block actually
      ran. Without it "no output" is ambiguous between "the logic is wrong" and "the test never
      started", and an agent asked to distinguish those from a bare fail will guess.
    - THE CO-RUNNING LOG SLICE (D21) — which other tests shared the tensor, so interference the
      graph did not predict is diagnosable. Under D26 this now has an exact meaning: the
      tensor, not the wave.
    - THE VALIDITY STAMP (DB-2): program version, map version.
    - MANIFEST PRESENCE (§9a): whether the object under test appears in the load manifest of
      the download that preceded the wave. Cheap, and it separates "wrong" from "never loaded".

DB-9 — THE SUBMISSION UNIT
  A test set is submitted ATOMICALLY (D31): the vectors, their observability declarations, and
  the blocks they target, as one unit that is admitted or refused whole. Observability must be
  declared before the download that generates the copy layer (D15 + §2.6; not D13 — see D31)
  — a declaration arriving
  after it cannot be honoured until the next boundary — and the packer needs the full set to
  colour well. A partial submission is a REFUSAL with reasons, never a partial admission.

DB-12 — TIME COMPRESSION  *** narrowed in draft 04, not dropped ***
  D19 called compression THE throughput lever. Under D26 that is now too strong: compression
  does nothing for wave OVERHEAD, which is tensor count and inert resets. What it still does,
  and what nothing else does, is make an individually LONG test runnable at all — a 40-hour
  dwell cannot run whatever the packing.

  *** AND THE CONSTRAINT THAT HAD NOT BEEN NAMED: YOU CANNOT COMPRESS A MODEL INDEPENDENTLY OF
  THE LOGIC IT DRIVES. *** Compressing a tank-fill model while the block's own dwell timer runs
  in real time does not accelerate the test, it DESYNCHRONISES it, and the block fails a test
  it would pass on real hardware. So compression requires TIMER PRESETS AS DATA, not literals,
  in the blocks under test — which is a design-for-testability requirement on authored IR, not
  a property of the harness.

  WORTH CHECKING BEFORE BUILDING ANYTHING: convention *** C-122 (dwell-timer PT-home) *** may
  already require exactly this. If PT already lives in a DB member by house rule, compression
  is close to free on conforming blocks and the work is a conformance check, not a change.

DB-10 — AGENT SCHEDULING  *** demoted ***
  States: WORKING / AWAITING-WAVE / BLOCKED. Agents YIELD rather than block a slot while
  waiting for a wave boundary. When a result lands, *** RESUME THE OWNING AGENT WITH ITS
  ORIGINAL CONTEXT rather than spawning a fresh one *** — the fresh agent re-derives what the
  original already knew, which is the same correlated-cost mistake as re-reading a spec to
  re-reach a conclusion already recorded.

  DEMOTED BECAUSE OF D26: at roughly a minute a wave, an agent can simply wait, and the
  machinery is not worth building until measurement says otherwise. Keep the state model
  written down for when it is.

DB-11 — THE RIG POOL  *** demoted furthest ***
  If a second rig exists, each rig gets its OWN test project — otherwise the version register
  (§9) stops identifying what is running where, which is the one thing it exists to do. Claims
  (`converter claim`) stay GLOBAL across rigs: a block number is a property of the program, not
  of the rig it happens to be loaded on.

  DEMOTED BECAUSE a second rig buys parallel waves, and better packing (DB-13) buys the same
  throughput for no hardware and no second project to keep synchronised. Revisit only once
  packing has demonstrably hit the conflict ceiling.

  INTERACTION: a deleted block frees its number, which the claims registry allocated. Releasing
  the claim must be part of the removal, or the number stays reserved forever.

5. DESIGN RULES
--------------------------------------------------------------------------------

R1. THE OB SET IS PRE-ALLOCATED AT RIG SETUP where practical. *** REVISED IN DRAFT 03: an OB
    change is no longer FORBIDDEN, it is DEFERRED *** — it is a STOP-class change and routes
    to the deferred queue (D23). New or deleted OB is `STOP` on this CPU [R], the biggest
    divergence from the S7-1500, which takes all three in RUN.

R2. SHARED UDTs FROZEN FOR A WAVE SET (D16). A revision lands only at a boundary and
    re-baselines every DB built on it.

R3. STOP-CLASS HANDLING IS TWO-STAGE (D17):
      STAGE 1, PREFLIGHT, no device, no baseline — properties of the IR alone: creates an OB,
        changes retentivity settings, adds a text list. Cheapest feedback; the agent finds out
        before anyone else is involved. *** These are now ROUTED, not refused. ***
      STAGE 2, ADMISSION, against DB-1's baseline — "modified UDT" is only a change relative
        to what is deployed, so reinit-class and object-count decisions happen when a batch is
        assembled.

R4. *** NEVER WRITE A DOWNLOAD DELEGATE THAT ACCEPTS EVERYTHING. *** A delegate written to
    say yes to everything so the download goes through is precisely how a harness wipes a rig.
    `DataBlockReinitialization = StopPlcAndReinitialize` initialises ALL data values INCLUDING
    RETAIN DATA [R].

    *** CORRECTED 2026-08-12 BY MEASUREMENT — THE MECHANISM IS NOT WHAT THIS RULE SAID. ***
    The original wording was "answer `NoAction` and let it abort". Measured: **`NoAction`
    CANNOT BE APPLIED** — `EngineeringTargetInvocationException: The configuration provided is
    invalid`, on `StopModules` and `DataBlockReinitialization` alike, through the property
    setter AND the underlying `SetAttribute`, even though `GetAttributeInfos()` reports
    `CurrentSelection : access=ReadWrite` [M].

    THE GUARD IS "REFUSE TO ANSWER AT ALL", which makes Openness abort with
    `Download configuration '<type>' was unhandled`. Still fail-closed, through a different
    door than assumed.

    Two readings remain and are NOT separable without applying a destructive selection: either
    `NoAction` is invalid FOR THAT INSTANCE because the stop or reinitialisation is genuinely
    mandatory, or the apply mechanism is broken for every value. *** OPERATIONALLY IT DOES NOT
    MATTER *** — same rule, same protection.

R4a. *** NEVER INFER SAFETY FROM THE CURRENT SELECTION. *** The zero values differ IN
    DIRECTION [M]:
        StopModulesSelections.NoAction ............................ = 0  (safe)
        DataBlockReinitializationSelections.StopPlcAndReinitialize . = 0  (DESTRUCTIVE)
    An unanswered configuration therefore reads as SAFE on one and DESTRUCTIVE on the other. A
    check written against one and reused for the other INVERTS SILENTLY.

R5. NEVER USE FOLDER-SCOPE DOWNLOADS — blocks existing only online are DELETED by them [R].

R6. ADMISSION CONTROL — a block enters the test project only after passing preflight and
    compiling clean in isolation.

R7. *** REVISED IN DRAFT 03. *** Draft 02 said "never pass `Software` (all)". That stands FOR
    WAVE-BOUNDARY DOWNLOADS, where it would reset retentive values for no reason. It is
    REVERSED for the disruptive boundary — see D25 and R8.

R8. *** THE ENTAILMENT OF D25, AND THE ONE PLACE THE GUARD IS DELIBERATELY OPENED. ***

    D25 requires a FULL download whenever testing must stop. MEASURED [M]: a full `Software`
    download raises `StopModules`, and `NoAction` cannot be applied to it — so *** A FULL
    DOWNLOAD IS IMPOSSIBLE UNLESS `StopAll` IS ANSWERED, AND `StopAll` IS FORBIDDEN BY THE
    WAVE-LOOP POLICY (D32 Class A). ***
    [CORRECTED 2026-08-12 BY AUDIT: this said "`StopAll` IS ON R4's DENY LIST". R4 contains no
    deny list — it forbids a permissive delegate and names one destructive selection. The deny
    list is enumerated in D32 Class B and has exactly two entries, `ResetModule -> DeleteAll`
    and `InitializeMemory -> AcceptAll`; `StopAll` is NOT one of them. `StopAll` is Class A —
    refused in the wave loop, ANSWERED at a disruptive boundary, which is what makes the
    exception below coherent rather than a contradiction. Three passages cited a list that was
    never in R4, and the list that does exist excludes the selection they cited it for.]

    Therefore D25 cannot be implemented without a sanctioned exception. The exception must be:
      - a SEPARATE, EXPLICITLY DECLARED DISRUPTIVE MODE — never a flag on the wave-boundary
        path, and never a fallback reached by retry;
      - permitted ONLY when the deferred queue is being drained (D24);
      - logged as a deliberate CPU stop, with what was in the queue and why;
      - and it must NOT relax the deny list for the wave loop, where stopping the CPU
        mid-testing remains forbidden.

    *** 2026-08-12 [M], AND RESTATED ACCURATELY AFTER AUDIT — READ THE QUALIFIER, IT IS NOT
    PEDANTRY. *** `StartModules` is raised in the POST delegate whenever the download stopped
    the modules; `StartModule` was ANSWERED AND ACCEPTED, and *** TIA REPORTED *** `PLC_1
    stopped.` then `PLC_1 started.`

    *** THAT IS TIA'S ACCOUNT OF WHAT IT DID — NOT A READING OF THE CPU'S OPERATING MODE. ***
    The probe's own log says so in capitals ("THAT IS A REQUEST, NOT A READING... confirm RUN
    at the device or in TIA Portal before relying on the rig"), and §16.11 proves the gap
    cannot be closed from here: `OnlineProvider` exposes NO operating mode, so *** NOTHING IN
    THIS TOOLING CAN ASK THE CONTROLLER WHETHER IT IS RUNNING. ***

    WHAT FOLLOWS, STATED HONESTLY. The earlier wording — "the disruptive boundary does NOT
    require a person, and unattended operation is not capped by this" — was drawn from this
    evidence and OVERSTATED IT. The mechanism is real and was exercised; what is missing is
    independent confirmation of the outcome. *** SO: CONFIRM RUN AT THE DEVICE ONCE, BY EYE,
    BEFORE THE FIRST UNATTENDED DISRUPTIVE BOUNDARY. *** After that single confirmation the
    withdrawal of "be at the machine" stands on a verified mechanism rather than on a
    message. This is one look at a rig, not a standing requirement for a person.

    STILL TRUE, and the reason the allowance list must include `StartModules`: if a download
    stops the CPU and `StartModule` is NOT answered, nothing else in the public API can bring
    it back. `StartModulesSelections.NoAction` is the ZERO value AND it applies cleanly — so a
    policy that merely un-denied `StopAll` without also answering `StartModules` would stop the
    rig, succeed, and leave it stopped while reporting success (R4a's hazard, exactly).

6. %MW IS STRUCTURAL, NOT PREFERENTIAL
--------------------------------------------------------------------------------

Four independent arguments, each arrived at from a different direction:

  1. it cannot suffer the silent layout-revert measured on 2026-08-11 [M, three times];
  2. `MB_HOLD_REG` requires standard access OR A MEMORY AREA [R for the status code 16#818C
     and the reported behaviour; the Siemens manual sentence itself was never retrieved —
     external gap G6, §14. TAG CORRECTED 2026-08-12 by audit: it read a bare [R]];
  3. adding a scan-stamp to a DB is a structural change; in `%MW` it is a code change;
  4. *** STRONGEST: standard access can never carry a memory reserve [R x4 + M x1, verified
     five ways], so a standard-access DB can NEVER be downloaded without reinitialization.
     Its layout is FROZEN FOR THE LIFE OF THE RUNNING PROGRAM — change one member and the
     whole DB resets to start values, in RUN, with no dialog and no error. ***
     *** TAG CORRECTED 2026-08-12 BY AUDIT, AND THE CORRECTION IS THE POINT OF THE EVIDENCE
     CONVENTION: THE PREMISE IS DOCUMENTED, THE CONCLUSION IS INFERRED [I]. *** The research

     Siemens documents both halves and JOINS THEM NOWHERE." So "standard access has no memory
     reserve" is [R]; "therefore it can never download without reinitialization" is [I]. This

     which is exactly why it must not wear a borrowed tag. The argument still holds — three
     other independent arguments reach the same place, and one of them ([M], the measured
     layout revert) is the most solid thing here.

Any design that re-derives the map at a boundary is safe ONLY on `%MW`. On a DB mirror every
re-derivation is a silent wipe.

7. WHAT THE TEST ENVIRONMENT REPLACES
--------------------------------------------------------------------------------

IT REPLACES THE FUNCTIONAL REVIEW, where a rig is available. Observing behaviour against a
spec-derived vector is stronger evidence than an AI reading code against a register.

IT DOES NOT REPLACE THE OTHER REVIEWS. Conventions and simplicity say nothing about
behaviour and behaviour says nothing about them. They stay in loop 1, twice (§1.1).

*** THE TRAP: COVERAGE. *** A functional reviewer reads EVERY requirement and returns a
verdict on each. A test suite covers only what somebody wrote a vector for. This trades a
COMPLETE BUT FALLIBLE check for a NARROW BUT SOLID one — a good trade only if the narrowing is
MEASURED. Without a coverage gate, "all tests passed" is indistinguishable from "all
requirements verified", and the requirements nobody wrote a vector for look exactly like the
ones that passed.

*** RESOLVED 2026-08-12. THE DENOMINATOR, THE BUCKETS, AND WHAT THE GATE ACTUALLY GATES. ***

*** THE UNIT IS THE SPECIFICATION-DERIVED ASSERTION, QUALIFIED BY INSTANCE (D35). *** Draft 04
said CLAUSE here and mandated ASSERTION in D35; this is the resolution, and it is not a
compromise between them — it keeps exactly what each was protecting.

*** THE INVARIANT THAT DECIDES IT, AND IT IS ABSOLUTE: THE DENOMINATOR COMES FROM THE
SPECIFICATION, NEVER FROM THE TEST SUITE. *** Any unit defined by what somebody wrote a vector
for is SELF-REFERENTIAL — you cannot be missing an assertion nobody wrote, so coverage is
always 100% and the gate is theatre.

    So the question is not "clause or assertion". It is WHERE THE UNIT IS ENUMERATED.
      VECTOR-DERIVED assertions .... forbidden. This is what draft 04 §7 was right to reject.
      SPEC-DERIVED assertions ...... required. Decomposing a clause into its atomic assertions
                                     is a SPECIFICATION-SIDE operation, performed against the
                                     requirement text and complete BEFORE any vector exists.
                                     A vector then CITES into that enumeration; it cannot
                                     extend it, and an assertion no vector cites is exactly
                                     what the gate is for.

WHY ASSERTION AND NOT CLAUSE, given the invariant is satisfied either way: a clause carrying
two assertions — "shall open when X and close when Y" — is marked COVERED by a vector testing
only one, and the other vanishes silently. Many vectors per clause is the EXPECTED shape, which
makes this the normal case rather than an edge one: five vectors on that clause can all
exercise X, and a clause-level denominator reports it fully covered while nothing ever tested
Y. That is this project's own correlated-check failure wearing coverage clothing.

*** AND THE DECOMPOSITION IS NOT DISCOVERED AT THE VECTOR. *** Stated because the first
formulation of D35 said the vector's declaration is "exactly what makes the gap visible", which
is vector-derived discovery by another name and is precisely what the invariant above forbids.
The gap is made visible by the SPEC-SIDE DECOMPOSITION; the vector's citation is checked
AGAINST it, and a vector citing an assertion the decomposition does not contain is an ERROR in
the vector, not an extension of the denominator.

THE THREE "THIS ALREADY EXISTS" REASONS SURVIVE THE CHANGE, with one adjustment:
  - `TestVector.Basis` ALREADY CITES THE CLAUSE — it must now cite the clause AND the
    assertion within it. That is the one piece of new metadata this costs, and it is a field,
    not a mechanism.
  - it remains LIKE-FOR-LIKE OR STRICTLY FINER than what it replaces: the functional
    reviewer's verdict was per-requirement, so an assertion-level verdict is at least as
    granular, which keeps the substitution honest rather than approximate.
  - `converter relation-reconcile` already works on `(instance, relation-id)` pairs, so
    instance qualification has precedent here rather than being invented.

*** AND IT RETIRES A PRECONDITION RATHER THAN ADDING ONE. *** Draft 04 required verifying that
rung-B/C artifacts emit ATOMIC clauses, on pain of silent under-counting. Under a spec-derived
assertion denominator that check stops being load-bearing: if clauses are already atomic the
assertion is trivially the clause and the citation costs nothing, and if they are not, the
decomposition is where the extra assertions are discovered. Either way nothing vanishes
silently, which was the whole worry.

SIGNALS ARE A SECOND, INDEPENDENT CHECK — NOT THE DENOMINATOR. `converter signal-sweep`'s
residue answers a different question: is there a SIGNAL no requirement mentions? That catches
SPEC gaps where clause coverage catches TEST gaps. Two failure modes, two tools, neither
substituting for the other.

THE FOUR BUCKETS. Every ASSERTION lands in exactly one, and the wave reports all four:
    COVERED             a vector exists and cites this assertion
    OUT-OF-SCOPE        not a control-logic requirement at all (wiring correctness, HMI
                        behaviour, operator procedure). These were out of scope for the
                        FUNCTIONAL REVIEWER too — they belong to commissioning, not testing,
                        and calling them "untestable" overstated the gap.
    DEFERRED            testable, but blocked or not yet written. Two sub-cases, and the
                        second is the interesting one:
                          - no vector yet — owner and date;
                          - NEEDS MODEL FIDELITY WE DO NOT HAVE. M4 already routes these to a
                            refusal, and a refusal naming the missing capability is a MODEL
                            TASK, not an untestable requirement. This sub-case SHRINKS as the
                            library matures.
    UNTESTABLE-ON-RIG   genuinely so. *** SHOULD BE NEARLY EMPTY *** — see below.

*** WHY IT SHOULD BE NEARLY EMPTY, correcting an earlier overstatement in this document. ***
An earlier draft warned that with no I/O wired, "no actuation can be observed", so the
untestable set might be large. THAT CONFLATED PHYSICAL ACTUATION WITH THE PROGRAM'S OUTPUT
DECISION, and only the second matters for control logic. A coil energising IS the decision,
and the copy layer latches it — so "does the interlock prevent the valve opening?" is answered
completely by the coil never energising, whether or not anything is wired to it. With coil
latching and event scan-stamps, control-logic requirements are broadly testable. If this
bucket turns out large, that is a FINDING TO CHASE, not a category to accept.

*** ONE REAL CATEGORY THIS DID NOT ACCOUNT FOR, ADDED 2026-08-12 BY AUDIT: FIRST-SCAN AND
POWER-UP REQUIREMENTS. *** "On start-up all valves shall be closed"; "retentive setpoints shall
survive a restart". The inert phase establishes a start STATE but cannot produce a first SCAN,
and OB100 never runs again once the CPU is in RUN — so these are genuinely untestable IN A
WAVE. They are NOT untestable ON THE RIG: §16.6 (X-F) routes them to the disruptive boundary,
which already stops and restarts the CPU. Classify them as a STARTUP TEST class, never as
UNTESTABLE-ON-RIG — the bucket stays nearly empty, but only because the class exists.

*** THE GATE IS `UNCLASSIFIED = 0`, NOT A PERCENTAGE. *** A threshold fails in a specific way:
the uncovered remainder is NOT random. It is the requirements that are hard to test, which
correlates with hard to implement, which is where defects live — so a threshold silently
concentrates risk in the worst place while reporting a comfortable number. Every ASSERTION
must have been CONSIDERED; not every assertion must have a test.

*** AND THE GATE STOPS THE CLAIM, NOT THE RUN. *** Blocking a wave for a bookkeeping reason
spends the scarce thing (rig time) to enforce the cheap thing. A wave with incomplete
classification still produces useful results — it simply MAY NOT CLAIM "requirements
verified". That decouples honesty from throughput.

HONEST LIMIT, ACCEPTED: the gate proves someone LOOKED, not that they looked WELL. Classifying
is cheap; classifying honestly is not, and under pressure everything becomes DEFERRED while
the gate still passes. What carries real weight is DEFERRED items having an OWNER and a DATE,
with their count and AGE reported every wave — aging deferrals are the signal, not the
classification.

CLASSIFICATION IS STICKY, so this does not churn: once an assertion is classified it stays
until the requirement text changes or the implementing block changes — detectable by hashing
the assertion text and by `converter ir-hash` respectively. Re-classification is proportional
to CHANGE, not to total requirement count.

*** ONE CONSEQUENCE OF THE ASSERTION UNIT THAT MUST BE BUILT FOR, NOT DISCOVERED: RE-READING A
CLAUSE CAN CHANGE ITS DECOMPOSITION. *** A clause previously read as one assertion may later
decompose into two. That is NOT a classification change and must not be silently absorbed as
one — the new assertion is UNCLASSIFIED and the gate must fail until someone rules on it.
Hashing the CLAUSE text alone would miss this, because the clause did not change; the
DECOMPOSITION did. So the sticky key is (clause hash, assertion index, assertion text hash),
and a decomposition that yields a different count than last time is reported as its own event.

AND THE INDEPENDENCE MUST SURVIVE THE SWAP. Part of what a functional reviewer provided was a
SECOND READING of the specification. A vector authored by a different agent preserves that;
one authored by the block's own author does not — it moves the failure rather than removing it
(D6).

7a. FAILURE ATTRIBUTION — WHICH OF FIVE THINGS IS WRONG
--------------------------------------------------------------------------------

A red result has FIVE possible causes, and the receiving agent is the WORST-PLACED party to
judge: it did not write the vector (D6) or the model (M1), so it can see only its own block
and will suspect that first.

  1. THE BLOCK IS WRONG           — the finding you wanted
  2. THE MODEL IS WRONG           — fidelity, or a modelling error
  3. THE VECTOR IS WRONG          — the author misread the spec
  4. ANOTHER AGENT INTERFERED     — shared state the graph did not predict
  5. *** THE BLOCK WAS NEVER DOWNLOADED *** — the cheapest to rule out and the most
                                    embarrassing to miss

THE DEFAULT FAILURE MODE IS AN AGENT "FIXING" CORRECT CODE UNTIL A WRONG TEST PASSES. Worked
example: a fill block implements a pre-act offset correctly; the model has no in-flight mass,
so nothing overshoots, so the fill stops short and the test fails; the agent removes the
offset and the test passes. *** THE CORRECT IMPLEMENTATION HAS BEEN ENGINEERED OUT BY THE
TEST, and the report says green. ***

THE APPROACH (decided 2026-08-12): the agent judges — but only after the FREE evidence is
attached to the result automatically. Cost, honestly priced:

  FREE, attached to every result:
    - the CO-RUNNING LOG (D21)                          -> cause 4
    - the VALIDITY STAMP comparison (DB-2): block
      unchanged but result changed                      -> not cause 1, by construction
    - the LOAD MANIFEST check (§9a): is this block
      in the last manifest at all?                      -> cause 5
    - CROSS-AGENT PATTERN: same shape failing across
      several agents                                    -> model or environment, not N bugs
    - the FIDELITY BOUNDARY CHECK — already enforced
      at ADMISSION by M4, so it never reaches diagnosis -> cause 2, prevented not diagnosed
    - *** ASSERT ON THE STIMULUS, NOT ONLY THE RESPONSE *** — the model is a block and its
      state is readable, so check the model actually produced the rate/setpoint the vector
      parametrised. If it did not, the fault is the model or the parametrisation and the
      block is exonerated WITHOUT BEING TOUCHED. Sharpest cheap discriminator available;
      costs a few registers in the mirror.

  CHEAP, on failures only:
    - BASIS RE-DERIVATION — one spec read by the vector's author        -> cause 3
    - RE-RUN IN ISOLATION via the enable bitmask — one test, a register
      write, NO download                                               -> cause 4, confirmed
    - DOES IT REPRODUCE? intermittent points at interference or the observability floor

  EXPENSIVE, and NEVER BY DEFAULT:
    - re-run against a DIFFERENT model of the same equipment. Only needed for "the model
      claims to represent this and does it wrong", which is a MODEL REVIEW problem (M5), not
      a per-failure diagnostic.

*** ONE HARD RULE: A FAILING TEST MAY NOT BE CLOSED BY CHANGING THE BLOCK UNTIL THE VECTOR'S
BASIS HAS BEEN RE-CONFIRMED. *** One spec read, on failures only, and it is what stops the
worked example above.

ORDER OF ELIMINATION: deployment, interference, vector, model, THEN block. *** THE BLOCK IS
THE LAST HYPOTHESIS, NOT THE FIRST *** — precisely because the receiving agent's instinct is
the reverse.

WORTH MEASURING ON THE FIRST REAL WAVE: log the eventual TRUE cause of every failure. If they
are overwhelmingly cause 1, most of this is over-engineering and the co-running log plus a
re-run-in-isolation button would cover it.

8. THROUGHPUT — WHERE THE COST ACTUALLY IS
--------------------------------------------------------------------------------

MEASURED BY THE OWNER, from experience: *** download time scales with the NUMBER OF OBJECTS,
not with the act of downloading. *** A small delta is around 20 seconds; a full program of
~100 objects around 2 minutes. Worked through the <=20 budget:

    6 agents  x (FB + UDT + iDB) = 18 objects = 1 download  ~= 20-25 s   [CORRECTED]
   20 agents                     = 60 objects = 3 downloads ~= 1-1.5 min [CORRECTED]

*** BOTH FIGURES CORRECTED 2026-08-12 BY AUDIT — THEY CONTRADICTED THIS SECTION'S OWN PREMISE,
AND REAL MEASUREMENTS EXISTED AND WERE NOT USED. *** They read "1-2 min" and "3-6 min", which
cannot follow from "time scales with the NUMBER OF OBJECTS" when ~100 objects takes ~2 min:
18 objects then costs about 22 s, and the premise explicitly denies a fixed per-download cost
that could account for the rest. MEASURED, from the probe logs, wall-clock end to end AND
INCLUDING Portal attach, project open and a read-only download-plan — so the download itself
was shorter still:

    99 objects (full)         80.9 s   [M, 2026-08-12]
     1 object  (differential) 32.1 s   [M, 2026-08-12]

*** AND THE OWNER'S ~20 s / ~2 min FIGURES ARE RECOLLECTION, NOT MEASUREMENT [I]. *** They are
tagged here because every throughput number in this document descends from them and they
carried no tag at all. They are consistent with the two measurements above, which is why they
survive — but design gap G-5 ("DOWNLOAD DURATION — MEASURE IT. One number.") was recorded as
CLOSED on recollection while three real measurements sat unused in the same job scratch.

MINUTES, NOT HOURS. Downloads are cheap enough that there is no reason to hoard them, which
reinforces DB-4's inversion: smaller, more frequent wave sets are fine.

*** THEREFORE DOWNLOADS ARE ALMOST CERTAINLY NOT THE BOTTLENECK. TEST EXECUTION IS. *** That
promotes D12 — time compression in the models — from a good idea to THE throughput lever.

--- CORRECTED IN DRAFT 04. The paragraph above is right about downloads and WRONG about what
    replaces them. ---

Under D26 the cost of the test half of a wave is:

    wave = download boundary + SUM over tensors ( inert reset + MAX test duration in tensor )

Worked, for 6 agents x 5 vectors = 30 tests, packing 6 wide into *** 5 TENSORS ***:

    inert 2 s,  longest test  5 s,  5 tensors  ->  ~55 s
    inert 5 s,  longest test 10 s,  5 tensors  ->  ~1.6 min
    inert 10 s, longest test 60 s,  5 tensors  ->  ~6 min

*** THE SAME 30 TESTS COMPUTED AS A SERIAL SUM GIVE 3.5 TO 35 MINUTES, AND THE PACKED FIGURE
    IS ABOUT 6x SMALLER — 4x TO 6x ONCE THE DOWNLOAD BOUNDARY IS COUNTED ON BOTH SIDES. ***
    The packed figure is the correct one. The serial arithmetic was performed in this project
    first, believed, and used to argue that feedback latency would ruin IR development. It
    would not.

    *** THESE TWO NUMBERS WERE THEMSELVES WRONG UNTIL 2026-08-12, WHEN THE AUDIT CAUGHT THEM —
    THE THIRD ARITHMETIC ERROR IN THIS SECTION. *** They read "8 to 35 minutes" and "5 to 10
    times smaller". The lower bound silently omitted this section's own fastest row
    (30 x (2+5) = 210 s = 3.5 min), and *** A 10x RATIO IS ARITHMETICALLY IMPOSSIBLE HERE: ***
    packed and serial scale by the same (inert + test) term, so the ratio IS THE PACKING WIDTH
    BY CONSTRUCTION — 6x at 6 wide, and less once a fixed boundary is added to both. A section
    that exists to stop a wrong number being re-derived had an unachievable figure in its own
    correction, which is worth more caution than the number itself.

TWO CONSEQUENCES THAT CHANGE PRIORITIES:

  1. *** THE BOTTLENECK IS TENSOR COUNT, AND TENSOR COUNT IS SET BY CONFLICT DENSITY *** — so
     the throughput lever is DB-13's packing and D28's per-test model instances, not time
     compression. D12/D19 keep a narrower job: individually long tests (DB-12).
  2. *** AT ABOUT A MINUTE A WAVE, FEEDBACK LATENCY IS NOT THE PROBLEM; ITERATION COUNT IS ***
     (D30). Optimise the information a wave returns (DB-8) before optimising how often waves
     happen.

WHAT WOULD FALSIFY THE PACKED FIGURE: tests that do not pack. If conflict density forces 1-2
per tensor, tensor count returns to test count and the serial arithmetic becomes correct after
all. That is a measurement, not a judgement — see DB-13's closing note.

9. THE VERSION REGISTER — LOAD-BEARING IN THREE PLACES
--------------------------------------------------------------------------------

The marker DB exists because the CPU will not state its own identity, so the PROGRAM
publishes it. The same trick answers post-download verification without any upload.

The coordinator knows exactly which IR set it downloaded, computes a build hash, and
GENERATES A LITERAL into the copy layer:

    MOVE  16#A93F2C71  ->  MD_ProgramVersion

That constant lives IN THE CODE, so it can only be present if that code is running.
Verification becomes ONE REGISTER READ — no upload, no Portal session, sub-second.

*** IT IS `%MD`, NOT `%MW` — CORRECTED 2026-08-12 BY AUDIT, AND IT MATTERS BECAUSE THIS IS THE
ONE PLACE THE MECHANISM IS SPECIFIED AND WILL BE COPIED. *** A `%MW` is a 16-bit WORD;
`16#A93F2C71` is eight hex digits, 32 bits. The line as previously written does not compile.
Consequences to carry through: the version register occupies TWO Modbus holding registers, the
word-order rule stated later in this section applies to it, and DB-6's "the map artifact
carries a hash; the version register carries the same value" means a 32-bit hash across that
same register pair. A 16-bit truncation of a build hash would also collide far too easily to
serve as an identity.

WHAT IT CATCHES: a download that aborted or was refused (the register still shows the OLD
version — external gap G4's undocumented half-loaded case, detected without needing Siemens to
document it); a download that never reached the device; and the SETTLING WINDOW, since the
value flaps or reads old until integration completes, so waiting for stability MEASURES the
window rather than guessing it.

WHAT IT DOES NOT CATCH: individual block corruption. That is a reasonable trust boundary — TIA
performed the download; if the version constant is live, the code carrying it is live.

THREE PURPOSES, ONE MECHANISM, designed once: post-download verification (D14), settling-window
detection (DB-3), and guarding the frozen map (DB-6).

9a. THE LOAD MANIFEST — measured 2026-08-12, and better than the version register
    for one specific question
--------------------------------------------------------------------------------

*** A DOWNLOAD REPORTS, PER OBJECT, WHAT IT ACTUALLY LOADED. *** The `DownloadResult`
message tree contains one message per object, verbatim:

    'DB_RigMarker' was loaded successfully.
    'UDT_CmdAck' was loaded successfully.
    ... one per object ...

MEASURED, and both runs matched prediction EXACTLY:
    DIFFERENTIAL : 1 message  — `DB_RigMarker`, precisely the one block that had changed
    FULL         : 99 messages — and `download-plan` had reported 66 blocks + 33 PLC data
                   types = 99. The predicted count and the loaded count agree.

THREE USES, and the third is the valuable one:

  (a) POSITIVE EVIDENCE OF TRANSFER, replacing an inference from absence.
      *** THIS CORRECTS THE PROBE. *** `download-probe` currently reports transfer by
      searching for "has not been loaded" / "up-to-date" and concluding TRANSFERRED when
      absent, stating in its own output that "TIA emits no positive 'the software was
      loaded' sentence to key on". THAT IS FALSE — there are 99 of them. The verdict should
      key on the per-object load messages and report the COUNT. Fix pending.

  (b) CONFIRMATION OF *WHAT* WAS DOWNLOADED, per object, not merely that something was.

  (c) *** A CROSS-CHECK ON DB-1. *** The coordinator PREDICTS a change set; TIA REPORTS the
      set it actually loaded. Comparing them checks our change tracker against TIA's own
      online/offline comparison, on every download, for free. A MISMATCH MEANS OUR TRACKER
      IS WRONG — and DB-1's baseline is what every STOP/RUN(Init) prediction and every
      <=20-object batching decision hangs off, so being able to falsify it continuously is
      worth more than the other two uses combined.
      It also closes a hole named in DB-1: `openness-cli export-all` reads the OFFLINE
      PROJECT, so it cannot detect a partially-applied download. The manifest reports what
      the DEVICE accepted.

RELATIONSHIP TO THE VERSION REGISTER (§9) — they answer different questions and neither
replaces the other:
    LOAD MANIFEST   : what moved in THIS operation. Per object. Available only at download
                      time, from the download's own result.
    VERSION REGISTER: what is running NOW. Readable at any time, over Modbus, sub-second,
                      and the only thing that detects an aborted or half-applied download
                      after the fact.

9c. THE DOWNLOAD FEEDBACK PARSER — a required component
--------------------------------------------------------------------------------

The `DownloadResult` message tree is the richest evidence any download produces, and every
run so far has proved it carries more than the design assumed. It needs a real parser, not
phrase-matching bolted on.

WHAT IT MUST EXTRACT:

  1. *** THE LOAD MANIFEST *** — every `'<name>' was loaded successfully` message, as a SET
     of object names plus a count. This is the positive evidence of transfer (§9a) and the
     cross-check on DB-1.
  2. *** RUN-STATE TRANSITIONS *** — `PLC_1 stopped.` / `PLC_1 started.`, in order, so the
     coordinator knows the state the CPU was left in rather than inferring it.
  3. *** NON-OBJECT LOADS *** — `Hardware configuration`, `Connection configuration`,
     `Routing configuration` were each reported with their own wording. A parser keyed only
     on the block form would silently drop all three.
  4. *** THE UP-TO-DATE SIGNAL *** — `The software has not been loaded, because it is
     up-to-date`, which means SUCCESS WITH NOTHING TRANSFERRED.
  5. Per-node state, error and warning counts, preserved with their nesting.

DESIGN RULES, each earned by something that has already gone wrong:

  - *** NEVER READ `state=Success` AS EVIDENCE OF TRANSFER. *** The first run that returned
    Success transferred nothing.
  - *** REPORT THE COUNT, NOT A BOOLEAN. *** "1 object" versus "99 objects" is what makes the
    DB-1 cross-check possible; a yes/no throws that away.
  - *** UNDETERMINED IS A THIRD VERDICT AND MUST NEVER COLLAPSE INTO A NEGATIVE. ***
  - *** SURFACE UNRECOGNISED MESSAGE SHAPES — DO NOT DROP THEM. *** Four distinct message
    vocabularies have appeared in six runs, and each new download option produced one nobody
    predicted. A parser that classifies only what it knows will go quietly blind exactly when
    something new happens, which is exactly when you need it.
  - Prefer POSITIVE evidence over inference from absence. The probe currently infers transfer
    from the absence of an up-to-date phrase while sitting on 99 positive load messages — the
    correction §9a records.
  - *** AND THE DEFECT IS WORSE THAN §9a DESCRIBES — FOUND 2026-08-12 BY AUDIT. *** The probe's
    verdict line does not only infer from absence; it ALSO READS `state=Success` directly:
    "WAS ANYTHING TRANSFERRED? *** YES - THE SOFTWARE WAS LOADED (state=Success, errors=0)."
    That is the exact reading the first rule in this list forbids. *** FIXING ONLY THE
    ABSENCE-INFERENCE LEAVES THE FORBIDDEN READING IN PLACE *** — both have to go, and the
    replacement for both is the load manifest.
  - AND THE SAME LOG STATES, WRONGLY, THAT "TIA emits no positive 'the software was loaded'
    sentence to key on" while carrying 99 sentences of exactly that form. A parser built from
    that sentence would be built to do the wrong thing on purpose.

WHERE IT IS USED: post-download verification (with §9's version register), the DB-1
cross-check, run-state tracking for DB-3's settling window, and the per-agent results that
carry the co-running log (§2.4).

10. PROTOCOL COEXISTENCE
--------------------------------------------------------------------------------

"Tolerate disruption" understates it. *** `MB_SERVER` IS PART OF THE PROGRAM BEING

11. MODELS, INERT STATE, FAILURE HANDLING, PROVENANCE
--------------------------------------------------------------------------------

MODELS (D4, D12). Driving raw values over the wire cannot express time: round trips are
79-108 ms [M] against a scan of ~10 ms, and a PID loop cannot be closed over a VPN at all.
Parametrising a PLC-side model generates the dynamics AT SCAN RATE inside the controller; the
link carries parameters and results. Already proven in this codebase by the live program's own
plant simulation.

*** THE MODEL-AUTHORING CONTRACT (resolves O4 and O5, decided 2026-08-12) ***

M1. AN INDEPENDENT lad-coder AUTHORS THE MODEL — never the agent that wrote the block it will
    test. Same independence rule as D6, same reasoning.

M2. *** THE PHYSICAL ANALYSIS IS GROUNDED IN THE EQUIPMENT, NOT IN THE CONTROL SPECIFICATION.
    *** This is the load-bearing half of M1 and it is easy to satisfy in appearance only. A
    model derived from the control spec — or from the same P&ID / equipment-spec artifacts the
    block was designed from — INHERITS THAT SPEC'S ASSUMPTIONS. A spec that never considered
    in-flight material yields a model with no in-flight material, and a block that ignores it
    passes. *** THE SPEC'S BLIND SPOTS BECOME UNTESTABLE, and the independence bought by using
    a different agent is spent, because both read the same source. *** The analysis must come
    from how the EQUIPMENT behaves — load-cell dynamics, settling time, in-flight mass, valve
    travel, sensor quantisation — not from what the control spec says about using it.

M3. EVERY MODEL CARRIES A FIDELITY DECLARATION: what it does and does NOT represent (noise,
    lag, overshoot, in-flight mass, saturation, quantisation), plus a declared SCAN-TIME
    BUDGET (M6). It is reproduced in every result derived from it, so a green is never read
    without its caveats.

M4. *** A VECTOR MAY ONLY ASSERT BEHAVIOURS THE MODEL CLAIMS TO REPRESENT; THE RUNNER REFUSES
    IT OTHERWISE. *** This makes fidelity MACHINE-CHECKABLE in exactly the way `Observability`
    already makes sampling limits machine-checkable, and it reuses a discipline the codebase
    has proven it will honour rather than adding one nobody enforces. Same principle: a green
    that cannot mean anything is worse than a refusal.

M5. *** A MODEL GETS MORE REVIEW THAN A BLOCK, NOT LESS — THE BLAST RADIUS IS INVERTED. *** A
    wrong block fails its own tests and the system catches it. A wrong model SILENTLY CORRUPTS
    EVERY VECTOR THAT USES IT, and the more useful the model, the more results it quietly
    invalidates. So models go through the same review path as blocks — conventions, simplicity,
    and a functional review against the physical analysis — plus validation against real plant
    data wherever any exists. Where none exists, that ABSENCE is recorded in the fidelity
    declaration.

M6. MODELS COMPETE FOR SCAN TIME. Every model runs every scan and they accumulate with agents,
    which interacts with OB80's overrun handling and the <=20-object batching. The declared
    budget makes the ceiling visible before it is hit rather than discovered as a cycle-time
    trip mid-wave.

M7. *** MODELS ARE PROVISIONAL UNTIL REVIEWED AND VALIDATED. *** The library ACCRETES from
    models written to order, and the trap in that is that the FIRST few become the standard by
    default — including their limitations, unexamined, and written before any wave had taught
    anyone which fidelity actually matters. Promotion into the library is a DECISION, never a
    consequence of having been first.

THE WORKED EXAMPLE THAT DECIDES M2 AND M4. A fill-control block closes the valve when weight
reaches setpoint. Against an idealised weigher — instant response, no material in flight — it
passes cleanly. On the real plant, material already falling continues after the valve closes,
so the vessel overshoots and the correct implementation needs a pre-act offset. *** THE
IDEALISED MODEL DOES NOT MERELY MISS THE DEFECT — IT CERTIFIES THE NAIVE IMPLEMENTATION AND
WOULD REJECT THE CORRECT ONE, *** which closes "early" and under-fills against a model with no
in-flight mass. That is worse than having no test.

INERT STATE (D5). FB statics survive between tests, so results depend on wave ORDER. A
GENERATED reset routine, triggered by a command register, with retentive members explicitly
written. *** THE RESET IS READ BACK AND CONFIRMED *** — an unverified reset is the "a warning
is not a gate" shape. Per-test instance DBs (D10) remove most of the need.

FAILURE HANDLING. Reject both a pre-wave smoke pass (costs time every wave to guard something
rare) and accept-the-risk-then-serialise (the expensive part is ATTRIBUTION). Instead:
generate an OB80 so an overrun is LOGGED rather than STOPping the CPU; write a "block currently
executing" register so OB80 attributes it for free; keep the block-enable bitmask as runtime
data so bisecting is a register write.
  Justified by COST ASYMMETRY, not probability: after a STOP a human must restore RUN, so
  unattended, one bad block turns a wave into a dead night.
  HONEST LIMIT: OB80 does not save you from a true infinite loop.
  NOTE: OB80 is itself a STOP-class change (a new OB), so it is installed at rig setup or via
  the deferred queue — never mid-wave.

PROVENANCE (D6). `TestVector.Basis` is required; a vector that cannot cite its specification
clause is not admissible into a wave.

BYTE AND WORD ORDER. Because we author both ends the convention is ours and a round-trip proves
the halves agree. ONE RESIDUAL: `MB_SERVER`'s own byte-to-register presentation is Siemens'
behaviour, which no fake we write can validate. Build swap as a configurable transform and
CALIBRATE with a known bit pattern — one measurement, once.

12. THE OBSERVABILITY FLOOR
--------------------------------------------------------------------------------

Polling observes at roughly 100 ms against a scan of ~10 ms, so a one-scan event is about ten
times below anything a sampler can see. NO POLLING RATE RECOVERS IT, and no protocol choice
changes it.

So the copy layer provides: a FREE-RUNNING SCAN COUNTER (always, unconditionally — one counter
for the whole program; its absence silently degrades every `WaitScans` into a wall-clock guess
on a non-real-time host); LATCHED TRANSIENTS (default on for coil-shaped signals — set-dominant
in the copy layer, cleared at TEST START rather than read-then-clear, so an observation does not
drag the write fence in); and EVENT SCAN-STAMPS (opt-in per signal in the map — a latch answers
"did it happen", a stamp answers "when, relative to what", at roughly 32x the memory).

*** AND THE "WHAT" A SCAN-STAMP IS RELATIVE TO IS NOW DEFINED: THE START BOOL'S RISING EDGE
(D37). *** Until that decision existed this section asked stamps to answer "when relative to
what" while the design supplied no origin, so a stamp was an absolute counter value that only
became meaningful by comparison with other stamps. Stamps are now DIFFERENCES IN SCANS FROM
T=0, which is the unit the whole observability argument is conducted in.

    A COROLLARY WORTH BUILDING FOR: the scan counter is free-running and WILL WRAP. A stamp
    taken as a difference from T=0 is immune to a wrap that happens between waves, which an
    absolute stamp is not — but a wrap DURING a long test still has to be handled in the
    subtraction rather than assumed away.

      STILL TO VERIFY BEFORE RELYING ON ANY OF IT: that a throw inside the delegate propagates

      path. The ORIGINAL question below is retained because it is what the ruling answers.

      THE ORIGINAL QUESTION: *** WHICH UNHANDLED CONFIGURATIONS ACTUALLY ABORT? *** Measured 2026-08-12: unhandled ABORTED for `StopModules`,
      `DataBlockReinitialization` and `OverwriteSystemData`, and DID NOT abort for
      `UserManagementDownload` — that download completed with TIA applying a default we
      neither chose nor can see. The whole protection model in R4/R8 rests on "refuse to
      answer => prevented". For any configuration that behaves like UserManagementDownload,
      refusing prevents NOTHING and produces the ILLUSION of a guard: the log reads "left
      unhandled on purpose" and the download reports Success.

      *** DECIDED 2026-08-12 — THE FIX IS TO THROW FROM THE DELEGATE. *** If we will not
      answer a configuration, WE abort the download rather than hoping Openness does. That is
      UNIFORM across every configuration including ones nobody has seen yet — which, given
      that each of the last three runs produced a configuration nobody predicted, is the case
      that matters. It also keeps the reporting honest: an abort WE caused is distinguishable
      from one TIA caused, the same way FailedToApply was separated from RefusedByPolicy.
      VERIFY BEFORE RELYING ON IT: that a throw inside the delegate propagates and leaves the
      CPU untouched rather than half-loaded — external gap G4, now on the critical path.

      *** AND A LOG, FOR UNATTENDED RUNS. *** Every configuration NOT SEEN BEFORE is
      registered, and — the part that makes it useful — SO IS WHAT HAPPENED WHEN WE DID NOT
      ANSWER IT: aborted, or completed anyway. Without the outcome the log tells you a new
      configuration exists but not whether the guard held for it, which is the only thing a
      later fix wave needs.

      WORKED FAILURE, for anyone tempted to leave this: `SelectiveDeleteDownload` offers
      `AcceptAll | DeleteSelected` and NO NoAction. Rule 3 leaves it unhandled. If it behaves
      like UserManagementDownload, TIA proceeds and deletes something; the log reads "left
      unhandled on purpose"; the download reports Success; and the load manifest may never
      mention what was removed. A silent destructive path wearing the shape of a refusal.

  O10. *** CLOSED 2026-08-12 — AND STRUCTURALLY, NOT BY DEPRIORITISATION. *** The owner ruled
      it unimportant and said it would surface as we run. It is stronger than that: *** D32
      makes the question UNABLE TO RECUR. *** We could not see which selection TIA applied
      only because we LET TIA CHOOSE by leaving the configuration unhandled. Under D32 nothing
      is ever left unhandled — an unanswered configuration aborts — so TIA never again applies
      a selection on our behalf, and there is never again a selection we cannot see.
      WHAT REMAINS IS PURELY HISTORICAL: one download on 2026-08-12 had one of
      `KeepOnlineUserManagementData`, `UpdateUserManagementDataButKeepOnlinePassword` or
      `DownloadAllUserManagementDataResetToProject` applied to a scratch project on a bench
      rig, and the result messages do not say which. Nothing downstream depends on knowing.

16. GAP ANALYSIS — FAULT PATHS AND INTERACTIONS THE DESIGN DID NOT CONSIDER
--------------------------------------------------------------------------------

Written 2026-08-12 by walking the design for HOLES rather than for inconsistencies. Each item
is a real gap in what is written above, not a restatement of a known unknown. Ordered by how
badly they bite; each carries a recommended treatment so none of them reopens the design
conversation.

*** STATUS: THESE TREATMENTS ARE PROPOSALS, NOT RULINGS. *** None carries a D-number, and §15
is the disposition of the O-questions only. X-A, X-C and X-E block the build and need a
decision before it proceeds; the rest can be ruled alongside.

*** NUMBERED X- RATHER THAN G- DELIBERATELY (2026-08-12). *** `G` was already carrying two
unrelated series — the SEVEN DESIGN GAPS G-1..G-7 (all closed; §13's title refers to G-7) and
the EXTERNAL VENDOR UNKNOWNS G1..G8 in §14, which is why "G8 — CLOSED, see §13" sits next to a
live G7 about something else entirely. A third G series would have been unreadable.

................................................................................
16.1  X-A  *** VECTOR APPLICATION IS NOT ATOMIC, AND A TORN WRITE IS UNDETECTABLE ***
................................................................................

Nothing in this design makes a vector's arrival at the PLC atomic. Modbus
write-multiple-registers carries at most 123 registers per transaction, so ANY tensor whose
combined vector data exceeds that is written across MULTIPLE transactions — and a link drop, a
retry, or a slow scan between them leaves the program running a HALF-APPLIED VECTOR. The block
sees a coherent-looking set of inputs that was never a vector anybody wrote, produces a result,
and that result is reported as a test outcome.

WHY IT IS INVISIBLE: every individual write SUCCEEDED. There is no partial-write error to
catch — the failure is at a level Modbus does not model.

*** AND IT IS A THIRD BOUND ON TENSOR WIDTH, alongside conflict-freedom and poll bandwidth
(D29): a tensor is also bounded by what can be applied atomically. ***

TREATMENT — stage-then-commit, a shape this design already uses elsewhere. Write vector data
to a staging region; then write ONE commit word, a sequence number, in a final single-register
transaction. The copy layer acts on staged data only when the sequence number INCREMENTS, and
the result package reports the sequence number it ran under. A torn write then leaves the
commit word unwritten and the tensor never starts — a detectable non-event instead of a
plausible wrong answer.

................................................................................
16.2  X-B  *** NO PER-TEST TIMEOUT — AND THE PACKER ALREADY NEEDS ONE ***
................................................................................

A vector whose expected condition never occurs hangs its tensor; a hung tensor hangs the wave;
nothing above bounds it. D26 computes a tensor's cost as the MAX TEST DURATION in it, which
presumes durations are known — yet no part of the design requires a test to declare one.

*** THE CHEAP RESOLUTION: THIS IS NOT NEW WORK. *** DB-13 cannot compute tensor cost without a
declared maximum duration per test, so the declaration is an input THE PACKER ALREADY REQUIRES.
Making it double as the timeout costs nothing and closes the hang.

TREATMENT — every vector declares a maximum duration, in SCANS (the unit §12 argues in) with a
wall-clock ceiling as backstop. Exceeding it is a DISTINCT OUTCOME — TIMED-OUT, never FAILED —
because "the condition never occurred" and "the wrong thing happened" are different findings,
and an agent told only FAILED will go and fix the wrong thing.

................................................................................
16.3  X-C  *** IF THE COORDINATOR DIES, NOTHING BRINGS THE RIG TO INERT ***
................................................................................

Every path to inert in this design is driven from the PC. If the coordinator crashes, loses its
network or is killed mid-tensor, the rig keeps running the last applied vector indefinitely —
resets released, models running, outputs driven. On restart the coordinator has no idea what
state the rig is in, and nothing above tells it to find out.

TREATMENT, two parts, and the second is the one that matters:
  1. ON CONNECT, ASSUME NOTHING — force inert before doing anything else, rather than assuming
     the rig is where it was left.
  2. *** A PLC-SIDE WATCHDOG IN THE COPY LAYER: no commit-word change for N seconds -> GO
     INERT AUTONOMOUSLY. *** The only protection that survives the PC dying, which is exactly
     the case part 1 cannot cover. It is a handful of rungs, and it is the difference between a
     crashed coordinator being an inconvenience and being a rig left driving outputs all night.

................................................................................
16.4  X-D  *** TIME COMPRESSION DESTROYS OBSERVABILITY — D12/DB-12 AGAINST §12 ***
................................................................................

Two parts of this design pull directly against each other and neither mentions the other.

§12 establishes that polling observes at ~100 ms against a ~10 ms scan, so a one-scan event is
already about ten times below the sampling floor. DB-12 requires models to run COMPRESSED so
long tests are runnable at all. *** BUT COMPRESSION SHORTENS THE REAL-TIME SEPARATION OF THE
EVENTS BEING OBSERVED. *** At 100x, a behaviour occupying 100 scans of plant time collapses
into one scan of real time — moving from comfortably observable to structurally invisible,
while every check still reports green because the assertion was simply never sampled.

*** SO THE COMPRESSION FACTOR IS NOT A FREE PARAMETER OF THE MODEL. IT IS BOUNDED BY THE
OBSERVABILITY REQUIREMENTS OF THE ASSERTIONS BEING TESTED. ***

TREATMENT — the runner computes the maximum admissible compression from the declared
observability of the assertions in the vector: one needing scan-level resolution caps
compression far lower than one checking a settled end state. A vector requesting more
compression than its own assertions can survive is REFUSED, with both numbers shown. Note the
interaction is with WHICH observability mechanism the assertion uses, not merely the factor —
LATCHING raises the ceiling substantially, because a latched transient survives compression
where a sampled level does not.

................................................................................
16.5  X-E  *** D32's EXCISION INVALIDATES DB-13's PACKING — A SEQUENCING HOLE ***
................................................................................

DB-13 colours the conflict graph AT ADMISSION, before the download. D32 excises a block AT
DOWNLOAD TIME, once an unhandled configuration is attributed to it. So the packing that was
computed no longer describes the test set that exists — and DB-9 says a submission is atomic,
admitted or refused WHOLE, which the excision has just violated from the other side.

Three things go inconsistent at once: the tensor assignment, the atomicity of the submission
the excised block belonged to, and any co-running-log expectation derived from the original
packing.

TREATMENT — excision forces a RE-PACK, never a hole in the existing one. The excised block's
tests are withdrawn and returned to their submitter as WITHDRAWN-NOT-FAILED (a distinct
outcome, since nothing about them was tested); the remainder is re-coloured, which may
legitimately yield FEWER tensors; and the affected submission is reported as PARTIALLY
WITHDRAWN rather than silently shrunk. DB-9's atomicity rule governs ADMISSION, not survival of
a download fault, and should say so explicitly.

................................................................................
16.6  X-F  *** FIRST-SCAN AND POWER-UP REQUIREMENTS ARE UNTESTABLE IN A WAVE — AND THE
           DESIGN ALREADY CONTAINS THE THING THAT WOULD TEST THEM ***
................................................................................

"On start-up, all valves shall be closed"; "retentive setpoints shall survive a restart". These
cannot be tested by the wave loop at all: the inert phase establishes a start STATE but cannot
produce a first SCAN, and OB100 never runs again once the CPU is in RUN. §7 claims the
UNTESTABLE-ON-RIG bucket "should be nearly empty" — this is a real category it did not account
for.

*** BUT THE CAPABILITY IS ALREADY PRESENT AND UNRECOGNISED. *** The disruptive boundary (D25,
R8) performs a FULL download that STOPS AND RESTARTS THE CPU — measured, §9b. That restart is
precisely the stimulus these requirements need, and it happens on a schedule the design already
manages.

TREATMENT — a distinct STARTUP TEST class, not packed into ordinary tensors but SCHEDULED AT A
DISRUPTIVE BOUNDARY and observed across the restart that boundary already performs. It costs no
additional CPU stop and converts a whole requirement category from untestable to routine. One
real constraint: the harness is DISCONNECTED across that download (D18), so first-scan evidence
must be LATCHED in the copy layer and read after reconnect — it can never be sampled live.

................................................................................
16.7  X-G  *** THE PACKER CAN MASK A GENUINE MULTI-WRITER DEFECT ***
................................................................................

Two blocks that both write the same coil are a conflict, so DB-13 puts them in different
tensors and both tests pass. *** THE SCHEDULER HAS SILENTLY REPAIRED A DEFECT THAT WILL SHIP. ***
In the deliverable both blocks run in the same scan cycle. `converter cross-check` already
reports multi-writer facts (C-308) that this design consumes ONLY as graph edges.

TREATMENT — conflict edges carry their PROVENANCE, and edges arising from multi-writer on a
DELIVERABLE signal are reported as FINDINGS as well as being used for packing. Separating them
is the right thing to do for testing and the wrong thing to do silently. Cheap: the fact is
already computed, only the reporting is missing.

................................................................................
16.8  X-H  *** D28's PER-TEST MODEL INSTANCING IS WRONG WHERE THE PLANT GENUINELY SHARES ***
................................................................................

D28 instances models per test so the conflict graph does not go complete. Correct when the
sharing is an artefact of authoring — WRONG when the plant itself shares the thing: one header
tank feeding two units, one common supply, one shared conveyor. Instancing produces two
independent tanks where reality has one, and both tests pass against a plant that cannot exist.

*** SHAREDNESS HAS TWO KINDS AND ONLY ONE IS REMOVABLE. *** Accidental sharing should be
instanced away; PHYSICAL sharing is a real conflict edge that must survive into the packing and
force those tests apart.

TREATMENT — the model declares which it is, and per M1/M2 that declaration comes from the
EQUIPMENT-GROUNDED PHYSICAL ANALYSIS the model was authored from, which is the only place the
distinction is knowable. A model that does not declare it is REFUSED rather than defaulted,
because both defaults are wrong in one direction.

................................................................................
16.9  X-I  *** MODELS ARE UNTESTED CODE THAT EVERY RESULT DEPENDS ON ***
................................................................................

§7a names "the model is wrong" as one of five causes of a red result, and M3/M4 require a
fidelity declaration — but NOTHING VERIFIES A MODEL. A model is IR like any other block,
authored by an agent from a written analysis, and every result is conditioned on it. A wrong
model does not produce one wrong test: it produces a consistent, plausible and wholly wrong
picture of a piece of equipment. §7a's own worked example — the pre-act offset engineered out
because the model had no in-flight mass — IS this failure, already written down.

TREATMENT, proportionate rather than a second test pyramid: a model carries a small set of
ANALYTIC SELF-CHECKS — known inputs with hand-computable outputs, closed-form where the physics
allows — run when the model is ADMITTED, not per wave. This does not prove fidelity; it catches
the sign error, the unit error and the transposed coefficient, which is the class that actually
occurs. The fidelity declaration remains the honest statement of what was not verified.

................................................................................
16.10 X-J  *** COORDINATOR-GENERATED BLOCKS ARE NOT IN THE CLAIMS REGISTRY ***
................................................................................

The coordinator generates the copy layer, the models, the %MW mirror scaffolding, OB80 and the
per-test instance DBs. All occupy BLOCK NUMBERS. `converter claim` exists to stop two parties
picking the same number, and the coordinator is a party that never claims.

TREATMENT — either the coordinator claims like anybody else, or a NUMBER RANGE IS RESERVED for
harness-generated objects and the claim tool refuses allocations inside it. The reserved range
is simpler and has a second benefit: harness objects become recognisable by number in every
listing, which also tells DB-7's cleanup what it owns.

................................................................................
16.11 X-K  *** A STOPPED CPU AND A DROPPED LINK LOOK THE SAME, AND THE API CANNOT TELL YOU ***
................................................................................

If the CPU goes to STOP mid-wave — a genuine fault, not a download — `MB_SERVER` stops serving
and the harness sees a dead connection, indistinguishable from a network fault. The escape
hatch is closed: it is MEASURED [M, in the probe's own online-mode reflection survey — NOT §13, which does
not record it] that `OnlineProvider` exposes NO CPU operating mode,
and that the download-configuration callback is the ONLY place a stop or start is expressible
in the public API. *** SO THE TOOLING CANNOT ASK WHETHER THE CPU IS RUNNING. ***

TREATMENT, partial and honest: the cases ARE partially separable BELOW Modbus, because a
stopped S7-1200 keeps its Ethernet interface up. A TCP connect to 502 REFUSED, against a host
still answering at IP level, is a live device not serving Modbus — the CPU-stopped shape. No
route at all is the network shape. Report the distinction as EVIDENCE, never as a verdict, and
treat either as wave-fatal. *** DO NOT BUILD A RECOVERY PATH THAT ASSUMES IT CAN TELL. *** This
gap is external, not ours to close.

................................................................................
16.12 SMALLER, RECORDED SO THEY ARE NOT REDISCOVERED
................................................................................

  - *** STABLE BUT UNEXPECTED. *** §9's version-register check confirms the value is STABLE. A
    value that is stable and NOT the one we downloaded means somebody else's program is on the
    rig — a manual TIA download being the obvious cause. That must refuse to test, and it is a
    different branch from "still settling".
  - *** MODELS AND INSTANCE DBs SHARE THE <=20 BUDGET. *** DB-4 counts an agent's FB, UDT and
    iDB and concludes "roughly six agents per download". Per-test instance DBs (D10) and
    per-test model instances (D28) are objects too, so the real per-agent object count is
    higher than three and that figure is optimistic in proportion.
  - *** EVERY REMOVAL PATH MUST RELEASE ITS CLAIM. *** Noted in DB-11 for a deleted block; it
    applies to DB-7's cleanup generally, or numbers leak until the range is exhausted.
