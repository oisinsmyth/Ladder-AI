0. THE REVERSAL THAT SHAPES EVERYTHING
--------------------------------------------------------------------------------

Drafts 00 and 01 were built on "downloading stops the CPU, therefore batch". That is
BACKWARDS. Siemens, verbatim [R]: ***"STEP 7 always tries to download in RUN first. If you
do not want this to happen, you must put the CPU into STOP."***

On an S7-1200 V4 a new FB/FC/DB/UDT, a deleted one, an FB/FC code change, an OB code change
and an FB/FC interface change are ALL downloadable in RUN [R].

*** THE RISK IS NOT THAT DOWNLOADS HALT THE WAVE. IT IS THAT THEY DO NOT, AND SILENTLY
    REINITIALISE STATE. BUILD A CHANGE CLASSIFIER, NOT A BATCH LOCK. ***

And: **the download option you pass does not decide STOP/RUN** [R]. "Software (all)" and
"Software (only changes)" are not rows in Siemens' table — the Engineering System computes
the verdict from the change classes inside the delta, plus a size limit. You cannot choose a
safe option; you can only control what is IN the delta.

--------------------------------------------------------------------------------
1. THE LOOPS
--------------------------------------------------------------------------------

Three nested loops and two download queues. This section is the heart of the document.

................................................................................
1.1  LOOP 1 — one block, authored by one lad-coder
................................................................................

    author IR
      -> compile
      -> REVIEW SKILLS (conventions, simplicity)
      -> changes from skills
           +---------------------------------------------------+
           |  compile -> FUNCTIONAL REVIEW (the test) -> iterate |
           +---------------------------------------------------+
      -> REVIEW SKILLS again
      -> changes from skills
      -> one last test cycle if needed

*** WHY THE TEST LOOP IS BRACKETED BY TWO REVIEW PASSES. *** Fixing for FUNCTION can break
FORM, and fixing for FORM can break FUNCTION. Reviews before the bracket kill cheap defects
before they cost rig time. Reviews after catch what the functional fixes did to readability
and conventions. The final test cycle catches what those review-driven edits did to
behaviour. *** WITHOUT THAT LAST STEP THE BLOCK SHIPS IN A STATE THAT WAS NEVER VERIFIED —
its last verified state would not be its final state. ***

CONSEQUENCE, stated plainly: the test sits INSIDE loop 1, so a lad-coder's iteration rate is
capped by WAVE CADENCE, not by its own speed. That is accepted; at a minute or two per
boundary it is not the bottleneck (§8).

................................................................................
1.2  LOOP 2 — admission
................................................................................

A block enters the TEST project only after passing preflight and COMPILING CLEAN IN
ISOLATION.

Not bureaucracy: Openness cannot download a selection [M] — every download is
whole-software — so THE WHOLE PROJECT MUST COMPILE BEFORE ANYONE'S DOWNLOAD. Without
admission control one agent's broken block blocks every agent. A failing block is simply not
in the next batch.

................................................................................
1.3  LOOP 3 — the wave
................................................................................

    collect admitted SUBMISSIONS (DB-9 — atomic: vectors + observability + target blocks)
      -> PACK INTO TENSORS (DB-13 — colour the conflict graph; this fixes the wave's duration)
      -> derive map, generate copy layer / models / mirror
      -> batch into <=20 DEPENDENCY-CLOSED objects
      -> harness goes inert, DISCONNECTS
      -> download
      -> reconnect -> READ VERSION REGISTER -> confirm stable
      -> RUN THE WAVE:
             for each tensor, in order:
                 establish INERT for THIS tensor       (D33 — its start state, dynamics
                                                        untriggered, resets held, latches
                                                        released, nothing recorded)
                                                       [CORRECTED 2026-08-12: this read "for
                                                        the NEXT tensor", which inside a
                                                        for-each-tensor loop leaves tensor[0]
                                                        with no inert phase at all and runs
                                                        every tensor from its SUCCESSOR's
                                                        start state. D33's "computed per
                                                        boundary from tensor[k+1]" is right
                                                        because there the boundary FOLLOWS
                                                        tensor[k]; transcribed into this loop
                                                        it becomes THIS.]
                 VERIFY inert                          (D33 — two checks: start conditions
                                                        established AND dynamics quiescent)
                 raise the START BOOLS                 (D37 — on a LATER scan, never the same
                                                        one; this edge is the tests' T=0)
                 observe until the tensor completes    (tests within a tensor run CONCURRENTLY)
         -> unconditionally, pass or fail (D34) — a failing test never diverts the sequence
      -> distribute results (DB-8's package, including the co-running log slice, §2.4)

*** THE SHAPE TO HOLD ON TO: inert -> tensor[0] -> inert -> tensor[1] -> ... *** Tensors are
SEQUENTIAL; the tests inside one are PARALLEL. Wave duration is therefore set by TENSOR COUNT,
not test count, and each tensor costs its LONGEST member rather than the sum (D26, §8).

................................................................................
1.4  THE TWO DOWNLOAD QUEUES  *** the routing rule ***
................................................................................

Changes are ROUTED, not merely predicted:

  RUN-CLASS  — new/edited FB, FC, DB, UDT; code changes; new PLC tags.
               Flow through normal wave boundaries. Cheap, non-disruptive.

  STOP-CLASS — OB add/delete, OB property change, hardware configuration, retentivity
               settings, text lists.
               *** DO NOT flow through wave boundaries. They ACCUMULATE IN A DEFERRED
               QUEUE. ***

The deferred queue is drained when TESTING CANNOT PROGRESS (D24). At that point the
disruptive download happens, and testing resumes.

*** THIS MAKES DB-1 A ROUTER, NOT JUST A PREDICTOR *** — deciding which queue a change
belongs in is its primary job, and a better justification for building it than "predict the
outcome".

ACCEPTED CONSEQUENCE: an agent whose work needs a STOP-class change waits longer, because it
cannot be tested until the next disruptive boundary. That delay is unavoidable in any design
and is not treated as a problem.

2. HOW lad-coder INTERACTS WITH THE TEST ENVIRONMENT
--------------------------------------------------------------------------------

2.1  WHAT IT OWNS, AND WHAT IT DOES NOT

lad-coder authors PLANT LOGIC — blocks, IR, the things that implement requirements.

THE COORDINATOR GENERATES EVERYTHING ELSE: the %MW mirror, the copy layer with its latches
and scan-stamps, the block-enable bitmask, OB80, the register map. Per D13 instrumentation is
a property of the COPY LAYER, not of the blocks under test, so lad-coder never writes
observability code, and per D8 it never sees a register number — it speaks TAG NAMES.

2.2  WHAT IT NEVER DOES

  - *** IT DOES NOT WRITE ITS OWN TEST VECTORS *** (D6). An agent authoring both a block and
    its tests encodes its MISREADING into both, and the wave returns green having verified
    only self-consistency. This is the PlantAutoControl failure exactly.
  - *** IT DOES NOT TOUCH THE TEST PROJECT. *** The coordinator is its sole writer, which is
    what makes `SoftwareOnlyChanges` safe (DB-5): that option carries WHATEVER DIFFERS,
    decided by TIA, so an agent writing there could ship another agent's half-finished work.
  - *** IT DOES NOT TAKE THE PROJECT ONLINE. *** An Openness download is REFUSED in online
    mode [M, measured 2026-08-12]. One agent going online blocks the whole wave loop.
  - *** IT DOES NOT REVISE A SHARED UDT MID-WAVE-SET *** (D16). A modified UDT is
    `RUN (Init)` for EVERY DB built on it [R] — the widest blast radius available.

2.3  WHAT DOES NOT APPLY TO IT, so it is not over-generalised

The memory-layout revert on re-import [M, measured three times] bites STANDARD-ACCESS blocks,
which are coordinator-owned mirror scaffolding. lad-coder's ordinary plant blocks are
optimized and unaffected.

2.4  WHAT COMES BACK

Per-vector pass/fail with OBSERVED VERSUS EXPECTED, never a bare verdict — plus:

*** THE CO-RUNNING LOG. *** Results carry a slice of the wave's TIMELINE: what else ran, and
when. This exists because computed disjointness (D9) will sometimes miss coupling that is not
a code reference the graph can see — plant-model state being the obvious case. When agent A
opens a valve, the model raises a level, and agent B's level-alarm test fails, B's own code is
innocent and B would otherwise hunt a phantom. INTERMITTENTLY, which is worse than always.
The log does not prevent interference; it makes it DIAGNOSABLE.

Design implication: the wave must record a timeline, and each agent's results carry the
relevant slice.

*** HOW A FAILING VECTOR MUST BE READ. *** A failure is evidence the block disagrees with a
SPEC-DERIVED expectation. Fix the block against THE SPECIFICATION, not against the vector. An
agent that starts inferring requirements from test data turns the vector into the spec — and
since a different agent wrote it from the same source, that re-creates the correlated check
by the back door.

2.5  THE BLACKLIST

lad-coder, or whoever designs the tests, may name other blocks that must NOT run concurrently
with a given test.

*** GUARDRAIL: A BLACKLIST MAY ONLY EVER ADD EXCLUSIONS, NEVER REMOVE THEM. *** An agent must
not be able to declare itself compatible with something the reference graph says it conflicts
with. Computed disjointness (D9) is the FLOOR; the blacklist sits on top for what the graph
cannot see.

FAILURE MODE TO WATCH: defensive over-blacklisting. If agents exclude everything whenever a
test looks flaky, concurrency collapses toward serial and nobody notices, because it still
WORKS. A recorded reason per entry makes that visible.

2.6  DESIGN-FOR-TESTABILITY — a future skill

Some designs are UNOBSERVABLE. A condition true for one scan is roughly ten times below the
sampling floor; a same-scan coincidence is unobservable at any rate (§12). The copy layer can
latch and scan-stamp — but ONLY IF DECLARED IN THE MAP BEFORE THE DOWNLOAD that generates it,
and that declaration is frozen for the wave set.

So a block whose only evidence of correct behaviour is a one-scan pulse may be untestable in
that wave, and the runner will correctly REFUSE the vector rather than return a meaningless
green.

*** THE CONTRACT THIS SECTION IMPLIES IS NOW DRAFTED — `docs/notes/test-environment-contract.md`
(phase 5.1, 2026-08-13). *** This section says a design can be unobservable and that the runner
refuses; it does not say what an author must therefore SUPPLY. That document does: the vector
format, `Basis` citing clause AND assertion, the observability declaration, the settling
declaration, start-bool binding, the blacklist, and how to read a result — each marked with
whether it is MECHANICALLY CHECKABLE and by what.

  *** TWO THINGS IT ADDS THAT THIS SECTION DOES NOT HAVE, BOTH FROM MEASUREMENT: ***
    - *** A COMPLETION FLAG IS NOT A SETTLING SIGNAL. *** Phase 2's defective build raised `Done`
      at 10 and then ramped to 15, so a faster-than-floor poll reads mid-ramp and returns a
      CONFIDENTLY WRONG VERDICT rather than an error — the worst outcome available, and the one
      the observability floor otherwise conceals. Vectors must declare when a value has SETTLED,
      and a settling condition that merely re-cites the done-flag is refused.
    - *** A SCAN COUNT IS MEANINGLESS WITHOUT THE COMPRESSION FACTOR IT WAS STATED AT. *** Under
      X-D a 20-scan window at `comp = 1` is a 2-scan window at `comp = 10` — crossing the floor
      with nobody editing the vector. The declaration carries its `comp` and the floor is
      re-checked at the one actually used.

  *** AND IT RAISES ONE QUESTION FOR THE OWNER THAT THIS SECTION LEAVES ANSWERED BOTH WAYS: MAY AN
  AUTHOR CHANGE A BLOCK'S INTERFACE PURELY TO MAKE IT TESTABLE? *** §2.6 offers no route from
  "unobservable" back to "testable"; the obvious one — expose the evidence as a block output —
  collides with D13 and §2.1, which put instrumentation in the COPY LAYER and say `lad-coder`
  never writes observability code. That is the central question of a document called
  design-for-testability, and the design currently answers it both ways.

*** THE SECOND UNTESTABLE SHAPE, FROM D37: A BLOCK WITH NO DISCOVERABLE START CONDITION. ***
D37's start bool binds to a command signal the block ALREADY has, found via
`converter candidate-scan --direction command` — never to a test-only input, because an input
added for the harness is scaffolding inside the block under test and DB-5 forbids exactly that
(what ships would no longer be what was tested). A purely reactive block needs no start gate
and is held inert by its inputs alone, which is fine. What is NOT fine is a block that is
neither: it has sequencing to trigger, but nothing external triggers it. *** THAT IS A
REPORTABLE FINDING ABOUT THE BLOCK, not a harness gap to be worked around by adding an input
to it *** — and it is the design-for-testability lesson most likely to recur, because nothing
in ordinary authoring pushes back on it.

    THE THIRD, FROM DB-12: TIMER PRESETS AS LITERALS. A block whose dwell is a literal cannot
    be time-compressed, so any test longer than the wave budget is unrunnable against it. Check
    C-122 (dwell-timer PT-home) first — the house style may already require the preset to live
    in a DB member, in which case conforming blocks are compressible for free.

*** THIS BELONGS IN A NEW SKILL *** for lad-coder or the test designer, carrying the test-
environment contract: the vector format and its `Basis` requirement (now citing clause AND
assertion, §7), the observability declaration, the start-bool binding and what to do when no
start condition exists, timer presets as data, the blacklist mechanism and its reason field,
how to read results including the co-running log, and the constraint set in §2.2. Premature to write until the environment
exists — named now so the environment is built with a teachable contract rather than one
reverse-engineered later.

3. DECISIONS
--------------------------------------------------------------------------------

D1.  (Superseded by D9; retained for numbering continuity.)
D2.  The register map is authored PC-SIDE and is authoritative. The PLC works off it.
D3.  Identity comes from the PLC. Program-published, with the weakening recorded.
D4.  A test vector may PARAMETRISE a PLC-side model rather than drive raw values.
D5.  Tests are returned to a known INERT state between them, and the reset is VERIFIED.
D6.  The block author does NOT author its own test vectors.
D7.  (Superseded by D15.)
D8.  Agents speak TAG NAMES and never see a register number.
D9.  Independent means NON-OVERLAPPING REACHABLE STATE — the transitive closure through each
     block's call tree, COMPUTED from the reference graph, not declared.
D10. Isolation is structural: PER-SLOT INSTANCE DBs — *** ONE PER TEST TENSOR, NOT ONE PER
     VECTOR. Corrected 2026-08-12. *** This read "per-test instance DBs", which was taken to
     mean per VECTOR and is wrong: a slot's vectors run SEQUENTIALLY through the same block
     with a verified inert phase between them (D26a), and results are collected per index, so
     nothing needs preserving from one vector to the next. One iDB per slot is sufficient.
     The isolation that matters is BETWEEN SLOTS, which is what this decision was always for.
D11. Execution is CONCURRENT. The enable bitmask survives as a DIAGNOSTIC (bisect, reproduce
     in isolation), not as the execution model.
     *** CLARIFIED IN DRAFT 04 — "CONCURRENT" MEANS WITHIN A TENSOR, AND ONLY THERE. *** As
     written it reads as "all tests in a wave run at once", which is not the design. Tensors
     are SEQUENTIAL, separated by a verified inert reset; the tests inside one are concurrent.
     D26 is the authoritative statement of the structure and this line is subordinate to it.
D12. Models MUST support time compression; vectors declare the factor they need.
     *** BOUNDED, NOT FREE — AMENDED 2026-08-12 BY AUDIT (§16.4, X-D). *** A vector may DECLARE
     a factor but may not have it: compression shortens the REAL-TIME separation of the events
     being observed, so past a point it pushes the assertion below §12's sampling floor and
     every check reports green having sampled nothing. The admissible factor is computed from
     the observability of the assertions in that vector, and an over-declared factor is
     REFUSED. Latching raises the ceiling; sampling does not.
D13. Instrumentation is a property of the COPY LAYER, not of the blocks under test.
D14. Post-download verification is a PROGRAM-VERSION CONSTANT read over Modbus, not an
     upload (§9).
D15. The map is FROZEN for a wave set; changes land only at a download boundary.
D16. Shared UDTs are FROZEN for a wave set; a revision lands only at a boundary and
     invalidates every result for every DB built on it.
D17. Stop-class refusals are TWO-STAGE — static ones in preflight, baseline-relative ones at
     admission (R3).
D18. The harness DISCONNECTS across a download. Reconnect plus version check is the NORMAL
     path, not error handling (§10).
D19. TIME COMPRESSION is the throughput lever, not download batching (§8).

--- the loop and queue structure (D20-D25) ---

D20. *** LOOP 1 BRACKETS THE TEST LOOP BETWEEN TWO REVIEW PASSES, and ends with a final test
     cycle if the second review changed anything *** (§1.1).
D21. *** RESULTS CARRY A CO-RUNNING LOG *** — a slice of the wave timeline, so interference
     the graph could not predict is diagnosable (§2.4).
D22. *** A BLACKLIST MAY ONLY ADD EXCLUSIONS, NEVER REMOVE THEM *** (§2.5).
D23. *** CHANGES ARE ROUTED INTO TWO QUEUES: RUN-class flows through wave boundaries;
     STOP-class ACCUMULATES IN A DEFERRED QUEUE *** (§1.4).
D24. *** THE DEFERRED QUEUE DRAINS WHEN NO TEST CAN MAKE PROGRESS. *** Chosen over "all
     queued tests complete" because the deferred queue holds other dependencies too, so in
     practice the two conditions converge.
D25. *** ANY DOWNLOAD THAT REQUIRES TESTING TO STOP MUST BE A FULL DOWNLOAD, NEVER A
     DIFFERENTIAL ONE. *** If the disruption is being paid for, it buys a known state rather
     than an unknown mixture. SEE R8 — THIS ENTAILS SOMETHING THAT MUST NOT BE MISSED.

--- the wave structure, and what follows from it (D26-D31) ---

D26. *** A WAVE IS A SEQUENCE OF TENSORS; A TENSOR IS A BATCH OF TESTS THAT RUN IN PARALLEL. ***
     *** TERMINOLOGY CORRECTED 2026-08-12 BY THE OWNER — THE WORD "TENSOR" WAS BEING USED FOR
     THE WRONG OBJECT, AND THE CORRECT NAMING IS D26a BELOW. *** Everything D26 says about
     SEQUENCE and PARALLELISM is right; what it calls a tensor is the WIRE SLICE, and the
     submitted unit is something else. Read D26a first — it is authoritative on the shape.

D26a. *** THE WAVE MODEL, IN THE OWNER'S TERMS AND THEY ARE THE CORRECT ONES. ***

       A SLOT supplies       testTensor_N = { a, b, c, ... }   ONE methodology, several
                                                                value-sets. Vectors within it
                                                                differ ONLY in VALUES.
       The wire carries      modbusTensor(i) = testTensor_0[i] ++ testTensor_1[i] ++ ...
                                                                the i-th vector of EVERY slot,
                                                                concatenated. i is the WAVE
                                                                INDEX.
       The wave runs         i = 0, 1, 2, ... with a verified inert phase between each.

     *** SO WHAT RUNS IN PARALLEL IS ONE INDEX ACROSS ALL SLOTS; WHAT RUNS IN SEQUENCE IS THE
     INDEX. *** The unit a slot submits is a COLUMN (one methodology over many values); the
     unit the wire applies is a ROW across all columns.

     THREE RULES FALL OUT, AND THEY ARE WHY THE MAP CAN BE FROZEN AT ALL (D15):
       1. *** "SAME METHODOLOGY" MEANS SAME REGISTER LAYOUT AND SAME OBSERVABILITY
          DECLARATION — VALUES ONLY. *** This is the load-bearing half of the rule. A slot's
          register layout is therefore CONSTANT across every i, so the map is derived once per
          wave set and each index only rewrites values into a fixed shape.
       2. *** TENSOR LENGTHS MAY DIFFER, AND A SLOT WITH NO VECTOR AT INDEX i IS NULL — AND
          NULL MEANS INERT. *** No new encoding: the slot's START BOOL IS SIMPLY NOT RAISED at
          that index, so D33's inert holds (resets asserted, dynamics untriggered) and the
          values are don't-care. The wave runs to MAX tensor length; short slots go quiet.
       3. *** A SLOT EXITS WHEN ITS OWN TENSOR IS DONE, NOT WHEN THE WAVE IS. *** Therefore
          *** FEEDBACK LATENCY IS BOUNDED BY A SLOT'S OWN TENSOR LENGTH, NOT THE WAVE'S. *** A
          3-vector slot has its results after index 2 even if the wave runs to index 6, so
          results are DISTRIBUTED PER SLOT ON COMPLETION and never batched to wave end.

     WHAT THIS CORRECTS ELSEWHERE, all of it recorded rather than silently patched:
       - DB-13 does NOT determine wave length. Wave length is MAX TENSOR LENGTH. What the
         conflict graph decides is WHICH SLOTS MAY SHARE A WAVE SET (see DB-13).
       - O14's framing was wrong: conflict density cannot lengthen a wave, it forces slots
         into SEPARATE wave sets. It costs WAVES PER PROJECT, not seconds per wave.
       - §8's "5 tensors" figure is right; its DERIVATION was not. The count is max tensor
         length (5), not a colouring of 30 tests 6 wide. Same number, wrong reason — and the
         wrong reason gives wrong answers as soon as tensor lengths differ, which rule 2
         above says they will.

D26b. *** A SLOT IS PER (AGENT, METHODOLOGY) — AN AGENT MAY HOLD SEVERAL. *** Decided
     2026-08-12 to remove a serialisation the one-tensor-per-AGENT rule would have imposed:
     an agent needing to test three behaviours would have needed three wave sets, run
     serially, because a second methodology breaks the stable-layout property of rule 1.

     Untying the slot from the agent removes that. Three methodologies against one block DO
     conflict — same reachable state — but given each slot its OWN instance DB (D10) and its
     OWN model instance (D28), they become independent INSTANCES of the same block type, and
     independent instances are conflict-free by the same D9 argument that lets two agents
     share a wave.

         shared by the agent : FB + UDT                    2 objects
         per slot            : iDB + model + model-iDB     3 objects
         an agent with K slots                             2 + 3K   (K=1 -> 5, K=3 -> 11)

     *** THE TRADE IS OBJECTS FOR WALL-CLOCK, AND OBJECTS ARE THE CHEAP SIDE *** — three wave
     sets cost three downloads and three full wave durations; three slots cost six extra
     objects ONCE, because they persist across waves.

     *** THE CONDITION, AND IT IS COMPUTABLE, NOT DECLARED: K SLOTS ARE PERMITTED ONLY IF THE
     BLOCK CAN BE INSTANTIATED K TIMES WITHOUT SHARED MUTABLE STATE. *** An FB with an
     instance DB, or a stateless FC — fine. A block writing to a shared global DB — NOT fine,
     the instances are not independent, and that case is correctly back to serial. It is the
     same disjointness test as D9 applied to instances of ONE block rather than to different
     blocks, and `converter cross-check`'s multi-writer facts already surface it.

         inert -> tensor[0] -> inert -> tensor[1] -> inert -> tensor[2] -> ...

     Tensors are SEQUENTIAL and separated by a verified inert reset (D5). The tests WITHIN one
     tensor are CONCURRENT (D11, as clarified). Therefore:

         wave = download boundary
              + SUM over tensors ( inert reset + MAX test duration in that tensor )

     *** WAVE DURATION IS SET BY TENSOR COUNT, NOT BY TEST COUNT, AND A TENSOR COSTS ITS
     LONGEST MEMBER, NOT THE SUM OF ITS MEMBERS. ***

     Recorded this explicitly because it was got wrong in both directions before it was got
     right, and the error was worth an order of magnitude (§8). Neither wrong reading was
     obviously wrong from D11's wording, which is the actual defect being repaired here.

D27. *** TENSOR PACKING IS A GRAPH COLOURING OVER THE CONFLICT GRAPH. *** Pack the submitted
     tests into the FEWEST tensors such that no two tests in a tensor conflict. Nodes are
     tests, edges are conflicts, colours are tensors (DB-13). Greedy colouring is sufficient —
     this does not need to be optimal and the graph is small.

D28. *** MODELS ARE INSTANCED PER TEST, NOT SHARED — this EXTENDS D10 from instance DBs to the
     models. *** The reason is D27 and it is the sharpest consequence in this draft: a model
     shared by every test of one piece of equipment places a conflict edge between EVERY PAIR
     of those tests, the graph goes complete, the colouring degenerates to one test per tensor,
     and the wave collapses to the serial case. *** THE MODEL, NOT THE INSTANCE DB, IS WHERE
     THE SHARING ACTUALLY BITES — instancing only the iDBs does not buy the packing. ***

D29. *** TENSOR WIDTH IS BOUNDED ABOVE BY CONFLICT-FREEDOM AND CAPPED BY POLL BANDWIDTH. ***
     Widening a tensor cuts the tensor count and so the wave — but every test in a tensor must
     be observed within the SAME poll cycle, so it is TENSOR WIDTH, not total test count, that
     the K x RTT arithmetic constrains (O11 and modbus-tcp-client-spec.md — NOT §12, corrected
     2026-08-12: §12 is the observability floor and contains no batching arithmetic at all).
     The two constraints bound one design
     variable from opposite sides and must be solved together.

     *** RE-DERIVED 2026-08-13 (§12a derivation 2) — THE DECISION STANDS AND ITS ARITHMETIC WAS
     ALREADY THE RIGHT SHAPE; WHAT CHANGES IS WHAT "WIDTH" MEANS AND WHAT THE CAP IS A FUNCTION
     OF. *** §12 asked whether this clause inverts, because it appeared to price registers. It
     does not: `K x RTT` counts ROUND TRIPS, and X-A already makes a slot cost exactly one FC03,
     so the expression was correct before the measurement and is correct after it. Three
     corrections, none of them a reversal:

       1. *** "WIDTH" MEANS SLOTS, NEVER REGISTERS. *** Marginal cost per register is ~0.040 ms
          on writes and no trend on reads [M at 123 registers, 2026-08-13 — the earlier
          `[I]` extrapolation from a 1..16 sweep is retired and it HELD], so a full-width slot
          costs ~4.9 ms more than a one-register slot: *** ~6% OF A ROUND TRIP, AGAINST 100% FOR
          A SECOND ONE. *** `K` is the slot count and slot width `W` enters only as `ceil(W/123)`,
          which is 1 for every legal slot. *** NARROWING A SLOT BUYS ABOUT 0.04 ms PER REGISTER
          AND COSTS A WHOLE ROUND TRIP IF IT FORCES ONE. *** Size a slot to what it needs.
       2. *** THE CAP IS NOT A CONSTANT — IT IS `floor(S_min x scan / RTT_p99)`, *** where
          `S_min` is the shortest declared SAMPLED observation window in the wave set. Worked
          values in §12a. It is keyed on the p99, never the median — and on the p99 measured AT
          FULL WIDTH (201 ms), not the one derived from the narrow sweep (173 ms), which cost the
          cap ~14% at `S >= 50` when it was corrected on 2026-08-13.
       3. *** WHEN EVERY OBSERVATION IN THE WAVE SET IS LATCHED, THIS CAP DOES NOT BIND AT
          ALL *** — a latch holds until test start, so there is no window to fit a poll into.
          The tension this clause describes then simply does not arise, and the binding
          constraint moves to work memory (§16.13) or the mirror (X-A).

     4. *** AND THE CAP GAINED A MULTIPLIER — F-1, ADOPTED 2026-08-13. *** X-A's rule is now "a
        read never SPLITS a slot" (it was "never straddles two"), so ONE FC03 read may cover
        `R = floor(125 / W)` WHOLE slots and the cap becomes
        *** `K_max = R x floor(S_min x scan / RTT_p99)` ***. This clause's tension — conflict
        freedom pushing tensors wider, poll bandwidth pushing them narrower — is therefore
        *** SUBSTANTIALLY RELIEVED, BY A FACTOR THE MAP DESIGNER CONTROLS: *** at a 20-register
        slot the poll side admits six times what it did. And it puts a NEW cost on padding, since
        padding reduces `R` — so "size a slot to what it needs" is now an economic rule and not
        merely a tidy one.

D30. *** THE FEEDBACK-LATENCY LEVER IS INFORMATION DENSITY PER WAVE, NOT WAVE DURATION. ***
     Under D26 a wave is order-of-a-minute, so duration is not what damages IR development —
     ITERATION COUNT is. Three guessing rounds at a minute each still cost three rounds of an
     agent editing correct code. This is why DB-8 is the first of the new blocks to build and
     DB-10/DB-11 are the last.

D31. *** SUBMISSION IS ATOMIC AND PRECEDES PACKING (DB-9). *** Two independent load-bearing
     reasons: observability declarations must be complete BEFORE the download that generates
     the copy layer (D15 + §2.6 — NOT D13, corrected 2026-08-12: D13 says where instrumentation
     LIVES, not when it must be DECLARED), AND the packer needs the whole submission set to colour the
     graph well — trickled submissions yield a worse colouring, hence more tensors, hence a
     longer wave for the same tests.

--- fault handling, inert, and coverage (D32-D37) ---

D32. *** EVERY UNHANDLED CONFIGURATION ABORTS THE DOWNLOAD, AND WE ABORT IT — NOT TIA
     (O9 RULED). *** The escalation ladder, in order:

       1. ABORT FROM THE DELEGATE (a throw). Ours, so it is distinguishable from one TIA
          caused — the same separation as FailedToApply versus RefusedByPolicy.
       2. LOG: the configuration, every selection it offered, and that we refused it.
       3. *** PAUSE TESTING. *** Not optional even though an abort means the program was not
          changed: an aborted download leaves a state Siemens does not document (G4), so
          resumption goes through the version register (§9) first, never on assumption.
       4. ATTRIBUTE — ask DB-1 which submitted change entails the configuration raised.
       5. IF ATTRIBUTABLE: *** EXCISE THAT IR BLOCK FROM THE WAVE SET, ROUTE IT TO THE
          DEFERRED QUEUE (D23), AND RE-DOWNLOAD WITHOUT IT. *** An ordinary boundary; no
          disruption is spent.
       6. IF NOT ATTRIBUTABLE: a disruptive FULL download (D25, never a differential) —
          *** BUT ONLY FOR CLASS A BELOW. For classes B and C step 6 is futile and step 7
          is immediate. ***
       7. TERMINAL: *** TOTAL TEST ABORT — NOT JUST THE WAVE — AND WAIT FOR A HUMAN. ***

     *** CAVEAT 1 — ATTRIBUTION IS STRUCTURALLY IMPOSSIBLE FOR SOME CONFIGURATIONS, AND THAT
     IS NOT A LOCATOR BUG. *** `DataBlockReinitialization` and `StopModules` ARE attributable:
     DB-1's change classes already map onto them. `UserManagementDownload` and
     `OverwriteSystemData` are PROJECT-LEVEL — no block entails them, so there is nothing to
     excise and step 6 is the only rung that exists. THE LOG MUST DISTINGUISH "no block is
     responsible" FROM "the locator failed to find one": they take the same branch but call
     for opposite fixes, and a log that conflates them will send a fix wave after a locator
     that was working correctly.

     *** CAVEAT 2 — THE LADDER HAS NO TERMINAL RUNG AND CAN LOOP; RULED 2026-08-12. *** If the
     step-6 disruptive download ALSO raises an unhandled configuration, step 1 fires again
     against an unchanged situation and the ladder restarts. Unattended that is an abort loop
     that consumes the night. *** RULED: THAT IS A TOTAL TEST ABORT — the whole test session,
     not merely the wave — AND IT WAITS FOR HUMAN INTERVENTION. *** Recorded as its own
     outcome class, because it is the case that generates a fix wave and the one thing in this
     ladder a person must see. NEVER RETRY A DISRUPTIVE DOWNLOAD THAT ABORTED ON A
     CONFIGURATION.

     *** CAVEAT 3 — AND IT DECIDES WHETHER STEP 6 IS PROGRESS OR A WASTED BOUNDARY. *** "If we
     cannot attribute it we have no choice but a full download" is right for ONE class of
     configuration and FUTILE for two others, because a full download has a LARGER delta than
     a differential and therefore raises MORE configurations, never fewer. It cannot make an
     unwanted configuration go away. What it can do is let us ANSWER one we were only refusing
     because we were in non-disruptive mode. So the class decides the rung:

       *** 🔴 A DEFECT IN THIS LADDER, FOUND 2026-08-12 WHILE BUILDING THE CLASSIFIER —
       `StartModules` IS CLASS A BUT ITS RUNG IS WRONG. *** O3's nuance is that `StartModules` is
       raised in the **POST** delegate, i.e. AFTER the download has already stopped the modules.
       So refusing it does NOT call for a *new* disruptive download — one has just happened. It
       calls for answering it *** WITHIN THE CURRENT ONE, OR THE CPU IS LEFT STOPPED. *** The
       CLASS is right ("a consequence the option already entails"); *** "GO TO STEP 6" IS
       CIRCULAR FOR THIS ENTRY ALONE *** and would send us to fetch a disruptive download we are
       already inside. Implemented as written and flagged rather than silently deviated from;
       the ladder needs a per-entry rung, not one rung per class.

       CLASS A — REFUSED ONLY BECAUSE THE MODE IS NON-DISRUPTIVE.
                 `StopModules`, `DataBlockReinitialization`, `StartModules` — the
                 --disruptive allowance list. Each is a consequence the chosen download option
                 ALREADY entails. *** STEP 6 GENUINELY RESOLVES THESE: the disruptive download
                 ANSWERS them rather than hoping they do not appear. This is the only class
                 for which spending a disruptive boundary buys anything. ***
       CLASS B — NEVER PERMITTED IN ANY MODE.
                 `ResetModule -> DeleteAll`, `InitializeMemory -> AcceptAll` — the deny list.
                 These destroy BEYOND what the option entails, so a disruptive download refuses
                 them exactly as a normal one does and aborts identically. *** GO STRAIGHT TO
                 STEP 7. Spending a full download here buys nothing and costs a stop. ***
       CLASS C — UNKNOWN, OR NO `NoAction` AND NOT ON EITHER LIST.
                 The `SelectiveDeleteDownload` shape (`AcceptAll | DeleteSelected`), and every
                 configuration nobody has seen yet — which, given that each of the last three
                 runs produced one, is the case that matters. We cannot know what it entails,
                 and guessing is the thing this whole policy exists to forbid.
                 *** GO STRAIGHT TO STEP 7. ***

     SO THE HONEST SHAPE OF THE LADDER: excise-and-continue is the only rung that makes
     progress cheaply, the disruptive download is a narrow second rung serving Class A alone,
     and everything else is a human. THE CLASSIFICATION MUST BE EXPLICIT IN THE LOG — "went
     to step 7 without attempting a download, because Class B" is a materially different
     record from "attempted the full download and it aborted too".

D33. *** INERT IS THE START STATE OF THE NEXT TEST, WITH DYNAMICS NOT TRIGGERED AND RESETS
     HELD (O12 RULED). *** Not "everything idle". Precisely:

       - the NEXT test's START CONDITIONS are established;
       - NO DYNAMICS ARE TRIGGERED — models sit AT the start condition, not running toward it;
       - *** RESETS ARE HELD ASSERTED for the whole inert period — a LEVEL, not an edge or a
         pulse *** — and released at test start;
       - LATCHES ARE RELEASED, and the release must COMPLETE before the first scan of the test;
       - *** OUTPUTS ARE NOT RECORDED DURING INERT. *** Establishing a start state moves
         outputs; recording that would put spurious activity in front of every single test.

     CONSEQUENCE 1: *** INERT IS PARAMETRISED BY WHAT COMES NEXT *** — it is not a canned
     routine but is computed per boundary from tensor[k+1]'s vectors.

     CONSEQUENCE 2, AND IT STRENGTHENS D27: one inert phase must establish the start state for
     EVERY test in the next tensor at once, and that is only WELL-DEFINED because the tests in
     a tensor are conflict-free — non-overlapping reachable state (D9) means their start
     conditions CANNOT CONTRADICT. *** So conflict-freedom is not only about interference
     during a test; it is what makes a shared inert phase constructible at all. *** Two tests
     needing contradictory start states are, by that fact alone, in different tensors.

     CONSEQUENCE 3: D5's "the reset is VERIFIED" now has TWO distinct checks — start
     conditions established, AND dynamics quiescent. A model sitting at the right value while
     still integrating toward another is not inert, and only the second check catches it.

D34. *** THE WAVE ALTERNATES INERT / TEST UNCONDITIONALLY, PASS OR FAIL (O6 RULED). *** A
     failing test does not abort the wave and does not change what follows it. This RESOLVES
     O6 by REMOVING THE NEED FOR A FAILURE POLICY rather than by choosing one: the inert phase
     (D33) is what contains a bad state, so the wave never has to reason about whether the
     previous test left one. Abort-loses-information and complete-risks-cascading were the two
     horns; establishing the next start state unconditionally takes neither.

     WHAT IS STILL OWED, AND IT IS SMALL: the case where *** INERT ITSELF CANNOT BE
     ESTABLISHED *** — a block latched in a fault that will not reset. That is NOT a test
     failure, it is a WAVE-BLOCKING condition, and the natural treatment is D32's: excise the
     offending block to the deferred queue and continue the wave without it. Recorded as O6's
     residual rather than quietly assumed.

D35. *** COVERAGE IS COUNTED PER ASSERTION, NOT PER CLAUSE, AND EVERY VECTOR DECLARES THE
     ASSERTION IT TARGETS (O13 RULED). *** Many vectors per clause is the expected shape and
     is entirely fine — *** but only if the denominator is assertions. *** Against §7's
     `clause x instance` denominator, five vectors on a two-assertion clause all tick the same
     box, and the second assertion reads as covered while nothing ever tested it. That is this
     project's own correlated-check failure wearing coverage clothing.

     *** THE ASSERTION SET IS ENUMERATED FROM THE SPECIFICATION, NEVER FROM THE TEST SUITE. ***
     Decomposing a clause into its atomic assertions is a SPEC-SIDE operation, complete before
     any vector exists; a vector CITES into that enumeration and cannot extend it. This
     qualifier is load-bearing, not decoration — a denominator defined by what somebody wrote a
     vector for is always 100%, and §7 rejects it by name.
     [CORRECTED 2026-08-12 BY AUDIT. This paragraph previously said that where clauses are NOT
     atomic "the declaration is exactly what makes the gap visible", which describes discovery
     AT THE VECTOR — the very mechanism §7 forbids. The headline stands; the justification was
     describing the rejected alternative.]

     WHY THIS FORM RATHER THAN "MAKE CLAUSES ATOMIC": it is correct WHETHER OR NOT clauses turn
     out to be atomic. If rung B/C already emits atomic clauses the citation is trivially the
     clause itself and costs nothing; if it does not, the spec-side decomposition is where the
     extra assertions appear. *** So the original O13 question — are clauses already atomic? —
     stops being load-bearing, which is why it can be closed without answering it. ***

D36. *** THE POLL-WIDTH CAP (O11) AND CONFLICT DENSITY (O14) ARE PARAMETERS TO BE MEASURED
     ONCE THE DESIGN BLOCKS EXIST — NEVER CONSTANTS ASSUMED NOW. *** Both deferred
     deliberately, so that the design blocks can be adapted to what is measured rather than
     the measurement being predicted. THE OBLIGATION THE DEFERRAL CARRIES: DB-13's colouring
     takes MAX TENSOR WIDTH as an explicit input with no default that could be mistaken for a
     measurement, and nothing anywhere assumes unlimited width or a particular packing.

     *** THE DEFERRAL STANDS, AND ITS SUBJECT NARROWED 2026-08-13. *** O11's ARITHMETIC no
     longer needs measuring — it is `floor(S_min x scan / RTT_p99)` and both constants are now
     measured (§12a derivation 2). What still needs the rig is `S_min`: whether real submission
     sets declare SAMPLED observation windows at all, and how short. *** DO NOT READ THE FORMULA
     AS CLOSING D36 — a formula whose free variable has never been observed is still a
     prediction, which is the exact thing this deferral exists to prevent. *** The obligation
     above also acquires a shape question, flagged for the owner as §12a F-2: an explicit SCALAR
     max-width input must be the worst case over every wave set, and the cap is per-set.

     *** ONE THING MUST NOT BE DEFERRED ALONGSIDE THEM: AUTHOR MODELS INSTANCED PER TEST FROM
     THE START (D28). *** Deferring the MEASUREMENT is right; defaulting to SHARED models
     while it is deferred is not. Instancing is nearly free while the models are being
     written and is a rewrite of every model afterwards — and if O14 comes back "packs 1-2
     wide", shared models are precisely the cause it will name. BE WRONG IN THE CHEAP
     DIRECTION.

D37. *** EACH VECTOR CARRIES A START BOOL, AND IT GATES THE BLOCK'S START CONDITION — NOT THE
     BLOCK'S EXECUTION. *** This is the MECHANISM for D33's "dynamics not triggered", which
     until now described a state with no stated means of reaching it.

     *** THE BLOCK IS CALLED EVERY SCAN, INCLUDING THROUGHOUT INERT. *** The tempting reading —
     gate the CALL, so the block does not run during inert — is WRONG, and D33 is what rules it
     out: resets are HELD ASSERTED during inert, and a reset is processed BY THE BLOCK. A block
     that is not called never processes its reset, so gating the call produces a block that is
     neither running nor reset, holding whatever its statics happened to contain. That is the
     opposite of inert.

     WHAT THE BOOL BINDS TO — AND THE CONSTRAINT THAT MATTERS:

       *** IT BINDS TO THE BLOCK'S EXISTING START CONDITION, DISCOVERED, NEVER TO A TEST-ONLY
       INPUT ADDED FOR THE PURPOSE. *** A test-only input is scaffolding inside the block under
       test, which is exactly what DB-5 forbids: what ships would then not be what was tested.
       The discovery tool already exists — `converter candidate-scan --direction command`
       computes command-versus-status FROM THE USAGE GRAPH rather than from the interface
       section, which is the right question here.

       *** NOT EVERY BLOCK HAS ONE, AND THE ABSENCE IS MEANINGFUL RATHER THAN A DEFAULT. *** A
       purely reactive block — a comparator, a level alarm, anything that is always processing —
       has no start gate, and for those inert is established BY THE INPUT VALUES ALONE (put the
       level below the threshold). So the field is OPTIONAL PER VECTOR, and a vector that omits
       it is asserting "this block has no start gate", which is a claim the harness can check
       rather than a blank it fills in.

     ORDERING, AND IT IS A RACE IF LEFT UNSTATED: release the latches, VERIFY quiescent (D33's
     second check), and only THEN raise the start bool — ON A LATER SCAN, never the same one.
     Releasing a reset and starting in one scan makes the outcome depend on rung order inside
     the block, which is not something a test should be sensitive to.

     PER TEST, NOT GLOBAL. Tests in a tensor hold independent start bools. Simultaneous start
     is the normal case; independence is what permits a staggered one without redesign.

     *** AND IT SUPPLIES SOMETHING THE DESIGN WAS MISSING: A DEFINED T=0. *** The rising edge
     of the start bool IS the test's time origin. §12 offers EVENT SCAN-STAMPS to answer "when,
     relative to what" — and until now there was no stated "what". Stamps become differences
     from the start edge, in scans, which is exactly the unit the observability floor argues in.

     DESIGN-FOR-TESTABILITY CONSEQUENCE, for the skill the owner has flagged as needed: a block
     with NO discoverable start condition and no way to be held inert by its inputs is HARD TO
     TEST — and that is a finding ABOUT THE BLOCK, reportable as such, not a gap in the harness
     to be worked around by adding a test input to it.

--------------------------------------------------------------------------------
4. THE DESIGN BLOCKS
--------------------------------------------------------------------------------

Six were proposed; they collapse into about four components. DB-1 and DB-2 are one graph
problem, DB-3 and DB-4 are one scheduler, DB-5 is structural, DB-6 is a client invariant.

DB-1 — CHANGE TRACKER *** AND ROUTER ***
  Three outputs: WHICH objects changed (for the <=20 budget), WHAT CLASS each change is
  (for routing per D23 and for STOP / RUN (Init) prediction), and BLAST RADIUS (a UDT change
  is one object plus every DB built on it).

  Change classes [R, Siemens' own RUN-download table, S7-1200 V4 column]:
    FB/FC code change ............................ RUN, nothing disturbed
    New / deleted FB, FC, DB, UDT ................ RUN
    New / deleted OB, or OB property change ...... STOP
    DB interface change (no memory reserve) ...... RUN (Init) - resets, retentives included
    Modified UDT ................................. RUN (Init) on EVERY DB built on it
    Modified retentivity settings ................ STOP
    New / revised text lists ..................... STOP
    Hardware configuration ....................... STOP
    Comments, new PLC tags ....................... RUN

  Existing tooling: `converter ir-hash` (cheap has-it-changed, immune to SIDECAR/UId churn),
  `converter diff` (changed networks, rest provably identical), `converter cross-check`
  (reference graph for blast radius).

  RESOLVED GAP: a local ledger desynchronises from the device. Reconciliation via
  `openness-cli export-all` + `converter drift-check --complete` is a periodic OBLIGATION.
  *** CAVEAT [M]: export-all reads the OFFLINE PROJECT, not the controller *** — Openness has
  no upload path — so that reconciliation compares IR-on-disk to the TIA project. The VERSION
  REGISTER (§9) is the only thing that verifies the DEVICE.

DB-2 — TEST / BLOCK DEPENDENCY
  Same graph, different query. A test can be invalidated by a block it does NOT target: if B
  writes a global A reads, B's change invalidates A's PASSING RESULT though A changed nothing.
  Dependency is transitive over the reference graph.

  Results carry a VALIDITY STAMP: (program version, map version). Without it the system will
  report a green obtained BEFORE the change that invalidated it.

DB-3 — DOWNLOAD TRACKING AND DURATION
  "Affected tests" means ALL tests — Openness cannot download a selection, so every download
  is whole-software.

  SETTLING WINDOW after "finished": `RUN (<21)` integrates across several scan cycles, during
  which the program runs as a MIXTURE of old and new blocks [R]. Results from that window are
  meaningless. The version register (§9) makes the window observable rather than guessed.

  FAILURE HANDLING: an aborted download leaves the device in a state Siemens does not
  document (external gap G4). NEVER resume on the assumption it worked — read the version
  register first.

  Inert-state-before-download stands, for a stronger reason than throughput: if a DB
  reinitialises during the download, there is no state to corrupt if you went inert first.

DB-4 — THE 20-OBJECT LIMIT
  More than 20 changed objects cannot be integrated consistently in one program cycle [R].

  *** CORRECTED 2026-08-12 BY AUDIT: THE BUDGET IS BIMODAL, AND THE OLD "3 OBJECTS PER AGENT,
  SO ROUGHLY SIX AGENTS PER DOWNLOAD" WAS THE STEADY-STATE CASE PRESENTED AS THE ONLY ONE. ***
  It counted an agent's FB, UDT and iDB and forgot that D10 creates an instance DB PER TEST and
  D28 a model instance PER TEST — both of which are objects, and neither of which existed as
  decisions when that figure was written.

    INTRODUCTION WAVE — a slot appears for the first time:
        shared by the agent : FB + UDT .................  2
        per slot            : iDB + model + model-iDB ..  3
        ------------------------------------------------------
        agent with K slots ............................. 2 + 3K   (K=1 -> 5, K=3 -> 11)
                                                                  => ROUGHLY FOUR single-slot
                                                                     agents per download.

    *** THIS SUPERSEDES A FIGURE OF ">=13 OBJECTS PER AGENT, SO ONE AGENT PER DOWNLOAD" THAT
    STOOD HERE FOR ABOUT AN HOUR ON 2026-08-12. *** It came from an audit finding that was
    arithmetically correct given the premise it was handed — one instance DB and one model
    instance PER VECTOR — and that premise was a misreading of the wave model, corrected in
    D26a/D10. Vectors within a slot run sequentially through ONE instance, so the multiplier
    is the number of SLOTS, not the number of vectors. Recorded because a wrong number was
    briefly in this document with an audit's authority behind it.

    STEADY-STATE ITERATION — the agent edits its block and re-runs existing tests:
        the FB, sometimes a UDT ........................ 1-2    => the original ~6 agents per
                                                                   download HOLDS here, because
                                                                   the per-test objects already
                                                                   exist unchanged and are not
                                                                   in the delta.

  *** THE REFINEMENT THE AUDIT DID NOT MAKE, AND IT IS THE REASON D30 SURVIVES: PER-TEST
  OBJECTS ARE CREATED ONCE AND PERSIST. *** They are only in a delta on the wave that
  introduces them. So the heavy case is real but NON-RECURRING per test set, and iteration —
  which is what actually dominates a lad-coder's loop (D30) — stays cheap.

  WHAT THIS DOES CHANGE: an introduction wave carries roughly 4 download boundaries rather than
  1, so at the corrected ~20-25 s per boundary (§8) it front-loads about 80-100 s. "A wave is
  order-of-a-minute" survives, but only just, and only because the boundary cost was also
  corrected downward. Both corrections came from the same audit and they pull in opposite
  directions — do not apply one without the other.

  AND IT SHARPENS DB-7: objects accumulate at ~10 per agent per introduction, while cleanup
  fires only at a drain boundary (D24). The budget is consumed by ACCUMULATION, not by change.

  Batches must be DEPENDENCY-CLOSED, not arbitrary slices — an FB, its instance DB and its
  UDT must land together or the program is inconsistent between downloads.

  The whole project must compile before ANY download, so admission control (§1.2) is the fix
  for one broken block blocking everyone.

DB-5 — TWO PROJECTS: IR DEV, AND TEST ENVIRONMENT
  The coordinator OWNS the test project, so `SoftwareOnlyChanges` — "the objects that differ
  online and offline", decided by TIA, not your edit list [M] — can only carry what the
  coordinator put there. The folder-download-deletes-online-only-blocks footgun [R] is
  contained for the same reason. Concurrent Openness sessions on DIFFERENT projects are
  supported and verified here.

  *** Harness scaffolding never contaminates the deliverable *** — MB_SERVER, the models, the
  latches and the mirror exist only in the test project.

  NAMED COST: what is tested is then not what ships. Extra code, extra scan time, different
  timing; a timing-sensitive behaviour could pass in test and fail in the deliverable.

DB-6 — ISOLATION BY CONSTRUCTION
  The research hazards are DATA LOSS, not leakage. The one genuine LEAK is PC-side: if the
  mirror's layout changes and the PC's map does not, agent A's write lands in agent B's
  registers. The protection is client-side and can be by construction:

    1. Layout version register checked before EVERY transaction batch, not only at connect —
       a download can land mid-session.
    2. The map artifact carries a hash; the version register carries the same value. A
       mismatch refuses the whole mirror.
    3. *** The client instance holds only its own region's bounds, so a write outside it is
       UNADDRESSABLE *** — not rejected by a check that could be skipped.

DB-7 — CLEANUP  *** new 2026-08-12 ***
  NOTHING IN THE DESIGN EVER REMOVES ANYTHING, and three things accumulate: per-test instance
  DBs (D10 — one per TEST, not per agent), models, and blocks no longer under test. Left alone
  they consume scan time (M6), object count, and eventually the <=20 batching budget.

  A CLEANUP STAGE runs on a cadence expressed in test cycles or disruptive downloads. What it
  removes: instance DBs for completed tests, models no vector still references, and blocks not
  in any admitted test.

  FOUR RULES, each earned:
    - *** IT RUNS WHEN TESTS ARE DRAINED *** — the same condition as the deferred queue (D24).
      Deleting something a running test depends on is the obvious way to make this dangerous.
    - *** ELIGIBILITY IS GRAPH-PROVEN, NEVER COUNT-BASED. *** "Nothing references this" is a
      computed fact from the reference graph (`converter cross-check`), not an assumption from
      age or from a test having finished. A block can be unreferenced by vectors and still
      called by another block.
    - *** EVERY REMOVAL IS RECORDED — what, why, and on whose authority. *** Otherwise this
      becomes the "a block silently disappeared" failure, which is exactly the shape of the
      folder-download footgun (R5) that we forbade elsewhere.
    - Deletions are ordinary changes: they route through DB-1, count against the <=20 budget,
      and — usefully — deleting an FB/FC/DB/UDT is RUN-class [R], so cleanup does NOT need a
      disruptive boundary of its own.

4a. THE WAVE-STRUCTURE DESIGN BLOCKS  *** new in draft 04 ***
--------------------------------------------------------------------------------

DB-1 to DB-7 answer "what may be downloaded, and when". DB-8 to DB-13 answer a different
question that only appeared once D26 made the wave structure explicit: *** given that a wave
costs about a minute, what actually limits how fast an agent converges on correct IR? ***

BUILD ORDER, AND IT IS NOT THE NUMBERING (D30):

     FIRST      DB-13  tensor packing      — it sets wave duration, and D28 falls out of it
     FIRST      DB-8   the result package  — iterations dominate, so density is the lever
     THEN       DB-9   the submission unit — both DB-13 and D31 depend on it
     LATER      DB-12  time compression    — narrowed; long tests only
     LAST       DB-10  agent scheduling    — at a minute a wave, an agent can simply wait
     LAST       DB-11  the rig pool        — better packing buys the same thing for free

DB-13 — WAVE-SET ADMISSION  *** it does NOT set wave duration — corrected 2026-08-12 ***

  *** WHAT THIS BLOCK ACTUALLY DECIDES: WHICH SLOTS MAY SHARE A WAVE SET. *** It was written
  as "pack tests into the fewest tensors", on the understanding that tensor count set the
  wave's length. Under the corrected model (D26a) every slot runs at every index, so there is
  no packing decision inside a wave at all: *** WAVE LENGTH IS MAX TENSOR LENGTH ACROSS THE
  SLOTS, and nothing this block does can change it. ***

  The colouring survives, applied to a different thing: colour the SLOTS, and *** EACH COLOUR
  CLASS IS A WAVE SET. *** Conflicting slots cannot run concurrently, so they go into
  DIFFERENT wave sets — which costs an extra wave, not a longer one.

  So the conflict graph is now an ADMISSION mechanism, not a scheduler, and the thing it
  buys is SLOTS PER WAVE rather than seconds per wave. The edges are unchanged:

    - OVERLAPPING REACHABLE STATE (D9) — the transitive closure through each block's call
      tree, from `converter cross-check`. Already the definition of "independent".
    - SHARED MODEL INSTANCES — two tests parametrising the same model of the same equipment.
      See D28; this is the dominant source and the one that is fixable.
    - BLACKLIST ENTRIES (§2.5, D22) — the manual additions, which may only ADD edges.
    - THE POLL-BANDWIDTH CAP (D29) — not a pairwise edge but a width limit on any tensor,
      derived from K x RTT against the observation set the tensor needs.

  MECHANISM. At admission the coordinator holds every submission (DB-9), so it builds the
  graph and colours it BEFORE the download. Greedy is fine. It then reports the tensor count
  and the predicted wave duration back with the plan, so an agent can see what its submission
  cost — a submission that adds one test and one tensor is visibly more expensive than one
  that adds five tests into existing tensors.

  *** THE MEASUREMENT THAT DECIDES WHETHER ANY OF THIS WORKS: THE CONFLICT DENSITY OF A REAL
  SUBMISSION SET. *** If tests pack 6-10 wide, waves are about a minute and feedback latency
  is a non-problem. If they pack 1-2 wide because everything shares a plant model, waves are
  10x longer and instancing the models (D28) is the highest-value change available anywhere in
  this design. *** THIS IS ANSWERABLE FROM THE FIRST REAL SUBMISSION SET, BEFORE ANY OF IT IS
  BUILT *** — it needs the graph, not the rig.

DB-8 — THE RESULT PACKAGE  *** build first alongside DB-13 ***
  The latency lever (D30): make one wave worth three by removing the reasons an agent has to
  guess. What a result carries:

    - OBSERVED VERSUS EXPECTED, per assertion, not a pass/fail for the test.
    - THE BASIS CITATION — which requirement clause and which spec artifact the expectation
      came from, so a disagreement is traceable to a source rather than argued from the code.
    - THE FIDELITY DECLARATION of every model involved (M3/M4, §11). A failure against a model
      declared as approximate is a different fact from one against a model declared exact.
    - *** THE STIMULUS CHECK *** — evidence the input actually arrived and the block actually
      ran. Without it "no output" is ambiguous between "the logic is wrong" and "the test never
      started", and an agent asked to distinguish those from a bare fail will guess.
    - THE CO-RUNNING LOG SLICE (D21) — which other tests shared the tensor, so interference the
      graph did not predict is diagnosable. Under D26 this now has an exact meaning: the
      tensor, not the wave.
    - THE VALIDITY STAMP (DB-2): program version, map version.
    - MANIFEST PRESENCE (§9a): whether the object under test appears in the load manifest of
      the download that preceded the wave. Cheap, and it separates "wrong" from "never loaded".

DB-9 — THE SUBMISSION UNIT
  A test set is submitted ATOMICALLY (D31): the vectors, their observability declarations, and
  the blocks they target, as one unit that is admitted or refused whole. Observability must be
  declared before the download that generates the copy layer (D15 + §2.6; not D13 — see D31)
  — a declaration arriving
  after it cannot be honoured until the next boundary — and the packer needs the full set to
  colour well. A partial submission is a REFUSAL with reasons, never a partial admission.

DB-12 — TIME COMPRESSION  *** narrowed in draft 04, not dropped ***
  D19 called compression THE throughput lever. Under D26 that is now too strong: compression
  does nothing for wave OVERHEAD, which is tensor count and inert resets. What it still does,
  and what nothing else does, is make an individually LONG test runnable at all — a 40-hour
  dwell cannot run whatever the packing.

  *** AND THE CONSTRAINT THAT HAD NOT BEEN NAMED: YOU CANNOT COMPRESS A MODEL INDEPENDENTLY OF
  THE LOGIC IT DRIVES. *** Compressing a tank-fill model while the block's own dwell timer runs
  in real time does not accelerate the test, it DESYNCHRONISES it, and the block fails a test
  it would pass on real hardware. So compression requires TIMER PRESETS AS DATA, not literals,
  in the blocks under test — which is a design-for-testability requirement on authored IR, not
  a property of the harness.

  *** SWEPT 2026-08-12 (plan task 0.4). THE PREMISE WAS HALF RIGHT, AND THE HALF THAT FAILED IS
  THE HALF THIS SECTION WAS RELYING ON. ***

  1. *** C-122 IS NOT A GENERAL "TIMER PRESETS SHALL BE DATA" RULE AND CANNOT BE CITED AS ONE. ***
     Its subject is ONLY a step-dwell timer inside a stepper block — a timer whose `IN` is gated
     by `Step = <n>`. Debounces, settle timers, feedback timeouts, watchdogs, heartbeats, pulse
     widths and run-hour totalisers are all outside its scope, and a literal PT on any of them
     is not a violation.

  2. *** AND ITS MECHANISED FORM CANNOT SEE A LITERAL PT AT ALL. *** The PT check is guarded by
     `if (timer.Pt is Expr.TagRef ptRef)`, so a literal falls straight through with NO finding —
     the exact case compression cares about is invisible to the rule. Worse, the subject test
     requires the tag's last component to be literally `Step`, and *** THE LIVE CORPUS CONTAINS
     NO `.Step` LEAF ANYWHERE (zero hits across 105 .ir files), SO C-122 SELECTS ZERO SUBJECTS
     AND PASSES VACUOUSLY THERE. *** A green `converter review` says NOTHING about timer presets
     on that corpus. This is FI-44's "empty is not clean" in a place nobody had looked.

  3. *** CONFORMANCE IN PRACTICE IS NEVERTHELESS GOOD — BUT AS HOUSE STYLE, NOT ENFORCEMENT. ***
     Measured: 86% / 57% / 77% of timers data-driven across the three corpora, and in ALL THREE
     *** EVERY PROCESS-BEHAVIOUR TIMER TAKES ITS PRESET FROM DATA ***, with literals confined to
     a recognisable set of infrastructure boilerplate (hand-start debounce, prestart request,
     run-hour totaliser, heartbeat tick). Treat that as verified observation, never as a
     guarantee — nothing enforces it and the checker cannot.

  *** 4. THE FINDING THAT ACTUALLY REDESIGNS THIS BLOCK: THE LONGEST BEHAVIOURS ARE NOT IEC
  TIMERS AT ALL. *** On the live corpus the multi-day and multi-hour durations are SECONDS
  ACCUMULATORS — `ADD(EN := SecondTick.Q AND <running>, IN1 := <elapsed>, IN2 := 1)` compared
  against a DInt setpoint, at six sites across three FBs. A 120-hour behaviour and a 4-hour
  repeating interval both work this way. *** A COMPRESSION DESIGN BUILT SOLELY AROUND TIMER PTs
  WOULD HAVE MISSED EVERY ONE OF THEM. ***

  So there are TWO LEVERS, and the second is the better one:

    LEVER A — LOWER THE DURATION SETPOINTS. The durations are already data (per-instance
      interface members from the parameter DB), so this is a PURE DATA WRITE: no IR edit, no
      download, and each behaviour compresses independently. Sufficient on its own.

    LEVER B — *** SHORTEN THE TICK PERIOD. *** One change compresses EVERY accumulator that
      consumes that tick by one uniform factor, *** PRESERVING ALL RELATIVE RATIOS BETWEEN
      THEM ***, in one place. Cleaner than A for exactly that reason — and the tick is currently
      a LITERAL, which makes it *** THE SINGLE HIGHEST-VALUE LITERAL IN THE CORPUS TO
      PARAMETERISE. ***

    🔴 *** AND THE TRAP, WHICH IS THIS SECTION'S OWN DESYNCHRONISATION FAILURE MADE CONCRETE:
    THERE ARE AT LEAST THREE DISTINCT TICK OSCILLATORS, CONTROL-SIDE AND SIMULATION-SIDE.
    COMPRESSING THE MODEL TICK WITHOUT THE CONTROL TICK IS PRECISELY THE FAILURE THIS BLOCK
    WARNS ABOUT *** — and it now has a name and a location rather than being a caution.

  5. *** SHORT LITERALS SET A FLOOR ON THE USABLE RATIO, AND THE FAILURE MODE IS RATIO
  DISTORTION RATHER THAN LOST RESOLUTION. *** Unchanged literals do not scale with the
  compressed behaviours around them. A 500 ms feedback debounce is 0.003% of a 4-hour interval
  and 2.5% of the same interval compressed to 20 seconds — so the block can pass or fail for
  reasons of CHANGED PROPORTION rather than changed logic. *** THIS IS A SEPARATE BOUND FROM
  §16.4's observability and timer-resolution limits, and it may bind before either. ***

  WHERE THE PARAMETER MEMBER SHOULD LIVE — costed, and the answer aligns with §16.13's
  retain-only restriction:
    - into the block's own interface UDT (what C-122 asks) — restructures EVERY instance DB of
      every block on that UDT, reinitialising download class, and the retained per-instance
      state is the batch state. *** EXPENSIVE AND RISKY. ***
    - into the existing global parameter DB — one structural change, still reinitialising, and
      that DB is all-retentive with commissioning calibration in it. Cheaper, still a real loss.
    - *** INTO A NEW, PURPOSE-BUILT NON-RETENTIVE TEST DB — NO RETAINED DATA TO LOSE, SO THE
      REINIT CLASS IS HARMLESS. THE CHEAPEST SAFE ROUTE, AND IT IS ALREADY WHAT §16.13's
      "EVERY HARNESS OBJECT IS NON-RETENTIVE" RULE REQUIRES. ***

  A CONFLICT THE SWEEP RAISED THAT IS ALREADY DISSOLVED: it noted that a parameter DB read back
  over classic S7comm would need STANDARD layout, which forecloses download-without-
  reinitialisation, while Optimized is invisible on the wire — two requirements pulling opposite
  ways. *** IT DOES NOT ARISE: ALL DATA READS GO OVER MODBUS BY RULING (§16.11), AND THE COPY
  LAYER MOVES VALUES BETWEEN `%MW` AND THE DB, SO THE DB'S LAYOUT IS NEVER ON THE WIRE. ***

DB-10 — AGENT SCHEDULING  *** demoted ***
  States: WORKING / AWAITING-WAVE / BLOCKED. Agents YIELD rather than block a slot while
  waiting for a wave boundary. When a result lands, *** RESUME THE OWNING AGENT WITH ITS
  ORIGINAL CONTEXT rather than spawning a fresh one *** — the fresh agent re-derives what the
  original already knew, which is the same correlated-cost mistake as re-reading a spec to
  re-reach a conclusion already recorded.

  DEMOTED BECAUSE OF D26: at roughly a minute a wave, an agent can simply wait, and the
  machinery is not worth building until measurement says otherwise. Keep the state model
  written down for when it is.

DB-11 — THE RIG POOL  *** demoted furthest ***
  If a second rig exists, each rig gets its OWN test project — otherwise the version register
  (§9) stops identifying what is running where, which is the one thing it exists to do. Claims
  (`converter claim`) stay GLOBAL across rigs: a block number is a property of the program, not
  of the rig it happens to be loaded on.

  DEMOTED BECAUSE a second rig buys parallel waves, and better packing (DB-13) buys the same
  throughput for no hardware and no second project to keep synchronised. Revisit only once
  packing has demonstrably hit the conflict ceiling.

  INTERACTION: a deleted block frees its number, which the claims registry allocated. Releasing
  the claim must be part of the removal, or the number stays reserved forever.

5. DESIGN RULES
--------------------------------------------------------------------------------

R1. THE OB SET IS PRE-ALLOCATED AT RIG SETUP where practical. *** REVISED IN DRAFT 03: an OB
    change is no longer FORBIDDEN, it is DEFERRED *** — it is a STOP-class change and routes
    to the deferred queue (D23). New or deleted OB is `STOP` on this CPU [R], the biggest
    divergence from the S7-1500, which takes all three in RUN.

R2. SHARED UDTs FROZEN FOR A WAVE SET (D16). A revision lands only at a boundary and
    re-baselines every DB built on it.

R3. STOP-CLASS HANDLING IS TWO-STAGE (D17):
      STAGE 1, PREFLIGHT, no device, no baseline — properties of the IR alone: creates an OB,
        changes retentivity settings, adds a text list. Cheapest feedback; the agent finds out
        before anyone else is involved. *** These are now ROUTED, not refused. ***
      STAGE 2, ADMISSION, against DB-1's baseline — "modified UDT" is only a change relative
        to what is deployed, so reinit-class and object-count decisions happen when a batch is
        assembled.

R4. *** NEVER WRITE A DOWNLOAD DELEGATE THAT ACCEPTS EVERYTHING. *** A delegate written to
    say yes to everything so the download goes through is precisely how a harness wipes a rig.
    `DataBlockReinitialization = StopPlcAndReinitialize` initialises ALL data values INCLUDING
    RETAIN DATA [R].

    *** CORRECTED 2026-08-12 BY MEASUREMENT — THE MECHANISM IS NOT WHAT THIS RULE SAID. ***
    The original wording was "answer `NoAction` and let it abort". Measured: **`NoAction`
    CANNOT BE APPLIED** — `EngineeringTargetInvocationException: The configuration provided is
    invalid`, on `StopModules` and `DataBlockReinitialization` alike, through the property
    setter AND the underlying `SetAttribute`, even though `GetAttributeInfos()` reports
    `CurrentSelection : access=ReadWrite` [M].

    THE GUARD IS "REFUSE TO ANSWER AT ALL", which makes Openness abort with
    `Download configuration '<type>' was unhandled`. Still fail-closed, through a different
    door than assumed.

    Two readings remain and are NOT separable without applying a destructive selection: either
    `NoAction` is invalid FOR THAT INSTANCE because the stop or reinitialisation is genuinely
    mandatory, or the apply mechanism is broken for every value. *** OPERATIONALLY IT DOES NOT
    MATTER *** — same rule, same protection.

R4a. *** NEVER INFER SAFETY FROM THE CURRENT SELECTION. *** The zero values differ IN
    DIRECTION [M]:
        StopModulesSelections.NoAction ............................ = 0  (safe)
        DataBlockReinitializationSelections.StopPlcAndReinitialize . = 0  (DESTRUCTIVE)
    An unanswered configuration therefore reads as SAFE on one and DESTRUCTIVE on the other. A
    check written against one and reused for the other INVERTS SILENTLY.

R5. NEVER USE FOLDER-SCOPE DOWNLOADS — blocks existing only online are DELETED by them [R].

R6. ADMISSION CONTROL — a block enters the test project only after passing preflight and
    compiling clean in isolation.

R7. *** REVISED IN DRAFT 03. *** Draft 02 said "never pass `Software` (all)". That stands FOR
    WAVE-BOUNDARY DOWNLOADS, where it would reset retentive values for no reason. It is
    REVERSED for the disruptive boundary — see D25 and R8.

R8. *** THE ENTAILMENT OF D25, AND THE ONE PLACE THE GUARD IS DELIBERATELY OPENED. ***

    D25 requires a FULL download whenever testing must stop. MEASURED [M]: a full `Software`
    download raises `StopModules`, and `NoAction` cannot be applied to it — so *** A FULL
    DOWNLOAD IS IMPOSSIBLE UNLESS `StopAll` IS ANSWERED, AND `StopAll` IS FORBIDDEN BY THE
    WAVE-LOOP POLICY (D32 Class A). ***
    [CORRECTED 2026-08-12 BY AUDIT: this said "`StopAll` IS ON R4's DENY LIST". R4 contains no
    deny list — it forbids a permissive delegate and names one destructive selection. The deny
    list is enumerated in D32 Class B and has exactly two entries, `ResetModule -> DeleteAll`
    and `InitializeMemory -> AcceptAll`; `StopAll` is NOT one of them. `StopAll` is Class A —
    refused in the wave loop, ANSWERED at a disruptive boundary, which is what makes the
    exception below coherent rather than a contradiction. Three passages cited a list that was
    never in R4, and the list that does exist excludes the selection they cited it for.]

    Therefore D25 cannot be implemented without a sanctioned exception. The exception must be:
      - a SEPARATE, EXPLICITLY DECLARED DISRUPTIVE MODE — never a flag on the wave-boundary
        path, and never a fallback reached by retry;
      - permitted ONLY when the deferred queue is being drained (D24);
      - logged as a deliberate CPU stop, with what was in the queue and why;
      - and it must NOT relax the deny list for the wave loop, where stopping the CPU
        mid-testing remains forbidden.

    *** 2026-08-12 [M], AND RESTATED ACCURATELY AFTER AUDIT — READ THE QUALIFIER, IT IS NOT
    PEDANTRY. *** `StartModules` is raised in the POST delegate whenever the download stopped
    the modules; `StartModule` was ANSWERED AND ACCEPTED, and *** TIA REPORTED *** `PLC_1
    stopped.` then `PLC_1 started.`

    *** THAT IS TIA'S ACCOUNT OF WHAT IT DID — NOT A READING OF THE CPU'S OPERATING MODE. ***
    The probe's own log says so in capitals ("THAT IS A REQUEST, NOT A READING... confirm RUN
    at the device or in TIA Portal before relying on the rig"), and §16.11 proves the gap
    cannot be closed from here: `OnlineProvider` exposes NO operating mode, so *** NOTHING IN
    THIS TOOLING CAN ASK THE CONTROLLER WHETHER IT IS RUNNING. ***

    WHAT FOLLOWS, STATED HONESTLY. The earlier wording — "the disruptive boundary does NOT
    require a person, and unattended operation is not capped by this" — was drawn from this
    evidence and OVERSTATED IT. The mechanism is real and was exercised; what is missing is
    independent confirmation of the outcome. *** SO: CONFIRM RUN AT THE DEVICE ONCE, BY EYE,
    BEFORE THE FIRST UNATTENDED DISRUPTIVE BOUNDARY. *** After that single confirmation the
    withdrawal of "be at the machine" stands on a verified mechanism rather than on a
    message. This is one look at a rig, not a standing requirement for a person.

    STILL TRUE, and the reason the allowance list must include `StartModules`: if a download
    stops the CPU and `StartModule` is NOT answered, nothing else in the public API can bring
    it back. `StartModulesSelections.NoAction` is the ZERO value AND it applies cleanly — so a
    policy that merely un-denied `StopAll` without also answering `StartModules` would stop the
    rig, succeed, and leave it stopped while reporting success (R4a's hazard, exactly).

6. %MW IS STRUCTURAL, NOT PREFERENTIAL
--------------------------------------------------------------------------------

*** A SIXTH ARGUMENT, AND IT IS THE FIRST ONE MEASURED ON THE EXACT DB SHAPE THIS DESIGN NEEDS
(2026-08-12). *** A standard-access DB was round-tripped `export -> to-ir -> to-xml` and
`drift-check --complete` returned `0 drifted, 1 match`. It is equal and it is still wrong:

    original export : <MemoryLayout>Standard</MemoryLayout>
    regenerated xml : NO MemoryLayout ELEMENT AT ALL
    drift-check     : MATCH — the Normalizer ignores the attribute

So re-importing IR-derived XML states NO OPINION on layout, TIA applies the S7-1200 default
(Optimized), and `MB_HOLD_REG` then refuses the DB with `16#818C`. *** EVERY CHECK IN THE
PIPELINE STAYS GREEN THROUGHOUT: drift-check is structurally blind, import does not error,
compile does not error. *** The first symptom is a Modbus status code at runtime.

*** THEREFORE THE MIRROR IS `%MW` AND NOT A DB, FOR A REASON THAT IS NOW MEASURED RATHER THAN
ARGUED: A DB-BACKED MIRROR IS ONE RE-IMPORT AWAY FROM BEING INVISIBLE ON THE WIRE, WITH NOTHING
IN THE TOOLCHAIN ABLE TO SEE IT HAPPEN. *** A DB can still serve as a STORE (§16.4's
compression parameters, DB-12) — it simply must never be the thing Modbus reads.

Four independent arguments, each arrived at from a different direction:

  1. it cannot suffer the silent layout-revert measured on 2026-08-11 [M, three times];
  2. `MB_HOLD_REG` requires standard access OR A MEMORY AREA [R for the status code 16#818C
     and the reported behaviour; the Siemens manual sentence itself was never retrieved —
     external gap G6, §14. TAG CORRECTED 2026-08-12 by audit: it read a bare [R]];
  3. adding a scan-stamp to a DB is a structural change; in `%MW` it is a code change;
  4. *** STRONGEST: standard access can never carry a memory reserve [R x4 + M x1, verified
     five ways], so a standard-access DB can NEVER be downloaded without reinitialization.
     Its layout is FROZEN FOR THE LIFE OF THE RUNNING PROGRAM — change one member and the
     whole DB resets to start values, in RUN, with no dialog and no error. ***
     *** TAG CORRECTED 2026-08-12 BY AUDIT, AND THE CORRECTION IS THE POINT OF THE EVIDENCE
     CONVENTION: THE PREMISE IS DOCUMENTED, THE CONCLUSION IS INFERRED [I]. *** The research
     states, verbatim and immediately after this same chain: "this final chain is a synthesis.
     Siemens documents both halves and JOINS THEM NOWHERE." So "standard access has no memory
     reserve" is [R]; "therefore it can never download without reinitialization" is [I]. This
     is the single claim this section calls STRONGEST and the whole justification for `%MW`,
     which is exactly why it must not wear a borrowed tag. The argument still holds — three
     other independent arguments reach the same place, and one of them ([M], the measured
     layout revert) is the most solid thing here.

Any design that re-derives the map at a boundary is safe ONLY on `%MW`. On a DB mirror every
re-derivation is a silent wipe.

7. WHAT THE TEST ENVIRONMENT REPLACES
--------------------------------------------------------------------------------

IT REPLACES THE FUNCTIONAL REVIEW, where a rig is available. Observing behaviour against a
spec-derived vector is stronger evidence than an AI reading code against a register.

IT DOES NOT REPLACE THE OTHER REVIEWS. Conventions and simplicity say nothing about
behaviour and behaviour says nothing about them. They stay in loop 1, twice (§1.1).

*** THE TRAP: COVERAGE. *** A functional reviewer reads EVERY requirement and returns a
verdict on each. A test suite covers only what somebody wrote a vector for. This trades a
COMPLETE BUT FALLIBLE check for a NARROW BUT SOLID one — a good trade only if the narrowing is
MEASURED. Without a coverage gate, "all tests passed" is indistinguishable from "all
requirements verified", and the requirements nobody wrote a vector for look exactly like the
ones that passed.

*** RESOLVED 2026-08-12. THE DENOMINATOR, THE BUCKETS, AND WHAT THE GATE ACTUALLY GATES. ***

*** THE UNIT IS THE SPECIFICATION-DERIVED ASSERTION, QUALIFIED BY INSTANCE (D35). *** Draft 04
said CLAUSE here and mandated ASSERTION in D35; this is the resolution, and it is not a
compromise between them — it keeps exactly what each was protecting.

*** THE INVARIANT THAT DECIDES IT, AND IT IS ABSOLUTE: THE DENOMINATOR COMES FROM THE
SPECIFICATION, NEVER FROM THE TEST SUITE. *** Any unit defined by what somebody wrote a vector
for is SELF-REFERENTIAL — you cannot be missing an assertion nobody wrote, so coverage is
always 100% and the gate is theatre.

    So the question is not "clause or assertion". It is WHERE THE UNIT IS ENUMERATED.
      VECTOR-DERIVED assertions .... forbidden. This is what draft 04 §7 was right to reject.
      SPEC-DERIVED assertions ...... required. Decomposing a clause into its atomic assertions
                                     is a SPECIFICATION-SIDE operation, performed against the
                                     requirement text and complete BEFORE any vector exists.
                                     A vector then CITES into that enumeration; it cannot
                                     extend it, and an assertion no vector cites is exactly
                                     what the gate is for.

WHY ASSERTION AND NOT CLAUSE, given the invariant is satisfied either way: a clause carrying
two assertions — "shall open when X and close when Y" — is marked COVERED by a vector testing
only one, and the other vanishes silently. Many vectors per clause is the EXPECTED shape, which
makes this the normal case rather than an edge one: five vectors on that clause can all
exercise X, and a clause-level denominator reports it fully covered while nothing ever tested
Y. That is this project's own correlated-check failure wearing coverage clothing.

*** AND THE DECOMPOSITION IS NOT DISCOVERED AT THE VECTOR. *** Stated because the first
formulation of D35 said the vector's declaration is "exactly what makes the gap visible", which
is vector-derived discovery by another name and is precisely what the invariant above forbids.
The gap is made visible by the SPEC-SIDE DECOMPOSITION; the vector's citation is checked
AGAINST it, and a vector citing an assertion the decomposition does not contain is an ERROR in
the vector, not an extension of the denominator.

THE THREE "THIS ALREADY EXISTS" REASONS SURVIVE THE CHANGE, with one adjustment:
  - `TestVector.Basis` ALREADY CITES THE CLAUSE — it must now cite the clause AND the
    assertion within it. That is the one piece of new metadata this costs, and it is a field,
    not a mechanism.
  - it remains LIKE-FOR-LIKE OR STRICTLY FINER than what it replaces: the functional
    reviewer's verdict was per-requirement, so an assertion-level verdict is at least as
    granular, which keeps the substitution honest rather than approximate.
  - `converter relation-reconcile` already works on `(instance, relation-id)` pairs, so
    instance qualification has precedent here rather than being invented.

*** AND IT RETIRES A PRECONDITION RATHER THAN ADDING ONE. *** Draft 04 required verifying that
rung-B/C artifacts emit ATOMIC clauses, on pain of silent under-counting. Under a spec-derived
assertion denominator that check stops being load-bearing: if clauses are already atomic the
assertion is trivially the clause and the citation costs nothing, and if they are not, the
decomposition is where the extra assertions are discovered. Either way nothing vanishes
silently, which was the whole worry.

SIGNALS ARE A SECOND, INDEPENDENT CHECK — NOT THE DENOMINATOR. `converter signal-sweep`'s
residue answers a different question: is there a SIGNAL no requirement mentions? That catches
SPEC gaps where clause coverage catches TEST gaps. Two failure modes, two tools, neither
substituting for the other.

THE FOUR BUCKETS. Every ASSERTION lands in exactly one, and the wave reports all four:
    COVERED             a vector exists and cites this assertion
    OUT-OF-SCOPE        not a control-logic requirement at all (wiring correctness, HMI
                        behaviour, operator procedure). These were out of scope for the
                        FUNCTIONAL REVIEWER too — they belong to commissioning, not testing,
                        and calling them "untestable" overstated the gap.
    DEFERRED            testable, but blocked or not yet written. Two sub-cases, and the
                        second is the interesting one:
                          - no vector yet — owner and date;
                          - NEEDS MODEL FIDELITY WE DO NOT HAVE. M4 already routes these to a
                            refusal, and a refusal naming the missing capability is a MODEL
                            TASK, not an untestable requirement. This sub-case SHRINKS as the
                            library matures.
    UNTESTABLE-ON-RIG   genuinely so. *** SHOULD BE NEARLY EMPTY *** — see below.

*** WHY IT SHOULD BE NEARLY EMPTY, correcting an earlier overstatement in this document. ***
An earlier draft warned that with no I/O wired, "no actuation can be observed", so the
untestable set might be large. THAT CONFLATED PHYSICAL ACTUATION WITH THE PROGRAM'S OUTPUT
DECISION, and only the second matters for control logic. A coil energising IS the decision,
and the copy layer latches it — so "does the interlock prevent the valve opening?" is answered
completely by the coil never energising, whether or not anything is wired to it. With coil
latching and event scan-stamps, control-logic requirements are broadly testable. If this
bucket turns out large, that is a FINDING TO CHASE, not a category to accept.

*** ONE REAL CATEGORY THIS DID NOT ACCOUNT FOR, ADDED 2026-08-12 BY AUDIT: FIRST-SCAN AND
POWER-UP REQUIREMENTS. *** "On start-up all valves shall be closed"; "retentive setpoints shall
survive a restart". The inert phase establishes a start STATE but cannot produce a first SCAN,
and OB100 never runs again once the CPU is in RUN — so these are genuinely untestable IN A
WAVE. They are NOT untestable ON THE RIG: §16.6 (X-F) routes them to the disruptive boundary,
which already stops and restarts the CPU. Classify them as a STARTUP TEST class, never as
UNTESTABLE-ON-RIG — the bucket stays nearly empty, but only because the class exists.

*** THE GATE IS `UNCLASSIFIED = 0`, NOT A PERCENTAGE. *** A threshold fails in a specific way:
the uncovered remainder is NOT random. It is the requirements that are hard to test, which
correlates with hard to implement, which is where defects live — so a threshold silently
concentrates risk in the worst place while reporting a comfortable number. Every ASSERTION
must have been CONSIDERED; not every assertion must have a test.

*** AND THE GATE STOPS THE CLAIM, NOT THE RUN. *** Blocking a wave for a bookkeeping reason
spends the scarce thing (rig time) to enforce the cheap thing. A wave with incomplete
classification still produces useful results — it simply MAY NOT CLAIM "requirements
verified". That decouples honesty from throughput.

HONEST LIMIT, ACCEPTED: the gate proves someone LOOKED, not that they looked WELL. Classifying
is cheap; classifying honestly is not, and under pressure everything becomes DEFERRED while
the gate still passes. What carries real weight is DEFERRED items having an OWNER and a DATE,
with their count and AGE reported every wave — aging deferrals are the signal, not the
classification.

CLASSIFICATION IS STICKY, so this does not churn: once an assertion is classified it stays
until the requirement text changes or the implementing block changes — detectable by hashing
the assertion text and by `converter ir-hash` respectively. Re-classification is proportional
to CHANGE, not to total requirement count.

*** THIS SECTION SETTLES WHERE THE UNIT IS ENUMERATED AND NEVER SAYS WHAT THE UNIT IS. THAT GAP
IS NOW FILLED — `docs/notes/assertion-enumeration.md` (2026-08-13). *** It was found while
dispatching the 5.1 skill: the contract requires a vector to cite an assertion ID "drawn from
the spec-derived enumeration", and the enumeration had no definition, so the skill could only
check that SOMETHING was written in the field — the difference between a gate and a formality.
*** AND AN AMBIGUOUS DECOMPOSITION MAKES THE DENOMINATOR NEGOTIABLE, WHICH DEFEATS THIS
SECTION'S OWN INVARIANT BY A DIFFERENT ROUTE: coverage stays 100% because the counting was
generous rather than because the unit was self-referential. *** The definition, in one line:

    *** AN ASSERTION IS THE SMALLEST STATEMENT ABOUT OBSERVABLE BEHAVIOUR THAT CAN BE FALSIFIED
    ON ITS OWN *** — there is a possible defect that makes it false while leaving every other
    assertion of the clause true. Written as `WHEN <trigger> THEN <response> [WITHIN <bound>]`
    or `NEVER <forbidden state>`; split on TRIGGER and on RESPONSE, never on QUALIFIERS such as
    a timing bound, and never on IMPLEMENTATION.

  🔴 *** ONE CORRECTION TO THIS SECTION, AND IT IS THE STICKY KEY. *** The key proposed above —
  `(clause hash, assertion index, assertion text hash)` — has a POSITIONAL middle term. Insert
  an assertion at index 1 and every later index shifts, so a stored classification silently
  comes to name a different assertion. The hazard is narrower here than it looks, because this
  section uses the key for STICKINESS rather than for CITATION — but a citation and a
  classification must not key on different things, and only the CONTENT-DERIVED form is safe.
  *** IDs ARE `REQ-014:3f9a1c` — clause ID plus a hash of the normalised assertion text, with
  NOTHING POSITIONAL IN THEM. The index survives as a DISPLAY ORDINAL that may never be cited. ***
  Editing an assertion's text CHANGES its ID deliberately: the old one dangles, prior citations
  are flagged stale, and a `supersedes:` link records it — because a citation that silently
  survives a rewording of what it cites was written against words nobody re-read.

  *** AND `UNCLASSIFIED = 0` IS MADE ENFORCEABLE BY NEVER BEING WRITABLE: *** it is the set
  difference `enumerated - (COVERED u OUT-OF-SCOPE u DEFERRED u UNTESTABLE-ON-RIG)`, computed
  and not declared, so a forgotten assertion produces a failed gate rather than a missing tick.
  Same shape as phase 2's `AddressesExamined` separate denominator. An enumeration parsing ZERO
  assertions is *nothing examined* and fails — empty is not clean.

  *** THREE THINGS IT RAISES THAT THIS SECTION DOES NOT ANSWER, THE LAST BEING THE IMPORTANT
  ONE: *** whether STARTUP is a fifth bucket or a scheduling attribute (proposed: attribute, so
  "exactly one bucket" survives); where a vector author's DECOMPOSITION DISPUTE is recorded and
  who rules on it; and *** WHO PERFORMS THE ENUMERATION — because if it is the block's author,
  D6's independence is lost AT THE DENOMINATOR, which undoes most of the protection this section
  is built on. That should be ruled before the 5.1 skill is built. ***

*** ONE CONSEQUENCE OF THE ASSERTION UNIT THAT MUST BE BUILT FOR, NOT DISCOVERED: RE-READING A
CLAUSE CAN CHANGE ITS DECOMPOSITION. *** A clause previously read as one assertion may later
decompose into two. That is NOT a classification change and must not be silently absorbed as
one — the new assertion is UNCLASSIFIED and the gate must fail until someone rules on it.
Hashing the CLAUSE text alone would miss this, because the clause did not change; the
DECOMPOSITION did. So the sticky key is (clause hash, assertion index, assertion text hash),
and a decomposition that yields a different count than last time is reported as its own event.

AND THE INDEPENDENCE MUST SURVIVE THE SWAP. Part of what a functional reviewer provided was a
SECOND READING of the specification. A vector authored by a different agent preserves that;
one authored by the block's own author does not — it moves the failure rather than removing it
(D6).

7a. FAILURE ATTRIBUTION — WHICH OF FIVE THINGS IS WRONG
--------------------------------------------------------------------------------

A red result has FIVE possible causes, and the receiving agent is the WORST-PLACED party to
judge: it did not write the vector (D6) or the model (M1), so it can see only its own block
and will suspect that first.

  1. THE BLOCK IS WRONG           — the finding you wanted
  2. THE MODEL IS WRONG           — fidelity, or a modelling error
  3. THE VECTOR IS WRONG          — the author misread the spec
  4. ANOTHER AGENT INTERFERED     — shared state the graph did not predict
  5. *** THE BLOCK WAS NEVER DOWNLOADED *** — the cheapest to rule out and the most
                                    embarrassing to miss

THE DEFAULT FAILURE MODE IS AN AGENT "FIXING" CORRECT CODE UNTIL A WRONG TEST PASSES. Worked
example: a fill block implements a pre-act offset correctly; the model has no in-flight mass,
so nothing overshoots, so the fill stops short and the test fails; the agent removes the
offset and the test passes. *** THE CORRECT IMPLEMENTATION HAS BEEN ENGINEERED OUT BY THE
TEST, and the report says green. ***

THE APPROACH (decided 2026-08-12): the agent judges — but only after the FREE evidence is
attached to the result automatically. Cost, honestly priced:

  FREE, attached to every result:
    - the CO-RUNNING LOG (D21)                          -> cause 4
    - the VALIDITY STAMP comparison (DB-2): block
      unchanged but result changed                      -> not cause 1, by construction
    - the LOAD MANIFEST check (§9a): is this block
      in the last manifest at all?                      -> cause 5
    - CROSS-AGENT PATTERN: same shape failing across
      several agents                                    -> model or environment, not N bugs
    - the FIDELITY BOUNDARY CHECK — already enforced
      at ADMISSION by M4, so it never reaches diagnosis -> cause 2, prevented not diagnosed
    - *** ASSERT ON THE STIMULUS, NOT ONLY THE RESPONSE *** — the model is a block and its
      state is readable, so check the model actually produced the rate/setpoint the vector
      parametrised. If it did not, the fault is the model or the parametrisation and the
      block is exonerated WITHOUT BEING TOUCHED. Sharpest cheap discriminator available;
      costs a few registers in the mirror.

  CHEAP, on failures only:
    - BASIS RE-DERIVATION — one spec read by the vector's author        -> cause 3
    - RE-RUN IN ISOLATION via the enable bitmask — one test, a register
      write, NO download                                               -> cause 4, confirmed
    - DOES IT REPRODUCE? intermittent points at interference or the observability floor

  EXPENSIVE, and NEVER BY DEFAULT:
    - re-run against a DIFFERENT model of the same equipment. Only needed for "the model
      claims to represent this and does it wrong", which is a MODEL REVIEW problem (M5), not
      a per-failure diagnostic.

*** ONE HARD RULE: A FAILING TEST MAY NOT BE CLOSED BY CHANGING THE BLOCK UNTIL THE VECTOR'S
BASIS HAS BEEN RE-CONFIRMED. *** One spec read, on failures only, and it is what stops the
worked example above.

ORDER OF ELIMINATION: deployment, interference, vector, model, THEN block. *** THE BLOCK IS
THE LAST HYPOTHESIS, NOT THE FIRST *** — precisely because the receiving agent's instinct is
the reverse.

WORTH MEASURING ON THE FIRST REAL WAVE: log the eventual TRUE cause of every failure. If they
are overwhelmingly cause 1, most of this is over-engineering and the co-running log plus a
re-run-in-isolation button would cover it.

8. THROUGHPUT — WHERE THE COST ACTUALLY IS
--------------------------------------------------------------------------------

MEASURED BY THE OWNER, from experience: *** download time scales with the NUMBER OF OBJECTS,
not with the act of downloading. *** A small delta is around 20 seconds; a full program of
~100 objects around 2 minutes. Worked through the <=20 budget:

    6 agents  x (FB + UDT + iDB) = 18 objects = 1 download  ~= 20-25 s   [CORRECTED]
   20 agents                     = 60 objects = 3 downloads ~= 1-1.5 min [CORRECTED]

*** BOTH FIGURES CORRECTED 2026-08-12 BY AUDIT — THEY CONTRADICTED THIS SECTION'S OWN PREMISE,
AND REAL MEASUREMENTS EXISTED AND WERE NOT USED. *** They read "1-2 min" and "3-6 min", which
cannot follow from "time scales with the NUMBER OF OBJECTS" when ~100 objects takes ~2 min:
18 objects then costs about 22 s, and the premise explicitly denies a fixed per-download cost
that could account for the rest. MEASURED, from the probe logs, wall-clock end to end AND
INCLUDING Portal attach, project open and a read-only download-plan — so the download itself
was shorter still:

    99 objects (full)         80.9 s   [M, 2026-08-12]
     1 object  (differential) 32.1 s   [M, 2026-08-12]

*** AND THE OWNER'S ~20 s / ~2 min FIGURES ARE RECOLLECTION, NOT MEASUREMENT [I]. *** They are
tagged here because every throughput number in this document descends from them and they
carried no tag at all. They are consistent with the two measurements above, which is why they
survive — but design gap G-5 ("DOWNLOAD DURATION — MEASURE IT. One number.") was recorded as
CLOSED on recollection while three real measurements sat unused in the same job scratch.

MINUTES, NOT HOURS. Downloads are cheap enough that there is no reason to hoard them, which
reinforces DB-4's inversion: smaller, more frequent wave sets are fine.

*** THEREFORE DOWNLOADS ARE ALMOST CERTAINLY NOT THE BOTTLENECK. TEST EXECUTION IS. *** That
promotes D12 — time compression in the models — from a good idea to THE throughput lever.

--- CORRECTED IN DRAFT 04. The paragraph above is right about downloads and WRONG about what
    replaces them. ---

Under D26 the cost of the test half of a wave is:

    wave = download boundary + SUM over tensors ( inert reset + MAX test duration in tensor )

Worked, for 6 agents x 5 vectors = 30 tests, packing 6 wide into *** 5 TENSORS ***:

    inert 2 s,  longest test  5 s,  5 tensors  ->  ~55 s
    inert 5 s,  longest test 10 s,  5 tensors  ->  ~1.6 min
    inert 10 s, longest test 60 s,  5 tensors  ->  ~6 min

*** THE SAME 30 TESTS COMPUTED AS A SERIAL SUM GIVE 3.5 TO 35 MINUTES, AND THE PACKED FIGURE
    IS ABOUT 6x SMALLER — 4x TO 6x ONCE THE DOWNLOAD BOUNDARY IS COUNTED ON BOTH SIDES. ***
    The packed figure is the correct one. The serial arithmetic was performed in this project
    first, believed, and used to argue that feedback latency would ruin IR development. It
    would not.

    *** THESE TWO NUMBERS WERE THEMSELVES WRONG UNTIL 2026-08-12, WHEN THE AUDIT CAUGHT THEM —
    THE THIRD ARITHMETIC ERROR IN THIS SECTION. *** They read "8 to 35 minutes" and "5 to 10
    times smaller". The lower bound silently omitted this section's own fastest row
    (30 x (2+5) = 210 s = 3.5 min), and *** A 10x RATIO IS ARITHMETICALLY IMPOSSIBLE HERE: ***
    packed and serial scale by the same (inert + test) term, so the ratio IS THE PACKING WIDTH
    BY CONSTRUCTION — 6x at 6 wide, and less once a fixed boundary is added to both. A section
    that exists to stop a wrong number being re-derived had an unachievable figure in its own
    correction, which is worth more caution than the number itself.

TWO CONSEQUENCES THAT CHANGE PRIORITIES:

  1. *** THE BOTTLENECK IS TENSOR COUNT, AND TENSOR COUNT IS SET BY CONFLICT DENSITY *** — so
     the throughput lever is DB-13's packing and D28's per-test model instances, not time
     compression. D12/D19 keep a narrower job: individually long tests (DB-12).
  2. *** AT ABOUT A MINUTE A WAVE, FEEDBACK LATENCY IS NOT THE PROBLEM; ITERATION COUNT IS ***
     (D30). Optimise the information a wave returns (DB-8) before optimising how often waves
     happen.

WHAT WOULD FALSIFY THE PACKED FIGURE: tests that do not pack. If conflict density forces 1-2
per tensor, tensor count returns to test count and the serial arithmetic becomes correct after
all. That is a measurement, not a judgement — see DB-13's closing note.

*** A FOURTH ARITHMETIC CORRECTION, 2026-08-13: THE WAVE MODEL ABOVE HAS NO WIRE TERM, AND ON
THE FASTEST ROW THE WIRE TERM IS WORTH ABOUT A THIRD OF THE WAVE. *** Applying a vector and
reading a result are round trips, and round trips are now measured (§12a). Derived in full at
§12a derivation 3; the result, at this section's own shape of 6 slots x 5 indices with 2 poll
rounds per test:

    round trips per index  =  K x ceil(W/123) + P x ceil(K/R) + 1        R = floor(125/W)   [D]

      W = 123, R = 1 : 6 + 12 + 1 = 19/index = 95/wave = *** 9.8 s at RTT_p90 102.79 ms ***
      W =  20, R = 6 : 6 +  2 + 1 =  9/index = 45/wave = *** 4.6 s ***

    (The read term is `P x ceil(K/R)` because ONE FC03 read may cover R WHOLE slots — X-A's rule
     as amended by F-1, adopted 2026-08-13. It was `P x K` until then. And the figures are keyed
     on RTT_p90 because a wave cost is DURATION-SHAPED — §12a's F-5 kind rule; they were quoted
     at RTT_p99 for part of 2026-08-13, which was a 1-in-100 case being presented as the cost.)

    row as written above          test half + boundary      + wire (R=1)      + wire (R=6)
    inert  2 s, test  5 s   ~55 s     35 s + ~20 s      ->  *** ~65 s, +18% ***  ~60 s,  +8%
    inert  5 s, test 10 s   ~1.6 min  75 s + ~20 s      ->      ~105 s, +10%     ~100 s,  +5%
    inert 10 s, test 60 s   ~6 min   350 s + ~20 s      ->      ~380 s,  +3%     ~375 s,  +1%

    (at RTT_p99, the pessimistic case: 74 / 114 / 389 at R=1, 64 / 104 / 379 at R=6)

*** THE CONCLUSIONS OF THIS SECTION ALL SURVIVE — ~74 s is still order-of-a-minute, downloads are
still not the bottleneck, and the packed-versus-serial ratio is unaffected because the serial case
pays the same per-test wire cost MORE times. *** What does not survive is quoting ~55 s as the fast
case: it is ~74 s, and the difference is the wire, which this section had priced at zero. The term
scales with K, so it grows with exactly the packing this section relies on for its 6x.
(Figures raised 2026-08-13 with `RTT_p99` 173 -> 201 ms; they read 16.4 s / ~71 s / +30% for one day.)

9. THE VERSION REGISTER — LOAD-BEARING IN THREE PLACES
--------------------------------------------------------------------------------

The marker DB exists because the CPU will not state its own identity, so the PROGRAM
publishes it. The same trick answers post-download verification without any upload.

The coordinator knows exactly which IR set it downloaded, computes a build hash, and
GENERATES A LITERAL into the copy layer:

    MOVE  16#A93F2C71  ->  MD_ProgramVersion

That constant lives IN THE CODE, so it can only be present if that code is running.
Verification becomes ONE REGISTER READ — no upload, no Portal session, sub-second.

*** IT IS `%MD`, NOT `%MW` — CORRECTED 2026-08-12 BY AUDIT, AND IT MATTERS BECAUSE THIS IS THE
ONE PLACE THE MECHANISM IS SPECIFIED AND WILL BE COPIED. *** A `%MW` is a 16-bit WORD;
`16#A93F2C71` is eight hex digits, 32 bits. The line as previously written does not compile.
Consequences to carry through: the version register occupies TWO Modbus holding registers, the
word-order rule stated later in this section applies to it, and DB-6's "the map artifact
carries a hash; the version register carries the same value" means a 32-bit hash across that
same register pair. A 16-bit truncation of a build hash would also collide far too easily to
serve as an identity.

WHAT IT CATCHES: a download that aborted or was refused (the register still shows the OLD
version — external gap G4's undocumented half-loaded case, detected without needing Siemens to
document it); a download that never reached the device; and the SETTLING WINDOW, since the
value flaps or reads old until integration completes, so waiting for stability MEASURES the
window rather than guessing it.

WHAT IT DOES NOT CATCH: individual block corruption. That is a reasonable trust boundary — TIA
performed the download; if the version constant is live, the code carrying it is live.

THREE PURPOSES, ONE MECHANISM, designed once: post-download verification (D14), settling-window
detection (DB-3), and guarding the frozen map (DB-6).

9a. THE LOAD MANIFEST — measured 2026-08-12, and better than the version register
    for one specific question
--------------------------------------------------------------------------------

*** A DOWNLOAD REPORTS, PER OBJECT, WHAT IT ACTUALLY LOADED. *** The `DownloadResult`
message tree contains one message per object, verbatim:

    'DB_RigMarker' was loaded successfully.
    'UDT_CmdAck' was loaded successfully.
    ... one per object ...

MEASURED, and both runs matched prediction EXACTLY:
    DIFFERENTIAL : 1 message  — `DB_RigMarker`, precisely the one block that had changed
    FULL         : 99 messages — and `download-plan` had reported 66 blocks + 33 PLC data
                   types = 99. The predicted count and the loaded count agree.

THREE USES, and the third is the valuable one:

  (a) POSITIVE EVIDENCE OF TRANSFER, replacing an inference from absence.
      *** THIS CORRECTS THE PROBE. *** `download-probe` currently reports transfer by
      searching for "has not been loaded" / "up-to-date" and concluding TRANSFERRED when
      absent, stating in its own output that "TIA emits no positive 'the software was
      loaded' sentence to key on". THAT IS FALSE — there are 99 of them. The verdict should
      key on the per-object load messages and report the COUNT. Fix pending.

  (b) CONFIRMATION OF *WHAT* WAS DOWNLOADED, per object, not merely that something was.

  (c) *** A CROSS-CHECK ON DB-1. *** The coordinator PREDICTS a change set; TIA REPORTS the
      set it actually loaded. Comparing them checks our change tracker against TIA's own
      online/offline comparison, on every download, for free. A MISMATCH MEANS OUR TRACKER
      IS WRONG — and DB-1's baseline is what every STOP/RUN(Init) prediction and every
      <=20-object batching decision hangs off, so being able to falsify it continuously is
      worth more than the other two uses combined.
      It also closes a hole named in DB-1: `openness-cli export-all` reads the OFFLINE
      PROJECT, so it cannot detect a partially-applied download. The manifest reports what
      the DEVICE accepted.

RELATIONSHIP TO THE VERSION REGISTER (§9) — they answer different questions and neither
replaces the other:
    LOAD MANIFEST   : what moved in THIS operation. Per object. Available only at download
                      time, from the download's own result.
    VERSION REGISTER: what is running NOW. Readable at any time, over Modbus, sub-second,
                      and the only thing that detects an aborted or half-applied download
                      after the fact.

9c. THE DOWNLOAD FEEDBACK PARSER — a required component
--------------------------------------------------------------------------------

The `DownloadResult` message tree is the richest evidence any download produces, and every
run so far has proved it carries more than the design assumed. It needs a real parser, not
phrase-matching bolted on.

WHAT IT MUST EXTRACT:

  1. *** THE LOAD MANIFEST *** — every `'<name>' was loaded successfully` message, as a SET
     of object names plus a count. This is the positive evidence of transfer (§9a) and the
     cross-check on DB-1.
  2. *** RUN-STATE TRANSITIONS *** — `PLC_1 stopped.` / `PLC_1 started.`, in order, so the
     coordinator knows the state the CPU was left in rather than inferring it.
  3. *** NON-OBJECT LOADS *** — `Hardware configuration`, `Connection configuration`,
     `Routing configuration` were each reported with their own wording. A parser keyed only
     on the block form would silently drop all three.
  4. *** THE UP-TO-DATE SIGNAL *** — `The software has not been loaded, because it is
     up-to-date`, which means SUCCESS WITH NOTHING TRANSFERRED.
  5. Per-node state, error and warning counts, preserved with their nesting.

DESIGN RULES, each earned by something that has already gone wrong:

  - *** NEVER READ `state=Success` AS EVIDENCE OF TRANSFER. *** The first run that returned
    Success transferred nothing.
  - *** REPORT THE COUNT, NOT A BOOLEAN. *** "1 object" versus "99 objects" is what makes the
    DB-1 cross-check possible; a yes/no throws that away.
  - *** UNDETERMINED IS A THIRD VERDICT AND MUST NEVER COLLAPSE INTO A NEGATIVE. ***
  - *** SURFACE UNRECOGNISED MESSAGE SHAPES — DO NOT DROP THEM. *** Four distinct message
    vocabularies have appeared in six runs, and each new download option produced one nobody
    predicted. A parser that classifies only what it knows will go quietly blind exactly when
    something new happens, which is exactly when you need it.
  - Prefer POSITIVE evidence over inference from absence. The probe currently infers transfer
    from the absence of an up-to-date phrase while sitting on 99 positive load messages — the
    correction §9a records.
  - *** AND THE DEFECT IS WORSE THAN §9a DESCRIBES — FOUND 2026-08-12 BY AUDIT. *** The probe's
    verdict line does not only infer from absence; it ALSO READS `state=Success` directly:
    "WAS ANYTHING TRANSFERRED? *** YES - THE SOFTWARE WAS LOADED (state=Success, errors=0)."
    That is the exact reading the first rule in this list forbids. *** FIXING ONLY THE
    ABSENCE-INFERENCE LEAVES THE FORBIDDEN READING IN PLACE *** — both have to go, and the
    replacement for both is the load manifest.
  - AND THE SAME LOG STATES, WRONGLY, THAT "TIA emits no positive 'the software was loaded'
    sentence to key on" while carrying 99 sentences of exactly that form. A parser built from
    that sentence would be built to do the wrong thing on purpose.

WHERE IT IS USED: post-download verification (with §9's version register), the DB-1
cross-check, run-state tracking for DB-3's settling window, and the per-agent results that
carry the co-running log (§2.4).

10. PROTOCOL COEXISTENCE

11. MODELS, INERT STATE, FAILURE HANDLING, PROVENANCE
--------------------------------------------------------------------------------

MODELS (D4, D12). Driving raw values over the wire cannot express time: round trips are
*** 71-78 ms median and 201 ms at the budgeting p99 [M, full width, 2026-08-13] against a scan of
23.33 ms [M] *** — 3.3 to 8.6 scans per exchange [D, §12a derivation 1] — with one sample in 2,000 at 2,216 ms,
which is 95 scans [D]. A PID loop cannot be closed over a VPN at all, and the tail is why: a
controller that is 95 scans late once every two thousand samples is not a controller.
(*** THE FIGURE HERE READ "79-108 ms [M] against a scan of ~10 ms" UNTIL 2026-08-13. *** Both
constants were wrong and they moved in OPPOSITE directions — see §12 and §12a. The conclusion
this paragraph draws is unchanged and in fact strengthened; the arithmetic under it was not.)
Parametrising a PLC-side model generates the dynamics AT SCAN RATE inside the controller; the
link carries parameters and results. Already proven in this codebase by the live program's own
plant simulation.

*** THE MODEL-AUTHORING CONTRACT (resolves O4 and O5, decided 2026-08-12) ***

M1. AN INDEPENDENT lad-coder AUTHORS THE MODEL — never the agent that wrote the block it will
    test. Same independence rule as D6, same reasoning.

M2. *** THE PHYSICAL ANALYSIS IS GROUNDED IN THE EQUIPMENT, NOT IN THE CONTROL SPECIFICATION.
    *** This is the load-bearing half of M1 and it is easy to satisfy in appearance only. A
    model derived from the control spec — or from the same P&ID / equipment-spec artifacts the
    block was designed from — INHERITS THAT SPEC'S ASSUMPTIONS. A spec that never considered
    in-flight material yields a model with no in-flight material, and a block that ignores it
    passes. *** THE SPEC'S BLIND SPOTS BECOME UNTESTABLE, and the independence bought by using
    a different agent is spent, because both read the same source. *** The analysis must come
    from how the EQUIPMENT behaves — load-cell dynamics, settling time, in-flight mass, valve
    travel, sensor quantisation — not from what the control spec says about using it.

M3. EVERY MODEL CARRIES A FIDELITY DECLARATION: what it does and does NOT represent (noise,
    lag, overshoot, in-flight mass, saturation, quantisation), plus a declared SCAN-TIME
    BUDGET (M6). It is reproduced in every result derived from it, so a green is never read
    without its caveats.

M4. *** A VECTOR MAY ONLY ASSERT BEHAVIOURS THE MODEL CLAIMS TO REPRESENT; THE RUNNER REFUSES
    IT OTHERWISE. *** This makes fidelity MACHINE-CHECKABLE in exactly the way `Observability`
    already makes sampling limits machine-checkable, and it reuses a discipline the codebase
    has proven it will honour rather than adding one nobody enforces. Same principle: a green
    that cannot mean anything is worse than a refusal.

M5. *** A MODEL GETS MORE REVIEW THAN A BLOCK, NOT LESS — THE BLAST RADIUS IS INVERTED. *** A
    wrong block fails its own tests and the system catches it. A wrong model SILENTLY CORRUPTS
    EVERY VECTOR THAT USES IT, and the more useful the model, the more results it quietly
    invalidates. So models go through the same review path as blocks — conventions, simplicity,
    and a functional review against the physical analysis — plus validation against real plant
    data wherever any exists. Where none exists, that ABSENCE is recorded in the fidelity
    declaration.

M6. MODELS COMPETE FOR SCAN TIME. Every model runs every scan and they accumulate with agents,
    which interacts with OB80's overrun handling and the <=20-object batching. The declared
    budget makes the ceiling visible before it is hit rather than discovered as a cycle-time
    trip mid-wave.

M7. *** MODELS ARE PROVISIONAL UNTIL REVIEWED AND VALIDATED. *** The library ACCRETES from
    models written to order, and the trap in that is that the FIRST few become the standard by
    default — including their limitations, unexamined, and written before any wave had taught
    anyone which fidelity actually matters. Promotion into the library is a DECISION, never a
    consequence of having been first.

THE WORKED EXAMPLE THAT DECIDES M2 AND M4. A fill-control block closes the valve when weight
reaches setpoint. Against an idealised weigher — instant response, no material in flight — it
passes cleanly. On the real plant, material already falling continues after the valve closes,
so the vessel overshoots and the correct implementation needs a pre-act offset. *** THE
IDEALISED MODEL DOES NOT MERELY MISS THE DEFECT — IT CERTIFIES THE NAIVE IMPLEMENTATION AND
WOULD REJECT THE CORRECT ONE, *** which closes "early" and under-fills against a model with no
in-flight mass. That is worse than having no test.

INERT STATE (D5). FB statics survive between tests, so results depend on wave ORDER. A
GENERATED reset routine, triggered by a command register, with retentive members explicitly
written. *** THE RESET IS READ BACK AND CONFIRMED *** — an unverified reset is the "a warning
is not a gate" shape. Per-test instance DBs (D10) remove most of the need.

FAILURE HANDLING. Reject both a pre-wave smoke pass (costs time every wave to guard something
rare) and accept-the-risk-then-serialise (the expensive part is ATTRIBUTION). Instead:
generate an OB80 so an overrun is LOGGED rather than STOPping the CPU; write a "block currently
executing" register so OB80 attributes it for free; keep the block-enable bitmask as runtime
data so bisecting is a register write.
  Justified by COST ASYMMETRY, not probability: after a STOP a human must restore RUN, so
  unattended, one bad block turns a wave into a dead night.
  HONEST LIMIT: OB80 does not save you from a true infinite loop.
  NOTE: OB80 is itself a STOP-class change (a new OB), so it is installed at rig setup or via
  the deferred queue — never mid-wave.

PROVENANCE (D6). `TestVector.Basis` is required; a vector that cannot cite its specification
clause is not admissible into a wave.

BYTE AND WORD ORDER. Because we author both ends the convention is ours and a round-trip proves
the halves agree. ONE RESIDUAL: `MB_SERVER`'s own byte-to-register presentation is Siemens'
behaviour, which no fake we write can validate. Build swap as a configurable transform and
CALIBRATE with a known bit pattern — one measurement, once.

*** THE FINDING THAT CHANGES THE DESIGN'S ARITHMETIC: MARGINAL COST PER REGISTER IS
INDISTINGUISHABLE FROM ZERO. *** 1, 4, 8 and 16 registers all cost the same within noise. **Slot
width is not the scarce resource — ROUND TRIPS ARE.** D29 bounds tensor width by poll bandwidth on
the assumption that registers cost; they do not, up to the FC03/FC16 limits. Re-derive.
(Measured over the tunnel, not a LAN.)

*** SHARPENED 2026-08-13 BY A FULL-WIDTH MEASUREMENT, AND THE HEADLINE ABOVE IS NOW SLIGHTLY TOO

estimates — see §12a]. That is ~1-5 ms across a full-width slot against a 75-78 ms round trip — so
**the conclusion survives by at least 16x and the phrase "zero" survives only as shorthand.** The
same re-measurement moved the p99 the design budgets on from 173 to 201 ms.

*** AND THE OBVIOUS FOLLOW-UP — DOES WIDTH WIDEN THE *TAIL* AS WELL AS THE BODY? — WAS FLAGGED
RATHER THAN ASSUMED, THEN MEASURED WITH 16,200 INTERLEAVED ROUND TRIPS, AND THE ANSWER IS NO
EFFECT DETECTABLE. *** The highest tail lands at width 16 in the read arm and width 123 in the
write arm. So `RTT_p99 = 201` is a *** SESSION *** figure rather than a width figure, it stands
unchanged, and *** NOTHING ARGUES FOR CAPPING SLOT WIDTH ON TIMING GROUNDS. *** §12a's constants
block and flag F-4 carry the sequence, the power limits and what the conclusion actually rests on.

*** RE-DERIVED 2026-08-13 — §12a. *** The three paragraphs above stated the problem and asked for
the arithmetic; §12a is the arithmetic, and it is the only place in this document where a timing
constant is chosen. Read it before using any figure below.

*** THE "~100 ms POLL" WAS NEVER A PARAMETER AND MUST STOP BEING WRITTEN AS ONE (2026-08-13). ***
A poll costs exactly one round trip per slot read, so the poll period is `K x RTT` — set by the
wire and the tensor width, not chosen. For one slot that is 78 ms typical and 201 ms at the p99
(raised from 173 on 2026-08-13 by a full-width re-measurement — §12a), which is *** 3.3 to 8.6
scans, and K TIMES THAT for a K-slot tensor *** [D, §12a derivation 1].
A one-scan event is therefore still structurally invisible to a sampler — the irreducible floor is
3 scans even for a poller running flat out at the fastest MEDIAN measured — but the margin
is 3.3-8.6x, not the ten times this section argued from. NO POLLING RATE RECOVERS IT, and no
protocol choice changes it. (The sentence replaced here read *"Polling observes at roughly 100 ms
against a scan of ~10 ms, so a one-scan event is about ten times below anything a sampler can
see"* — both constants wrong, and the 100 ms was an assumption that had been re-read as a fact.)

So the copy layer provides: a FREE-RUNNING SCAN COUNTER (always, unconditionally — one counter
for the whole program; its absence silently degrades every `WaitScans` into a wall-clock guess
on a non-real-time host); LATCHED TRANSIENTS (default on for coil-shaped signals — set-dominant
in the copy layer, cleared at TEST START rather than read-then-clear, so an observation does not
drag the write fence in); and EVENT SCAN-STAMPS (opt-in per signal in the map — a latch answers
"did it happen", a stamp answers "when, relative to what", at roughly 32x the memory).

*** AND THE "WHAT" A SCAN-STAMP IS RELATIVE TO IS NOW DEFINED: THE START BOOL'S RISING EDGE
(D37). *** Until that decision existed this section asked stamps to answer "when relative to
what" while the design supplied no origin, so a stamp was an absolute counter value that only
became meaningful by comparison with other stamps. Stamps are now DIFFERENCES IN SCANS FROM
T=0, which is the unit the whole observability argument is conducted in.

    A COROLLARY WORTH BUILDING FOR: the scan counter is free-running and WILL WRAP. A stamp
    taken as a difference from T=0 is immune to a wrap that happens between waves, which an
    absolute stamp is not — but a wrap DURING a long test still has to be handled in the
    subtraction rather than assumed away.

    it makes healthy tests fail.

    *** AND THE DEEPER POINT, WHICH IS THE WHOLE REASON F-5 WAS ADOPTED: A SINGLE TAIL NUMBER WAS
    BEING ASKED TO DO TWO JOBS. *** Replacing one single number with a different single number
    would repeat that mistake in the other direction. *** THE PAIR DESCRIBES THE DISTRIBUTION'S
    SHAPE — p90 says where the body ends, exceed_250 says how often the outlier regime is
    entered — AND EACH HALF HAS A JOB. *** Neither is "the tail figure".

    A bound is therefore quoted as a p99-keyed figure PLUS its residual exposure:
    `exceed_250 x (round trips in the operation)` — an expected count of over-threshold exchanges,
    which is a number the reader can act on rather than an implied percentage.

    *** HOW TO QUOTE THE TWO, AND THEY ARE NOT QUOTED THE SAME WAY: ***
      - *** p90 AS A NUMBER *** — 102.79 ms, +/- ~1.05%. It is precise, and it is SILENT about the
        worst case.
      - *** exceed_250 AS AN ORDER OF MAGNITUDE — "about one round trip in 300." *** It rests on
        57 events, so its 95% interval is +/- ~26%; quoting "0.352%" to three figures implies a
        precision it does not have. It is the ONLY one of the two that describes the outlier
        regime at all, which is why it earns its place despite the width.

    🔴 *** A CORRECTION TO THE REASONING THIS DOCUMENT GAVE FOR PREFERRING AN EXCEEDANCE RATE, AND
    IT IS WORTH RECORDING BECAUSE THE WRONG VERSION IS PLAUSIBLE. *** F-5 argued that an exceedance
    rate is better because it *"pools across runs without inheriting an order statistic's
    variance."* *** THAT IS WRONG FOR THE p90. THE PROBLEM WITH THE p99 WAS NEVER THAT IT IS AN
    ORDER STATISTIC — IT IS THAT IT IS AN ORDER STATISTIC IN THE SPARSE TAIL. ***

        at p99 of a 300-sample run   you are reading the 4th-worst value
        at p90 of 16,200             the rank has SD 38 out of 14,580, sits inside a ~2 ms
                                     window, and has ~1,600 samples above it

    *** DENSITY AROUND THE QUANTILE GOVERNS THE VARIANCE, NOT QUANTILE-NESS. *** The p90 is an
    order statistic and is the most precise number in this section (+/- 1.05%); the exceedance
    rate is a simple count and is the least precise (+/- 26%, on 57 events). The original
    reasoning had the mechanism backwards while reaching a defensible conclusion, which is the
    kind of error that survives review.

*** WHY RTT_p99 IS SET AT THE WORST OBSERVED (201) AND NOT THE WEIGHTED ESTIMATE (183) — THE
REASONING IS EXPLICIT BECAUSE PICKING ONE SILENTLY IS THE FAILURE HERE. ***

  1. *** FOUR RUNS IS A THIN BASIS FOR A TAIL STATISTIC, AND THE ARITHMETIC SAYS SO. *** The four
     run p99s are 157 / 201 / 168 / 185: unweighted mean 177.75, sample SD 19.3, standard error
     9.7 [D]. So a ~95% upper bound on the MEAN run-p99 is about 197 ms — and *** 201 IS
     ESSENTIALLY THAT BOUND, arrived at by taking the worst observation. *** Choosing the worst
     observed is not pessimism piled on top of statistics here; it lands where the statistics land.
  2. *** THE COST ASYMMETRY IS STARK, AND IT ALL POINTS ONE WAY. *** Setting the p99 too HIGH
     costs a few slots of tensor width and slightly longer backstops — both cheap, and derivation
     4 already established that a generous timeout costs nothing because it only elapses on a
     request that has already failed. Setting it too LOW costs *** A MISSED ASSERTION REPORTED AS
     A PASS *** (derivation 2), which is a silent wrong answer and the most expensive outcome this
     design has. *** A BUDGET KEYED ON AN UNCERTAIN TAIL MUST FAIL TOWARD THE PESSIMISTIC SIDE. ***
  3. *** THE RUN-TO-RUN SPREAD IS BIGGER THAN THE CORRECTION IT IS BEING USED TO MAKE. *** The
     four p99s span 44 ms; the shift from the old 173 to the new figure is 10-28 ms. So *** THE
     DOMINANT UNCERTAINTY IS SAMPLING, NOT WIDTH *** — a caution when it was written, and now
     the measured answer: the interleaved experiment found no width effect, and found a
     within-width per-run p99 range of 136-562 ms.

  *** CONFIDENCE: LOW-TO-MODERATE, AND IT IS THE WEAKEST CONSTANT IN THIS SECTION. *** It is a
  1-in-100 statistic estimated from a handful of runs in ONE session. Treat 201 as a working bound
  that is fit for budgeting BECAUSE it fails safe, not as a well-determined property of the link.
  Until then, no figure derived from RTT_p99 should be quoted to three significant figures.

  *** WHAT WOULD FIRM IT UP — AND THE ANSWER CHANGED ONCE F-4 WAS MEASURED. *** It is NOT more
  runs of the kind already done: 16,200 round trips in one afternoon could not resolve 28 ms at
  the p99, because a per-run p99 is an extreme-value statistic and carries the variance to match
  (smallest detectable difference 83 ms read / 145 ms write; ~170 runs per arm, ~17 hours, to
  reach 10 ms of standard error). *** IT IS BREADTH: MANY SESSIONS, AT DIFFERENT TIMES OF DAY. ***
  The tunnel is shared infrastructure; one session measures one draw of what it was doing that
  afternoon, however many round trips that session contains. *** AND THERE IS A CHEAPER ROUTE
  THAN CHASING THE p99 AT ALL — see flag F-5, which proposes changing the metric rather than
  measuring this one harder. ***

  *** THE CAUSAL CLAIM WAS REFUSED HERE, THEN MEASURED, AND IT IS FALSE — SO THE CONSTANT IS
  RE-BASED. *** This block used to say that *"width widens the tail"* was NOT established, and
  named the experiment that would settle it: interleaved narrow/wide runs in one session. That
  experiment was run — 16,200 round trips, three widths, both arms (inputs above) — and:

      *** NO WIDTH EFFECT ON THE TAIL IS DETECTABLE. THE HIGHEST TAIL IS AT WIDTH 16 IN THE READ
      ARM AND WIDTH 123 IN THE WRITE ARM; THE TWO PER-RUN ESTIMATES HAVE OPPOSITE SIGNS AND
      SIMILAR MAGNITUDE. ALL SIX CELLS BRACKET BOTH 173 AND 201. ***

  *** WHAT THAT DOES AND DOES NOT DO TO THE CONSTANT: ***

    - *** IT DOES NOT MAKE 201 WRONG. *** It was chosen because an uncertain tail must fail
      pessimistic, and that reasoning is untouched — strengthened, if anything, by a within-width
      per-run p99 range of 136-562 ms.
    - *** IT DOES CHANGE WHAT 201 IS A MEASUREMENT OF. *** It is not "the p99 at full width". It
      is *** THE WORST RUN p99 SEEN IN ONE SESSION *** — and session-to-session variation alone
      is more than sufficient to produce the whole 173 -> 201 move. §12a implied a width
      provenance for one day; it never had one.
    - *** IT THEREFORE CHANGES THE REVISIT TRIGGER, WHICH IS THE PART THAT MATTERS OPERATIONALLY:
      REVISIT ON BREADTH, NOT ON WIDTH. *** More widths tell us nothing further. *** WHAT WOULD
      MOVE THIS NUMBER IS MANY SESSIONS, AT DIFFERENT TIMES OF DAY *** — the tunnel is shared
      infrastructure and one session cannot answer how bad the tail gets across days. A single
      session, however large, measures one draw of whatever the link was doing that afternoon.
    - *** AND IT RETIRES A WORRY RATHER THAN CREATING ONE: nothing here argues for capping slot
      width on timing grounds. *** See F-4.

*** THE [I] IS RETIRED — 2026-08-13, MEASURED, AND IT HOLDS. *** This block used to warn that
*"slot width is free up to FC03's 125 and FC16's 123"* was inferred from a 1..16-register sweep and
that no figure below might be quoted as measured beyond 16 registers. It has now been measured at
123: *** ~0.040 ms PER REGISTER ON WRITES AND NO TREND ON READS *** [M]. The inference held.

  *** BUT IT HELD FOR THE MEAN AND NOT FOR THE TAIL, AND THAT DISTINCTION IS THE WHOLE FINDING OF
  2026-08-13. *** "Free" now means, precisely:

      in the MEAN   :  0.040 x 123 = ~4.9 ms on a 75-78 ms round trip = ~6%  [D]
                       — against 100% for a SECOND round trip. *** THE CONCLUSION "ROUND TRIPS
                       COST, REGISTERS DO NOT" SURVIVES BY A FACTOR OF ABOUT SIXTEEN. ***
      in the TAIL   :  *** NO EFFECT DETECTABLE — MEASURED, 16,200 ROUND TRIPS, F-4. *** This
                       line read "NOT FREE, AND NOT QUANTIFIED" while a width effect was
                       suspected. It was looked for and not found: the highest tail lands at
                       width 16 in one arm and width 123 in the other. A 28 ms effect is EXCLUDED
                       at the p90 (where the experiment is powered) and merely NOT DETECTED at
                       the p99 (where it is not).

  So: keep sizing slots for what they need and keep preferring one wide read to two narrow ones —
  that guidance is unchanged, now has a number behind it, and no longer carries a tail caveat.
  What may NOT be said any more is the bare phrase *"marginal cost per register is zero"*: it is
  ~0.009-0.040 ms/register, which is negligible against a round trip and is not zero.

DERIVATION 1 — THE OBSERVABILITY FLOOR, IN SCANS  [D]
................................................................................

A poll is one round trip. There is no separate "poll rate" to choose: the coordinator reads one
slot per FC03 (X-A), serialised on one connection, so a K-slot tensor gives each slot a poll
period of `K x RTT`. For K=1:

    floor_typ  = RTT_typ / scan = 78    / 23.33 = 3.3 scans    [D]  DURATION — the typical gap
    floor_p90  = RTT_p90 / scan = 102.79/ 23.33 = 4.4 scans    [D]  DURATION — *** NEW 2026-08-13,
                                                                    and this is the honest
                                                                    "how far apart are polls"
                                                                    figure ***
    floor_p99  = RTT_p99 / scan = 201   / 23.33 = 8.6 scans    [D]  *** BOUND — THIS IS THE ONE A
                                                                    DECLARATION MUST CLEAR, AND IT
                                                                    DOES NOT MOVE TO THE p90 ***
    floor_best = 71 / 23.33                    = 3.0 scans      [D]  the FASTEST MEDIAN in the
                                                                     sweep — the irreducible
                                                                     floor for K=1. *** SAID
                                                                     PRECISELY: it is the best
                                                                     TYPICAL round trip, not the
                                                                     best single sample, which
                                                                     was not recorded. Treat 3
                                                                     scans as the floor a poller
                                                                     could SUSTAIN, not as the
                                                                     luckiest exchange possible.
    floor_tail = 2216 / 23.33                  = 95 scans       [D]  once per 2,000 polls

  *** A SAMPLED LEVEL MUST PERSIST FOR 9 SCANS TO BE CAUGHT AT THE p99, AND FOR 95 SCANS TO BE
  CAUGHT AGAINST THE WORST GAP EVER MEASURED. *** (ceil of floor_p99 and floor_tail.) Multiply
  both by K for a K-slot tensor.

  *** THE PERSISTENCE REQUIREMENT IS A BOUND AND KEEPS THE p99 — F-5 CHANGES NOTHING HERE, AND
  THE TEMPTATION TO "UPDATE" IT IS EXACTLY WHAT THE KIND RULE EXISTS TO STOP. *** At the p90 the
  same arithmetic gives 4.4 scans, which would let an author declare a 5-scan window — and
  *** 10% OF POLL GAPS WOULD THEN EXCEED THE DECLARED WINDOW, PRODUCING A MISSED ASSERTION
  REPORTED AS A PASS *** roughly one poll in ten rather than one in a hundred. The 4.4 figure is
  a DESCRIPTION of typical spacing; 8.6 is the REQUIREMENT. Same division, two different jobs.

  §12's CONCLUSION SURVIVES INTACT: a one-scan event is invisible to any sampler, because even a
  poller running flat out at the best round trip on record leaves a 3-scan hole. What does NOT
  survive is the SIZE of the margin — it is 3.3x typical and 8.6x at the p99, not the "about ten
  times" §12 argued from. *** ANY ARGUMENT THAT SPENT THAT MARGIN AS SLACK MUST BE RE-CHECKED
  RATHER THAN ASSUMED STILL SAFE. ***

  *** THE 2026-08-13 CORRECTION MOVED THIS FIGURE BACK TOWARD THE OLD CLAIM WITHOUT RESTORING IT,
  AND THAT IS WORTH SAYING PLAINLY: 8.6x IS NOT 10x. *** §12's "about ten times" is still wrong,
  the margin is still smaller than the design was written against, and nothing that was re-checked
  after 2026-08-13's first pass needs re-checking again in the other direction — the p99 moved
  UP, so every conclusion drawn from the smaller margin remains conservative.

  AND THE TAIL SAYS SOMETHING §12 COULD NOT: *** A SAMPLED ASSERTION IS NEVER GUARANTEED. ***
  0.05% of poll gaps are ~95 scans wide, so any sampled window under ~2.2 s of plant time carries
  a measured miss rate, and a miss presents as a silent wrong answer rather than an error. A
  LATCH does not have this property — it holds until cleared at test start (§12) and is immune to
  the gap entirely. That is an argument for §12's latched default that §12 did not have, and it
  is why "should SAMPLED assertions be admissible at all?" is flagged at the end of this section.

DERIVATION 2 — O11: THE MAXIMUM TENSOR WIDTH THE POLL BUDGET SUSTAINS  [D]
................................................................................

*** THE ANSWER'S SHAPE INVERTS: THE CAP IS NOT A NUMBER, IT IS A FUNCTION OF THE OBSERVABILITY
DECLARATIONS OF THE SLOTS ADMITTED — AND WHEN EVERY OBSERVATION IS LATCHED IT IS NOT BINDING AT
ALL. *** That is what a near-zero marginal cost per register (~0.040 ms [M], ~6% of a round trip
across a full-width slot) does to the question.

  THE COST MODEL, per wave index (one column of D26a's tensor), K slots in the wave set, slot
  width W registers, P poll rounds per test:

      writes  =  K x ceil(W / 123)     one FC16 per slot; ONE transaction while W <= 123.
                                       *** UNCHANGED BY F-1 — read-side change only ***
      commit  =  1                     all start bools in a single register write (X-A, D37)
      reads   =  P x ceil(K / R)       *** R = floor(125 / W) WHOLE SLOTS PER FC03 READ ***
                                       (F-1, adopted 2026-08-13: a read never SPLITS a slot, and
                                       may cover several whole ones — X-A)
      ------------------------------------------------------------------------
      round trips per index  =  K x ceil(W/123) + P x ceil(K/R) + 1        [D]

  *** THE READ TERM WAS `P x K` UNTIL F-1 — ONE FC03 PER SLOT. *** It is now `P x ceil(K/R)`, and
  since `R = floor(125/W)`, *** SLOT WIDTH HAS ENTERED THE ROUND-TRIP COUNT FOR THE FIRST TIME —
  IN THE DENOMINATOR. *** Registers still do not cost on the wire; what they now do is decide how
  many slots share a read. `W` is free per-register and expensive per-`R`-step.

  THE BINDING CONSTRAINT. A slot is polled once per read cycle, and a read cycle is
  `ceil(K/R) x RTT` — *** NOT `K x RTT`, WHICH IS WHAT IT WAS BEFORE F-1. *** A SAMPLED assertion
  whose true window is S scans is observed only if that cycle fits inside it:

      ceil(K/R) x RTT_p99  <=  S x scan
      *** K_max(S)  =  R x floor( S x 23.33 / 201 )       R = floor(125 / W) ***      [D]

      *** BOUND-SHAPED. IT KEEPS THE p99 AND MUST NOT BE RE-KEYED ON THE p90 (F-5's kind rule).
      *** An admission cap sized on the p90 admits roughly TWICE the slots — at the p90 the table
      below reads 2 / 4 / 11 / 22 / 45 against 1 / 2 / 5 / 11 / 23 — and the extra slots are
      admitted on the assumption that a poll cycle fits a window that *** 10% OF POLL CYCLES WOULD
      EXCEED ***. The failure is not a slow wave; it is a missed assertion reported as a pass,
      which is derivation 2's whole reason for existing.

  *** THE CAP IS NOW PROPORTIONAL TO SLOTS-PER-READ. *** The old table is the `R = 1` column, and
  it is the WORST case rather than the only one:

                        S (scans)   R=1 (W=123)   R=5 (W=25)   R=6 (W=20)   R=10 (W=12)
                        ---------   -----------   ----------   ----------   -----------
                             10           1            5            6            10
                             20           2           10           12            20
                             50           5           25           30            50
                            100          11           55           66           110
                            200          23          115          138           230

      *** READ THE FIRST COLUMN AS "WHAT A BADLY-SIZED MAP GETS" AND THE REST AS "WHAT SIZING THE
      SLOT TO ITS CONTENTS BUYS". *** At S = 10 scans — the row where the cap bit hardest and
      where the p99 correction could not help — a 20-register slot admits SIX slots where a
      padded 123-register slot admits ONE. *** THAT ROW IS THE POINT OF F-1: the cap that was
      binding at 1 was an artefact of the map, not of the link. ***

      (at RTT_typ = 78 ms the `R = 1` column reads 2 / 5 / 14 / 29 / 59 — which is why the p99 is
       the row that must be used: keyed on the median, a wave set admits four to six times more
       slots than the link can actually observe, and the failure is a MISSED ASSERTION REPORTED
       AS A PASS.)

      LATCHED assertions: the window is unbounded until cleared at test start, so `S` does not
      exist and *** THE POLL BUDGET IMPOSES NO WIDTH CAP AT ALL *** — before F-1 and after it.
      The cap then comes from somewhere else entirely — work memory (§16.13), the `%MW` mirror
      (X-A), wave duration (derivation 3) — and O11 stops being the constraint it was written as.

  SO O11's RE-DERIVED ANSWER, IN ONE LINE:

      *** max tensor width = floor(125 / W) x floor( S_min x scan / RTT_p99 ), where W is the
      wave set's slot size and S_min is the SHORTEST DECLARED SAMPLED OBSERVATION WINDOW among
      the slots admitted; UNBOUNDED by this constraint when every observation in the set is
      latched. ***

  *** F-1 CHANGED THIS ANSWER'S SHAPE A SECOND TIME, AND IT IS WORTH NAMING WHAT MOVED. *** The
  cap was already a FUNCTION rather than a number (of the admitted set's observability mode). It
  is now a function of TWO per-set quantities — `S_min` AND the slot size — and the second one is
  *** UNDER THE MAP DESIGNER'S CONTROL IN A WAY THE FIRST IS NOT. *** `S_min` is a property of
  what the tests need; `W` is a property of how the map was laid out. So the cheapest way to raise
  the cap is now, in order: LATCH the assertion (removes it entirely), then SIZE THE SLOT TO ITS
  CONTENTS (multiplies it by `R`), and only then anything about the link.

  WHAT THIS DOES AND DOES NOT CLOSE. It closes the arithmetic — the formula needs no rig. It
  does NOT close O11's empirical half, which is whether real submission sets declare sampled
  windows at all and how short they are; that stays deferred under D36, and the deferral's
  condition is now sharper rather than weaker (see the flags at the end of this section).

DERIVATION 3 — THE WIRE TERM §8's WAVE MODEL OMITS  [D]
................................................................................

§8 computes a wave as `download boundary + SUM over tensors ( inert reset + MAX test duration )`.
*** THAT MODEL HAS NO WIRE TERM, AND THE WIRE TERM IS NOT NEGLIGIBLE AT THE SHORT END. ***

  Worked at §8's own shape — K=6 slots, L=5 indices, P=2 poll rounds — and now as a function of
  slot size, because F-1 put slot size in the read term:

      round trips per index = K x ceil(W/123) + P x ceil(K/R) + 1        [D, derivation 2]

        W = 123, R = 1  :  6 + 12 + 1 = *** 19 ***      the pre-F-1 figure, unchanged
        W =  25, R = 5  :  6 +  4 + 1 = *** 11 ***      -42%
        W =  20, R = 6  :  6 +  2 + 1 = ***  9 ***      -53%

      *** DURATION-SHAPED — SO THIS IS THE ONE THAT MOVES TO THE p90 (F-5, 2026-08-13). *** The
      question is "what does a wave cost", the error is symmetric, and nothing gates on it.

      per wave  (W=123, 95 round trips) : *** 9.8 s at RTT_p90 ***   (19.1 s at the p99)
      per wave  (W= 25, 55 round trips) : *** 5.7 s at RTT_p90 ***   (11.1 s at the p99)
      per wave  (W= 20, 45 round trips) : *** 4.6 s at RTT_p90 ***   ( 9.0 s at the p99)

      *** THE p90 ROW IS THE PLANNING FIGURE AND THE p99 ROW IS RETAINED AS THE PESSIMISTIC
      ONE *** — both are quoted because a schedule wants the first and a worst-case wants the
      second, and neither is a bound on anything.
      *** THE WIRE TERM ROUGHLY HALVES, WHICH IS F-5 DOING WHAT IT WAS ADOPTED FOR: the old
      figure was not wrong, it was a 1-in-100 case being quoted as though it were the cost. ***

  *** WHAT THE WIN ACTUALLY IS, STATED THREE WAYS, BECAUSE "5x" IS TRUE OF ONLY THE FIRST: ***

      on the READ TERM ALONE       12 -> 4 or 2 round trips     *** 3x to 6x ***
      on ROUND TRIPS PER INDEX     19 -> 11 or 9                *** 1.7x to 2.1x ***
      on WAVE DURATION             74 s -> 66 s or 64 s         *** 11-13% ***

  *** THE `5x` IS A PROPERTY OF THE READ TERM, NOT OF THE WAVE. *** Three things dilute it, all of
  them real: the write term and the commit are untouched by F-1; `ceil(K/R)` is a step function, so
  6 slots at R=5 needs TWO reads and not 1.2; and a wave is mostly inert-plus-test time, into which
  the whole wire term disappears. *** QUOTE THE 11-13% WHEN TALKING ABOUT WAVES AND THE 3-6x WHEN
  TALKING ABOUT POLLING. *** The place the full factor really does land undiluted is O11's cap
  (derivation 2), which is keyed on the READ CYCLE alone — there, `R` multiplies directly.

  *** AND F-1 RELOCATES THE BOTTLENECK, WHICH IS THE MORE INTERESTING CONSEQUENCE: AFTER IT, THE
  WRITE SIDE IS THE DOMINANT ROUND-TRIP TERM. *** At W=20 the split is 6 writes / 2 reads /
  1 commit — *** TWO THIRDS OF THE WAVE'S ROUND TRIPS ARE NOW VECTOR WRITES. *** That is NOT an
  invitation to batch writes the same way: the write side carries A1's coherence guarantee, which
  was measured at 16 registers per FC16 with one request never split, and F-1 says nothing about
  it (X-A, "what F-1 does not change"). It is recorded because the next person looking for wire
  savings will look at the read term first, and the read term is no longer where the cost is.

  AGAINST §8's THREE ROWS (each of which is `5 x (inert + test)` plus a ~20 s download boundary),
  at RTT_p90, at the worst case W=123 / R=1 and at a sanely-sized W=20 / R=6:

                                          base      + wire (R=1)     + wire (R=6)
      inert  2 s, test  5 s :  35 + 20 =   55 s  ->  65 s  (+18%)  ->  60 s   (+8%)
      inert  5 s, test 10 s :  75 + 20 =   95 s  -> 105 s  (+10%)  -> 100 s   (+5%)
      inert 10 s, test 60 s : 350 + 20 =  370 s  -> 380 s   (+3%)  -> 375 s   (+1%)

  (the same rows at RTT_p99, retained as the pessimistic case: 74 / 114 / 389 at R=1, and
   64 / 104 / 379 at R=6)

  *** "A WAVE IS ORDER-OF-A-MINUTE" SURVIVES — 74 s is still order-of-a-minute — BUT §8's
  FASTEST ROW IS MORE THAN A THIRD OPTIMISTIC, AND §8's ROWS ARE THE ONES EVERY THROUGHPUT
  ARGUMENT IN THIS DOCUMENT IS BUILT ON. *** The term scales with K and with P, so it grows with
  exactly the packing §8 relies on for its 6x. It does not overturn the packed-versus-serial
  conclusion (the serial case pays the same per-test wire cost and pays it more times), but it
  must be IN the model rather than assumed away.

  *** AND THE WRITE HALF NEEDS NO SEPARATE WIDTH TERM, WHICH IT WOULD HAVE DONE UNDER THE OLD
  CONSTANT: *** RTT_p99 = 201 was measured AT 123 registers, so the ~4.9 ms full-width write cost
  is already inside it. Budgeting a per-register term on top of it would double-count.

DERIVATION 4 — THE 2,216 ms OUTLIER, AND THE TIMEOUT FLOOR IT SETS  [D]
................................................................................

*** IT IS NOT DROPPED, AND IT IS NOT AVERAGED IN. IT IS TREATED AS WHAT IT IS: A ROUTINE EVENT
AT A KNOWN RATE. *** One sample in 2,000 is 0.05%, and a wave issues round trips in the
hundreds, so the correct question is never "will it happen" but "how often, and what does it
cost when it does".

  HOW OFTEN, at derivation 3's worked wave (19 round trips x 5 indices = 95 per wave):

      P(at least one outlier in a wave) = 1 - (1 - 0.0005)^95 = *** 4.6%, about one wave in 22 ***

  *** AND F-5 REPLACES THE WEAKEST STEP IN THAT ARITHMETIC WITH A MEASURED RATE — 2026-08-13. ***
  The 0.05% above is *one sample in 2,000 being the LARGEST*, which is not a rate at all: it
  bounds P(exceeding 2,216 ms) at roughly 1/2000 and measures nothing. `exceed_250` IS a rate,
  measured on 57 events, and it lets the same idiom be applied to a threshold that actually has
  data behind it:

      expected over-250 ms exchanges per wave  = 95 x 0.00352 = *** 0.33 ***                [D]
      P(at least one)  = 1 - (1 - 0.00352)^95  = *** ~28%, about one wave in 3.5 ***         [D]
      at W=20 (45 round trips)                 = 0.16 expected, ~15%, about one wave in 7    [D]

  *** THE TWO FIGURES ARE NOT IN COMPETITION — THEY DESCRIBE DIFFERENT PARTS OF THE SAME TAIL. ***
  About one wave in 3.5 contains a round trip over 250 ms; about one in 22 contains one over
  2,216 ms. The first is measured, the second is a single observation. *** QUOTE THE FIRST AS "ABOUT
  ONE IN THREE OR FOUR WAVES", NOT AS 28.5% *** — it inherits the exceedance rate's +/- 26%.

  WHAT IT COSTS IN DURATION: +2.2 s on a ~74 s wave = +3%. *** NEGLIGIBLE, AND THAT IS THE WHOLE
  OF ITS THROUGHPUT SIGNIFICANCE. *** It must not be added to RTT_p99, and no budget above
  includes it.

  *** UNAFFECTED BY THE 2026-08-13 p99 CORRECTION, AND DELIBERATELY SO. *** `RTT_max` is a
  separate measurement from a separate part of the distribution; raising the p99 from 173 to 201
  does not move it, does not change the 0.05% rate, and *** DOES NOT CHANGE THE 3,000 ms TIMEOUT
  FLOOR, which is keyed on RTT_max and never on the p99. *** Only the middle term of the backstop
  below moves.

  WHAT IT COSTS IF A TIMEOUT IS SET BELOW IT: *** EVERYTHING. *** A per-request timeout under
  2,216 ms converts a measured, ordinary tail event into a transport failure — at ~1 in 2,000
  requests, which is ~1 in 22 waves, arriving as an intermittent unattributable red.

      *** RULE [D]: THE CLIENT'S PER-REQUEST TIMEOUT IS >= 3,000 ms. *** RTT_max x ~1.35. There
      is no throughput cost to a generous timeout — it only ever elapses on a request that has
      already failed — and there is a large diagnostic cost to a tight one.

      *** RULE [D]: X-B's WALL-CLOCK BACKSTOP IS COMPUTED, NOT GUESSED: ***

          backstop = (declared max duration in scans x 23.33 ms)
                   + (expected round trips for the test x RTT_p99)      <- 201 ms. *** STAYS ***
                   + one RTT_max allowance (2,216 ms)                   <- *** STAYS ***

      *** 🔴 THE BACKSTOP IS THE SHARPEST CASE OF F-5's KIND RULE, AND IT DELIBERATELY DID NOT
      MOVE. *** It is BOUND-shaped: a shorter allowance produces MORE spurious TIMED-OUT, not more
      safety. Substituting RTT_p90 for the middle term would shrink the allowance by half while
      *** 10% OF ROUND TRIPS EXCEED THAT FIGURE BY CONSTRUCTION *** — on a test issuing 19 round
      trips, roughly two would be expected to blow the per-trip assumption every run. The
      2,216 ms outlier term is untouched for the same reason and must not be trimmed.

      A backstop computed on RTT_typ, or without the outlier allowance, will fire on a healthy
      test roughly once every 22 waves and report TIMED-OUT — the outcome X-B invented precisely
      so that "the condition never occurred" would be distinguishable from a real failure. A
      spurious TIMED-OUT is worse than a spurious FAILED, because it is believed.

  AND THE ONE THING THAT MUST NOT BE BUILT: *** A RETRY THAT IS INDISTINGUISHABLE FROM A LOST
  REQUEST. *** If the client retries after a timeout, the original request may still land. On a
  write that is a duplicated vector application; on the START-BOOL COMMIT it is a second T=0.
  The commit transaction (X-A) must therefore be idempotent or non-retried — decided at build
  time, recorded here because the outlier is what makes it a live case rather than a theoretical
  one.

DERIVATION 5 — X-D's COMPRESSION CONSTANTS  [D]
................................................................................

X-D's `comp_max` terms carried `~10 ms` for the scan and `~100 ms` for the poll. Both are
replaced, and *** THE TIMER TERM — THE ONE X-D SAYS OFTEN BINDS FIRST — IS HALVED. ***

    scan_period   ~10 ms   ->   23.33 ms                        [M]  unchanged 2026-08-13
    poll_period  ~100 ms   ->   K x RTT_p99, >= 201 ms at K=1    [D, derivation 2]
                                *** BOUND-SHAPED — KEEPS THE p99 (F-5's kind rule). *** `comp_max`
                                is a CEILING on compression; sizing it with the p90 would permit a
                                compression at which 10% of poll cycles no longer resolve the
                                behaviour, and the symptom is a green that was never sampled.
    timer floor  k x scan, k~5:  50 ms  ->  *** 116.7 ms ***     [D]  *** UNCHANGED — it depends
                                only on the scan, which did not move ***

  WORKED, on X-D's own example — a 500 ms preset:

      comp_max(timer) = 500 / 116.7 = *** 4.3x ***   was 500 / 50 = 10x                  [D]

  *** AND THE TERM THIS SECTION SAYS BINDS FIRST IS THE ONE THE 2026-08-13 CORRECTION DID NOT
  TOUCH. *** The timer bound is a function of the SCAN, and the scan is the best-determined
  constant in §12a. So the practical compression ceiling on a typical block is unmoved; what
  tightened by 14% is the SAMPLED-assertion term, which is the term latching removes entirely.

  So a block's shortest dwell preset now caps compression at less than half what X-D's arithmetic

  AND THE LATCHED-VERSUS-SAMPLED SPREAD X-D CALLS A THROUGHPUT LEVER:

      201 / 23.33 = *** 8.6x, not 10x ***  (3.3x at RTT_typ)                             [D]
                                           (was 7.4x at RTT_p99 = 173)

  Still a real lever, still worth the latch, and somewhat smaller than advertised — the
  2026-08-13 correction moved it back toward X-D's original 10x without reaching it.

    50 tags read individually  : 50 x 102.79 ms = *** 5.1 s at RTT_p90 ***                 [D]

    a scan-counter poll        : 1 round trip — *** 102.79 ms at RTT_p90 *** (201 at the p99)

    widening a read by ~110 registers :  ~1.0 ms  [M, interleaved — the better-controlled figure]

    one additional round trip         :  *** 102.79 ms at RTT_p90 *** (78 median, 201 p99)  [D]

WHAT THIS RE-DERIVATION CANNOT DECIDE — THREE FLAGS FOR THE OWNER
................................................................................

*** EACH OF THESE IS A DESIGN CHANGE THAT THE NEW ARITHMETIC MAKES ATTRACTIVE. NONE OF THEM IS
APPLIED ANYWHERE IN THIS DOCUMENT. *** They are recorded here so the arithmetic that suggests
them is not lost, and so that nobody applies one by reading the numbers and drawing the obvious
conclusion without the ruling.

  F-1. *** ADOPTED BY THE OWNER, 2026-08-13. X-A's RULE IS NOW "A READ NEVER SPLITS A SLOT". ***
       The question was: should one FC03 read be allowed to cover several WHOLE slots? It is, and
       the spec half is implemented — X-A carries the new rule, the coherence argument that
       motivates it, and *** THE EXPRESSION MECHANISM: reads are addressed as `read(first_slot,
       slot_count)` so that a split read is UNEXPRESSIBLE rather than merely rejected *** (the
       `MirrorClient` precedent — an unaddressable operation cannot be reached by a later change,
       where a skippable validator can).

       THE ORIGINAL REASONING, KEPT: with registers all but free and round trips scarce, packing
       `R = floor(125 / W)` whole slots into one read divides the READ cost by `R`. The coherence
       argument survives the change untouched, because the hazard was never "touching two slots"
       — it was "touching half of one", and a read of several WHOLE slots is still one
       transaction that catches no slot half-published.

       *** WHAT IT ACTUALLY BOUGHT, NOW THAT THE ARITHMETIC IS RE-RUN (derivations 2 and 3):
       3-6x on the read term, 1.7-2.1x on round trips per index, 11-13% on wave duration, and —
       the one place the factor lands undiluted — a straight `x R` on O11's cap. *** The `5x` is
       true of the read term only; quote the right one for the question being asked.

       *** AND IT MOVED A COST RATHER THAN ONLY REMOVING ONE: padding a slot is no longer free,
       because padding reduces `R`. *** X-A's "the small slots pay nothing for the padding" was
       corrected the same day. Size a slot to its contents.

  F-6. *** NEW, RAISED BY F-1's ADOPTION AND NOT DECIDED: SHOULD WAVE-SET ADMISSION GROUP BY SLOT
       SIZE? *** Slots are FIXED-SIZE within a wave set, sized to the largest member (X-A). Before
       F-1 that cost nothing. After it, *** ONE WIDE SLOT COLLAPSES `R` FOR THE WHOLE SET *** — a
       single 123-register slot admitted alongside twenty 20-register slots takes `R` from 6 to 1
       and sextuples the read cost of every one of them, and cuts O11's cap by the same factor.
       So slot-size HOMOGENEITY has become worth something, and DB-13's colouring currently knows
       nothing about it. *** THE CHEAP VERSION IS A PREFERENCE, NOT A CONSTRAINT: prefer to place
       same-sized slots together when the conflict graph leaves a choice. *** The expensive
       version — a size dimension in the colouring, or splitting a set on size — is a real change
       to DB-13 and interacts with F-2. Flagged, not decided; the arithmetic for judging it is
       derivation 2's `K_max = R x floor(S_min x scan / RTT_p99)`.

  F-2. *** DB-13's "MAX TENSOR WIDTH AS AN EXPLICIT INPUT" (D36's condition) IS THE WRONG
       SHAPE. *** Derivation 2 makes the cap a function of the admitted set's own observability
       declarations, not a scalar constant. Keeping it a scalar means picking one number for
       every wave set, which must be the worst case, which throws away most of the width the
       link can actually sustain. D36's condition — no default that could be mistaken for a
       measurement — is satisfiable either way; the shape of the input is the question.

  F-3. *** SHOULD SAMPLED (UNLATCHED) ASSERTIONS BE ADMISSIBLE AT ALL? *** Derivation 1 measures
       a 0.05% chance that any given poll gap is ~95 scans wide, and a sampled assertion that
       falls in one is a silent wrong answer rather than an error. §12 already defaults coil-
       shaped signals to latched; making it mandatory for every assertion would close the hole
       entirely, at the cost of the copy-layer memory §12 prices at 32x for scan-stamps. That is
       a correctness-versus-cost trade, which is not the arithmetic's to make.
       *** STRENGTHENED 2026-08-13: latching also removes the ONE term the p99 correction
       tightened *** — the sampled-assertion term in X-D and the whole of O11's cap. An
       all-latched wave set is INDIFFERENT to whether RTT_p99 is 173, 201 or 250, which is a
       property worth having while the constant is this uncertain.

  F-4. *** ANSWERED — MEASURED, AND IT COMES BACK AGAINST THE HYPOTHESIS. NO OWNER DECISION IS
       NEEDED. *** Kept in the flag list rather than deleted, because the reasoning that raised
       it is the reasoning that got it measured instead of assumed.

       THE QUESTION WAS TWO QUESTIONS. *** ONLY THE FIRST IS ANSWERED, AND THAT IS ENOUGH TO
       CLOSE THE SECOND: ***

         (i)  IS THE TAIL WIDTH-SENSITIVE? *** NO EFFECT IS DETECTABLE. *** 16,200 round trips,
              interleaved 16/64/123, both arms. The highest tail sits at width 16 in the read arm
              and width 123 in the write arm; per-run estimates have OPPOSITE SIGNS and similar
              magnitude (-47.5 / +51.3 ms), both CIs spanning zero; all six pooled cells fall in
              152-195 ms and bracket both 173 and 201. Inputs block has the table.
         (ii) SHOULD SLOT WIDTH THEREFORE BE CAPPED BELOW THE FC03 LIMIT? *** NOTHING HERE
              ARGUES FOR CAPPING SLOT WIDTH ON TIMING GROUNDS. *** The premise of the question
              was the effect in (i), and it was not found. Derivation 6's guidance — lay the map
              out for the widest legal read — stands without qualification. *** ANY FUTURE CASE
              FOR A WIDTH CAP MUST COME FROM SOMEWHERE OTHER THAN TIMING *** (the 125-register
              read limit, the mirror, work memory) — those are unaffected either way.

       *** THE LIMITS OF THE ANSWER, PRESERVED DELIBERATELY, BECAUSE "NOT DETECTED" IS NOT
       "ABSENT" AND THIS PROJECT HAS BEEN BITTEN BY READING ONE AS THE OTHER: ***
         - *** THE EXPERIMENT IS NOT POWERED FOR 28 ms AT THE p99 *** — smallest detectable
           difference 83 ms (read), 145 ms (write). A per-run p99 is itself an extreme-value
           statistic. This is NOT a strong null at the p99 and is not offered as one.
         - *** THE CONCLUSION RESTS ON THE p90, WHICH IS ADEQUATELY POWERED *** — 13 ms and
           21 ms detectable, measured at +0.5 and +3.4 ms. A 28 ms width effect at p90 is
           EXCLUDED in both arms. That is the load-bearing half of the result.
         - *** AND ONE FACT NEEDS NO POWER ARGUMENT: within a SINGLE fixed width, in ONE session,
           per-run p99 ranged 136-371 ms (read w16) and 136-562 ms (write w123). *** The spread
           within one width dwarfs the 28 ms anyone was trying to attribute to width.
         - The body DOES move with width, reproducibly and tinily: median +1.0 ms from 16 to 123
           registers, *** the same in both arms *** — consistent with derivation 6 and about four
           times SMALLER than the across-session per-register estimate it refines.

       *** WHAT IT CHANGED ELSEWHERE: the provenance of `RTT_p99`, not its value *** — 201 is a
       SESSION figure, not a width figure, and its revisit trigger is BREADTH. Constants block.

  F-5. *** ADOPTED BY THE OWNER, 2026-08-13 — SPECIFY THE TAIL AS p90 PLUS AN EXPLICIT EXCEEDANCE
       RATE, INSTEAD OF A p99 POINT ESTIMATE. *** The form is now the design's; the two constants
       it needs have not yet been extracted, so the transition is staged and its state is recorded
       in the constants block above. What follows is the reasoning as it was put, kept because in
       six months "why is the tail two numbers?" is exactly the question this answers.

       THE FORM PROPOSED:  a p90 constant, plus a stated *** FRACTION OF ROUND TRIPS OVER A NAMED
       THRESHOLD *** (the suggested threshold is 250 ms, which sits above all six of F-4's pooled
       cells) — in place of the single `RTT_p99` figure every budget currently multiplies by.

       *** THE ARGUMENT FOR IT, AND IT IS A GOOD ONE: A p99 POINT ESTIMATE IS EXACTLY WHAT
       DEFEATED A 16,200-ROUND-TRIP EXPERIMENT. *** Measuring it harder is expensive and slow
       (F-4: ~170 runs per arm, ~17 hours, for 10 ms of standard error), while the p90 from the
       same data was precise to +/- 1%.

       🔴 *** THE MECHANISM ORIGINALLY GIVEN HERE WAS WRONG, AND THE CORRECTED ONE IS IN THE
       CONSTANTS BLOCK. *** This entry said an exceedance rate is better because it *"pools across
       runs without inheriting an order statistic's variance"*. *** THE PROBLEM WITH THE p99 WAS
       NEVER THAT IT IS AN ORDER STATISTIC — IT IS THAT IT IS AN ORDER STATISTIC IN THE SPARSE
       TAIL, WHERE THERE IS ALMOST NO DATA. *** The p90 is equally an order statistic and is the
       most precise figure in this section. *** DENSITY AROUND THE QUANTILE GOVERNS THE VARIANCE,
       NOT QUANTILE-NESS *** — and measured against that, the exceedance rate is the LEAST precise
       of the pair (+/- 26% on 57 events, against the p90's +/- 1.05%). It earns its place not by
       precision but because *** IT IS THE ONLY ONE OF THE TWO THAT DESCRIBES THE OUTLIER REGIME
       AT ALL. *** Recorded because the wrong version is plausible and reached a right answer.

       *** AND IT IS NOT A NEW IDIOM — IT IS DERIVATION 4's IDIOM, GENERALISED. *** Derivation 4
       already treats the 2,216 ms outlier exactly this way: a rate (0.05%), multiplied by the
       round trips in a wave, giving an expected count and an explicit exposure (4.6% of waves).
       That treatment is the most defensible arithmetic in this section. F-5 proposes applying it
       to the whole tail rather than only to the single worst sample.

       *** WHAT IT WOULD CHANGE, STATED SO THE COST IS VISIBLE: ***
         - EVERY budget expression in §12a: derivation 1's floor, derivation 2's `K_max`,
           derivation 3's wire term, X-B's backstop, X-D's sampled term. Each becomes a p90-keyed
           figure PLUS a stated expected number of over-threshold exchanges per wave.
         - O11's cap formula, which other lanes consume, gains a second input.
         - Consumers move from ONE constant to TWO. *** THAT IS THE REAL COST *** — a single
           number is easy to hold and easy to key a budget on, and admission control, the
           backstop and the copy layer would all have to carry the pair.
         - The budgets get WEAKER as bounds and HONESTER as statements: a p90-keyed budget is
           wrong ~10% of the time BY CONSTRUCTION and says so, where a p99-keyed one is wrong ~1%
           of the time by assertion, on a p99 nobody can pin down. *** WHICH OF THOSE IS
           PREFERABLE IS A JUDGEMENT ABOUT HOW THE RESULTS WILL BE READ, NOT ABOUT THE DATA. ***
         - It would also make the "how bad across days" question (the constants block's BREADTH
           trigger) cheap to answer, because an exceedance rate accumulates across sessions.

       *** WHAT IS MISSING BEFORE IT COULD BE ADOPTED: the pooled p90 value and the exceedance
       count at the chosen threshold are not recorded here *** — F-4 reports p90 DIFFERENCES
       (+0.5 / +3.4 ms) and not p90 LEVELS. So this proposal is set out as a shape and a cost,
       with no numbers attached, deliberately. Adopting it starts with producing those two
       figures from data that already exists.

       *** AND ADOPTION DID NOT PRODUCE THEM, SO THEY ARE STILL MISSING — SEE THE STAGED
       TRANSITION IN THE CONSTANTS BLOCK. *** The ruling changed the FORM the design commits to;
       it did not conjure the two measurements, and this document will not carry an invented p90
       to look finished. Until they are extracted, budgets continue to key on `RTT_p99 = 201`,
       and that is stated at the point of use rather than left to be discovered.

HOW THE FLAGS INTERACT — CHECKED 2026-08-13 AFTER F-1's ADOPTION
................................................................................

*** ASKED BECAUSE AN ADOPTED FLAG CAN QUIETLY CHANGE WHAT A PENDING ONE IS WORTH, AND THE OWNER
SHOULD KNOW THAT BEFORE RULING ON THE REST. ***

  *** F-1 x F-2 (DB-13's max-width input) — F-1 MAKES F-2 STRONGER, AND MORE URGENT. *** F-2
  already argued that an explicit SCALAR max-tensor-width input is the wrong shape because the cap
  is per-wave-set. After F-1 the cap depends on TWO per-set quantities — `S_min` and the slot size
  — via `K_max = R x floor(S_min x scan / RTT_p99)`. A single scalar must now be the worst case
  over both, which is further from adequate than it was this morning. *** AND F-6 IS THE SAME
  CONVERSATION: *** if admission gains any notion of slot size, F-2's input shape is decided by
  that work rather than separately. *** RECOMMEND RULING F-2 AND F-6 TOGETHER. ***

  *** F-1 x F-3 (should SAMPLED assertions be admissible at all) — F-1 WEAKENS THE THROUGHPUT
  ARGUMENT FOR MANDATORY LATCHING AND LEAVES THE CORRECTNESS ARGUMENT EXACTLY WHERE IT WAS. ***
  Sampled assertions are now `R` times more affordable: an `S = 10` set that admitted ONE slot
  admits SIX at a 20-register slot size. So "latch everything, the cap is brutal otherwise" is a
  materially weaker case than it was. *** BUT F-3's REAL ARGUMENT WAS NEVER THROUGHPUT — it is
  that 0.05% of poll gaps are ~95 scans wide, and a sampled assertion falling in one is a silent
  wrong answer. *** That is a property of the outlier, not of the read cycle, and F-1 does not
  touch it. *** SO: F-3 IS NOW A NARROWER, PURELY CORRECTNESS-SHAPED DECISION — WHICH ARGUABLY
  MAKES IT EASIER TO RULE ON, NOT HARDER. ***

  *** F-1 x F-5 (p90 + exceedance rate) — INDEPENDENT, AND THEY COMPOSE CLEANLY. *** F-1 changes
  HOW MANY round trips a budget covers; F-5 changes HOW THE COST OF ONE is expressed. Neither
  blocks or complicates the other. One small favourable interaction: F-1 cuts the round trips per
  wave (95 -> 45 at W=20), and F-5's exceedance arithmetic multiplies a rate BY that count — so
  adopting F-1 first makes F-5's exposure figures smaller and its case no harder to make.

  *** F-1 x F-4 (answered) — F-4 IS WHAT MAKES F-1 SAFE, AND THIS IS WORTH STATING BECAUSE THE
  ORDER LOOKS ACCIDENTAL AND IS NOT. *** F-1's whole win is issuing FEWER, WIDER reads. Had F-4
  come back the other way — a tail that grows with width — then a 125-register read would have
  cost tail latency, every budget here is p99-keyed, and *** F-1's saving would have been partly
  paid back in exactly the currency the budgets are denominated in. *** F-4 found no such effect,
  at either width, in either arm. So F-1 banks its round-trip saving without a tail penalty, and
  the two flags should be read as a pair rather than as one answered and one adopted.

  *** NO CONFLICTS FOUND. *** F-1 does not contradict any pending flag, and does not reopen any
  ruling recorded in this document.

SHAPE OR MAGNITUDE? — WHAT THE 2026-08-13 p99 CORRECTION DID AND DID NOT DO
................................................................................

*** WRITTEN FOR THE LANES BUILDING AGAINST THIS SECTION, BECAUSE "THE CONSTANT MOVED" AND "THE
CONCLUSION MOVED" NEED DIFFERENT RESPONSES — ONE IS A RECOMPILE, THE OTHER IS A REDESIGN. ***

  *** NO CONCLUSION IN §12a CHANGED SHAPE. EVERY ONE OF THEM IS THE SAME STATEMENT WITH A
  DIFFERENT NUMBER IN IT. *** Specifically, all of these survive untouched:

    - a one-scan event is invisible to any sampler, and no polling rate recovers it (D1)
    - round trips cost, registers do not — now by a measured ~16x rather than an assumed
      infinity (D6, and the constants block)
    - O11's cap is a FUNCTION of the admitted set's observability mode, and does not bind at all
      on an all-latched set (D2)
    - D29 does not invert; "width" means slots (D2)
    - a wave is order-of-a-minute (D3)
    - the outlier is negligible to throughput and decisive for timeouts (D4)
    - use comp_min, never comp_max; the timer term binds first (D5)

  *** ONE CLAIM DID CHANGE SHAPE, AND IT IS A CLAIM RATHER THAN A DECISION: "MARGINAL COST PER
  REGISTER IS ZERO" IS NOW FALSE AS STATED. *** It is ~0.009-0.040 ms/register — negligible,
  measured, and not zero. Anywhere that phrase is used as a premise rather than as shorthand, it
  must be replaced by the figures in the constants block.

  *** AND ONE FURTHER ROUND OF THIS, RESOLVED WITHIN THE SAME DAY AND WORTH READING AS A UNIT
  (F-4): the tail was BRIEFLY thought to be width-sensitive, and it is not. *** The sequence went:
  p99 raised 173 -> 201 on a full-width re-measurement; the causal claim REFUSED at the time as
  unestablished; measured with 16,200 interleaved round trips; *** NO WIDTH EFFECT DETECTABLE. ***
  Net effect on this table: *** NOTHING IN IT MOVES A SECOND TIME. *** `RTT_p99` stays 201, every
  derived figure above stays as listed, and what changed is the constant's PROVENANCE (a session
  figure, not a width figure) and its REVISIT TRIGGER (breadth, not width). *** NO LANE HAS TO ACT
  ON F-4's ANSWER *** — an unchanged constant needs no propagation, which is the whole reason the

      configuration exists but not whether the guard held for it, which is the only thing a
      later fix wave needs.

      WORKED FAILURE, for anyone tempted to leave this: `SelectiveDeleteDownload` offers
      `AcceptAll | DeleteSelected` and NO NoAction. Rule 3 leaves it unhandled. If it behaves

  O10. *** CLOSED 2026-08-12 — AND STRUCTURALLY, NOT BY DEPRIORITISATION. *** The owner ruled
      it unimportant and said it would surface as we run. It is stronger than that: *** D32

................................................................................
16.1  X-A  *** VECTOR APPLICATION IS NOT ATOMIC, AND A TORN WRITE IS UNDETECTABLE ***
................................................................................

Nothing in this design makes a vector's arrival at the PLC atomic. Modbus
write-multiple-registers carries at most 123 registers per transaction, so ANY tensor whose
combined vector data exceeds that is written across MULTIPLE transactions — and a link drop, a
retry, or a slow scan between them leaves the program running a HALF-APPLIED VECTOR. The block
sees a coherent-looking set of inputs that was never a vector anybody wrote, produces a result,
and that result is reported as a test outcome.

WHY IT IS INVISIBLE: every individual write SUCCEEDED. There is no partial-write error to
catch — the failure is at a level Modbus does not model.

*** AND IT IS A THIRD BOUND ON TENSOR WIDTH, alongside conflict-freedom and poll bandwidth
(D29): a tensor is also bounded by what can be applied atomically. ***

*** RESOLVED 2026-08-12 — AND THE MECHANISM WAS ALREADY IN THE DESIGN. NO STAGING REGION, NO
SEQUENCE NUMBER, NO NEW PLC-SIDE LOGIC. ***

The proposed fix was stage-then-commit with a sequence word. Unnecessary, because of D26a:
*** THE VECTOR DATA DOES NOT NEED TO BE ATOMIC AT ALL — NOTHING IS RUNNING WHILE IT IS
WRITTEN. *** The rig is inert during the write. What must be atomic is the START.

And D37's start bools already are that: ONE BIT PER SLOT, so every start bool in the wave fits
in a single register write.

    inert established, VERIFIED (D33)
      -> write modbusTensor(i) across AS MANY TRANSACTIONS AS IT TAKES   (nothing is running)
      -> *** ONE TRANSACTION RAISING ALL START BOOLS *** — the commit, and D37's T=0
      -> observe

A torn write in the data phase therefore leaves the start bools unraised, *** so nothing runs
and it is a detectable non-event rather than a plausible wrong answer *** — the exact property
wanted, obtained from a mechanism that exists for another reason.

*** THE PARTITION REQUIREMENT SURVIVES ONLY ON THE READ SIDE. *** Polling happens DURING a
test, so a read spanning transactions can catch a publish half-done. Per-SLOT coherence is
sufficient — slots are independent by construction (D9) — so the rule is:

    *** EACH SLOT'S RESULT REGION MUST FIT IN ONE FC03 READ (125 REGISTERS), AND *** A READ NEVER
    *** SPLITS *** A SLOT. *** Refused at MAP-DERIVATION time if a slot exceeds 125 — a
    design-time error, never a runtime one.

*** THIS RULE READ "A READ NEVER STRADDLES TWO SLOTS" UNTIL 2026-08-13 (F-1, ADOPTED BY THE
OWNER). *** The change is deliberate and it is a RELAXATION IN ONE DIRECTION ONLY: a read may now
cover SEVERAL WHOLE SLOTS; it may still never return PART of one.

*** THE COHERENCE ARGUMENT IS UNCHANGED, AND IT IS WHY THE NEW WORDING IS SAFE — READ THIS BEFORE
"OPTIMISING" THE RULE ANY FURTHER. *** What must never happen is *** A READ THAT RETURNS PART OF A
SLOT ***, because polling runs DURING a test and a partial read can catch that slot's publish
half-done, yielding a coherent-looking result nobody ever published. A read covering three ENTIRE
slots does not do that: it is still ONE transaction, and each slot inside it is either wholly
before or wholly after any publish. *** THE FORBIDDEN THING WAS NEVER "TOUCHING TWO SLOTS" — IT
WAS "TOUCHING HALF OF ONE". *** The old wording forbade a superset of the actual hazard, and that
surplus was costing round trips, which §12a establishes are the scarce resource.

................................................................................
*** HOW A READ IS EXPRESSED — AND THIS IS THE MECHANISM, NOT A STYLE NOTE ***
................................................................................

*** A SPLIT READ MUST BE UNEXPRESSIBLE, NOT MERELY REJECTED. *** The precedent is `MirrorClient`,
built so that an out-of-region write is *** UNADDRESSABLE *** rather than caught by a check — and
the difference matters because a check is something a later change can skip, disable, or fail to
call, whereas a thing that cannot be written down stays unwritten.

    *** READS ARE ADDRESSED IN SLOT UNITS, NEVER IN REGISTER UNITS. *** The read primitive names
    a FIRST SLOT and a COUNT OF SLOTS:

        read(first_slot, slot_count)        slot_count >= 1

    and the register range is DERIVED, never supplied:

        start  = mirror_base + first_slot x slot_size
        length = slot_count  x slot_size          (must be <= 125, checked at map derivation)

*** THERE IS NO PARAMETER IN WHICH A PARTIAL SLOT COULD BE NAMED. *** Not "a register offset that
happens to be validated" — no register offset at all. A caller wanting half a slot has nothing to
type. That is the whole of the enforcement, and it is why this clause specifies the SHAPE OF THE
CALL rather than a constraint on its arguments.

*** DO NOT IMPLEMENT THIS AS A VALIDATOR OVER A REGISTER-RANGE READ. *** A `read(start, length)`
guarded by `assert(start % slot_size == 0)` satisfies the letter of the rule and abandons its
mechanism: the unsafe call still exists, still compiles, and is one refactor from being reached.
If a validator is the only thing standing between the client and a split read, the design has
already lost the property it is trying to hold.

Slots are FIXED-SIZE, sized to the largest slot in the wave set, so a client's bounds check is
`base + index x slot_size` (DB-6 point 3 becomes arithmetic rather than a check).

*** AND UNDER F-1, SIZING THEM IS NO LONGER FREE — THIS PARAGRAPH IS CORRECTED, 2026-08-13. *** It
used to say the small slots "pay nothing for the padding", which was true when every slot cost one
FC03 regardless. It is now false: *** PADDING A SLOT REDUCES HOW MANY SLOTS FIT IN A READ, AND
THAT IS PAID IN ROUND TRIPS. ***

    slots per read      R = floor(125 / slot_size)      [D]

    slot_size  25  ->  R = 5        slot_size  62  ->  R = 2
    slot_size  20  ->  R = 6        slot_size 123  ->  R = 1
    slot_size  12  ->  R = 10

*** SO THE TWO COSTS NOW PULL IN OPPOSITE DIRECTIONS, AND THEY ARE NOT THE SAME SIZE: *** widening
a slot costs ~0.009-0.040 ms per register on the wire (negligible, §12a), but widening it far
enough to drop `R` costs a WHOLE ROUND TRIP per read per slot-group — 78 ms typical, 201 ms at the
p99. *** SIZE A SLOT TO WHAT ITS CONTENTS NEED. Padding to the FC03 limit "because width is free"
is now the expensive mistake, not the cheap one. ***

    *** AND THE FIXED-SIZE RULE ACQUIRES A REAL COST THAT IT DID NOT HAVE: one wide slot in a wave
    set forces EVERY slot in that set to its width, collapsing `R` for all of them. *** A single
    123-register slot admitted alongside twenty 20-register slots takes `R` from 6 to 1 and
    sextuples the read cost of the entire wave. Flagged as F-6 — whether admission should group by
    slot size — and NOT decided here.

*** WHAT F-1 DOES NOT CHANGE, STATED EXPLICITLY SO IT IS NOT READ AS A LICENCE TO WIDEN ANYTHING
ELSE: ***

  - *** THE WRITE SIDE IS UNTOUCHED. *** F-1 is a READ-side change. Vector data is still written
    "across as many transactions as it takes" while nothing is running, and the commit is still
    ONE transaction raising all start bools. No write is batched differently because of this.
  - *** A1's COHERENCE GUARANTEE IS UNTOUCHED, AND IT IS NARROWER THAN THE DESIGN ALREADY USES. ***
    "No tear observed in 3,340 writes" was measured at *** 16 REGISTERS PER FC16, one request never
    split ***. That evidence does not stretch to a full-width write merely because F-1 made reads
    cheaper — F-1 says nothing about writes at all. The gap between A1's 16 registers and the
    width the design actually uses is a PRE-EXISTING item, neither widened nor closed here.
  - *** THE PER-SLOT COHERENCE REQUIREMENT IS UNTOUCHED *** — it is the thing the new wording
    exists to preserve, not a cost the relaxation pays.
  - *** THE 125-REGISTER READ CEILING IS UNTOUCHED. *** `slot_count x slot_size <= 125` still
    binds, still at map-derivation time.

TWO THINGS THAT FALL OUT AND MUST BE BUILT FOR:

  1. *** `MB_SERVER`'s POSITION IN THE SCAN IS LOAD-BEARING. *** An atomic Modbus write still
     lands DURING the `MB_SERVER` call, so blocks executing before that call in the same scan
     see the old values and blocks after it see the new — a torn read ACROSS BLOCKS despite a
     perfectly atomic write. *** `MB_SERVER` IS CALLED FIRST IN THE SCAN, BEFORE ANY COPY-LAYER
     READ. *** That is a checkable rule, not a convention.
  2. *** THERE IS A HARD MEMORY CEILING ON THE MIRROR — VERIFIED 2026-08-12, AND IT IS TWICE
     WHAT THIS SAID. *** The 1214C's bit memory is *** 8192 BYTES = 4096 WORDS *** [R, System
     Manual V4.4 Table A-48], not the 4096 bytes / 2048 words previously carried here with an
     `[I]` tag asking to be verified before use. It is verified, and the ceiling doubled: at a
     100-register slot that is roughly FORTY slots' worth of address space, not twenty.
     (1211C and 1212C have 4096 bytes; 1214C/1215C/1217C and all G2 models have 8192.)

     *** AND THE MORE IMPORTANT HALF: `%M` IS SEPARATE FROM WORK MEMORY [R]. *** Siemens
     classifies bit memory under SYSTEM memory, a different area from work memory, and every
     datasheet carries "Flag — size, max" as its own row. *** SO THE MIRROR COSTS ZERO WORK
     MEMORY *** and does not compete with the harness's DBs and code for the scarce budget
     (§16.13). That is a FIFTH independent argument for §6's "`%MW` is structural, not
     preferential" — and the only one about CAPACITY rather than correctness.

     *** ONE PLACEMENT RULE, AND IT IS FREE: PUT THE MIRROR ABOVE THE PROGRAM'S RETENTIVE `M`
     RANGE. *** Retentive bit memory ALWAYS starts at MB0 and runs contiguously upward [R], and
     retentive `M` DOES count against retain memory — which §16.13 shows is the tightest budget
     on the rig by a factor of twelve. Placing the mirror low risks it landing inside a
     retentive window and silently consuming the scarcest resource there is; placing it high
     removes that path entirely.

     *** THIS IS THEREFORE NO LONGER THE BINDING CONSTRAINT ON CONCURRENCY. WORK MEMORY IS ***
     — see §16.13. The mirror bound roughly doubled while the work-memory bound did not move.

*** ONE ASSUMPTION UNDERNEATH ALL OF THIS THAT IS NOT MEASURED [I]: that `MB_SERVER` applies
one request's registers within a SINGLE SCAN. *** It is how the instruction is documented to
behave, and the whole atomicity-by-addressing argument rests on it. Cheap to test — write a
known pattern across a full slot in a loop while the program checks for a mixture — and this
project has been caught twice this week by exactly this class of obviously-true premise.

................................................................................
16.2  X-B  *** NO PER-TEST TIMEOUT — AND THE PACKER ALREADY NEEDS ONE ***
................................................................................

A vector whose expected condition never occurs hangs its tensor; a hung tensor hangs the wave;
nothing above bounds it. D26 computes a tensor's cost as the MAX TEST DURATION in it, which
presumes durations are known — yet no part of the design requires a test to declare one.

*** THE CHEAP RESOLUTION: THIS IS NOT NEW WORK. *** DB-13 cannot compute tensor cost without a
declared maximum duration per test, so the declaration is an input THE PACKER ALREADY REQUIRES.
Making it double as the timeout costs nothing and closes the hang.

TREATMENT — every vector declares a maximum duration, in SCANS (the unit §12 argues in) with a
wall-clock ceiling as backstop. Exceeding it is a DISTINCT OUTCOME — TIMED-OUT, never FAILED —
because "the condition never occurred" and "the wrong thing happened" are different findings,
and an agent told only FAILED will go and fix the wrong thing.

*** THE WALL-CLOCK BACKSTOP IS COMPUTED, NOT GUESSED — DERIVED 2026-08-13, §12a derivation 4. ***
A backstop is a number that fires on a HEALTHY test if it is set too low, and a TIMED-OUT verdict
is believed precisely because it is meant to be rare:

    backstop = (declared max duration in scans x 23.33 ms)          [M, loaded scan]
             + (expected round trips for the test x 201 ms)         [M, RTT p99 at full width,
                                                                    raised from 173 on 2026-08-13]
             + 2,216 ms                                             [M, worst RTT in 2,000]

*** THE LAST TERM IS NOT PADDING AND MUST NOT BE TRIMMED. *** One round trip in 2,000 took
2,216 ms on the rig. At §12a's worked wave that is one wave in twenty-two, so a backstop computed
without it reports TIMED-OUT on a healthy test roughly every twenty-second wave — an intermittent
red that no amount of re-running the block will explain, on the one verdict the design built to be
unambiguous. The same measurement sets a floor of *** 3,000 ms on the client's PER-REQUEST
timeout ***, for the same reason and at the same cost, which is none.

................................................................................
16.3  X-C  *** IF THE COORDINATOR DIES, NOTHING BRINGS THE RIG TO INERT ***
................................................................................

Every path to inert in this design is driven from the PC. If the coordinator crashes, loses its
network or is killed mid-tensor, the rig keeps running the last applied vector indefinitely —
resets released, models running, outputs driven. On restart the coordinator has no idea what
state the rig is in, and nothing above tells it to find out.

*** SCOPED 2026-08-12 BY RULING: IF THE COORDINATOR DIES, EVERY TEST AND RESULT IN FLIGHT IS
INVALID. *** No autonomous recovery, no PLC-side watchdog for now — the option to improve it
later is held open deliberately.

*** THIS IS DEFENSIBLE SPECIFICALLY BECAUSE OF THE RIG FENCE, AND THAT DEPENDENCY MUST BE
RECORDED. *** A rig left running is harmless only because its outputs are PHYSICALLY INCAPABLE
OF ACTUATING (ADR-0009). *** IF THIS IS EVER POINTED AT A RIG WHOSE OUTPUTS CAN ACTUATE, THE
SCOPING IS NO LONGER SAFE AND THE WATCHDOG BECOMES MANDATORY. *** That is the condition to
revisit on, and it is a property of the TARGET, not of this design.

THREE SMALL THINGS THE SCOPING STILL REQUIRES:
  1. *** ON CONNECT, ASSUME NOTHING *** — force inert before anything else, rather than
     assuming the rig is where it was left. Cheap, and not the watchdog.
  2. *** A PERSISTED WAVE-IN-PROGRESS MARKER ON THE PC SIDE. *** Without it a restarted
     coordinator cannot tell "I died mid-wave" from "I am starting clean", and will treat
     stale rig state as a fresh start. This is the one piece that must actually be built, and
     it is a file.
  3. *** RESULTS FROM AN INTERRUPTED WAVE ARE DISCARDED, NEVER RE-READ. *** The version
     register can confirm the PROGRAM is intact; it says nothing about whether a test
     completed.

*** RULED 2026-08-13 — AN UNREADABLE MARKER INVALIDATES THE WHOLE RIG STATE, NOT A SET OF
SLOTS. *** Point 3 discards results BY SLOT, and the build of the marker (`src/wave-control/`,
2026-08-12) walked straight into the case that rule cannot cover:

    *** THE CRASH THAT PRODUCES AN UNREADABLE MARKER IS EXACTLY THE CRASH IN WHICH THE SLOTS ARE
    UNKNOWN. *** Discard-by-slot needs a slot list, and the slot list was in the marker. So on
    the one failure the marker exists to detect, the stated rule is not merely conservative —
    it is UNIMPLEMENTABLE.

THE RULE, and it is the SPEC's now rather than an implementer's improvisation:

    *** IF THE WAVE-IN-PROGRESS MARKER CANNOT BE READ OR CANNOT BE PARSED, THE ENTIRE RIG STATE
    IS INVALID. *** Every result that could have come from that wave is discarded, whether or
    not any slot can be named; the rig is forced inert on connect (point 1) and the wave is
    re-run from submission. No partial salvage, and no attempt to reconstruct the slot set from
    rig-side evidence — rig-side evidence is exactly what the crash made untrustworthy.

WHY THIS AND NOT A NARROWER RULE. It is the only answer that is implementable in the case that
produced the question, it needs no information the crash may have destroyed, and it is
consistent with the scoping directly above — X-C has already ruled that everything in flight is
invalid on coordinator death, and an unreadable marker is a coordinator death whose extent is
unknown. It also matches the marker's own construction: `NoWaveInProgress` is deliberately not
the zero value and an unreadable marker never reads as clean, so the file was already built to
fail toward "a wave WAS in progress". *** THIS RULE IS THAT CONSTRUCTION'S SPEC-SIDE HALF; the
code fails closed and now so does the document. ***

*** THE CONDITION TO COME BACK ON: IF DISCARD-BY-SLOT EVER BECOMES THE REAL MECHANISM — a
per-slot result store, or per-slot commit records that survive the coordinator — THIS NEEDS THE
OWNER AGAIN. *** At that point whole-rig invalidation stops being the only implementable answer
and starts being merely the most conservative one, and that is a different decision from the one
ruled here. Anything that makes the slot set recoverable without the marker reopens it.

HELD FOR LATER, so the improvement path is written down rather than rediscovered: a PLC-side
watchdog in the copy layer — no commit change for N seconds, GO INERT AUTONOMOUSLY — is the
only protection that survives the PC dying, which is exactly what item 1 cannot cover. A
handful of rungs.

................................................................................
16.4  X-D  *** TIME COMPRESSION DESTROYS OBSERVABILITY — D12/DB-12 AGAINST §12 ***
................................................................................

Two parts of this design pull directly against each other and neither mentions the other.

§12 establishes that polling observes at one round trip per slot against a 23.33 ms scan, so a
one-scan event is already 3.3 to 8.6 times below the sampling floor *** (CORRECTED 2026-08-13 —
this read "~100 ms against a ~10 ms scan ... about ten times below"; both constants were wrong and
the replacement is §12a derivation 1) ***. DB-12 requires models to run COMPRESSED so
long tests are runnable at all. *** BUT COMPRESSION SHORTENS THE REAL-TIME SEPARATION OF THE
EVENTS BEING OBSERVED. *** At 100x, a behaviour occupying 100 scans of plant time collapses
into one scan of real time — moving from comfortably observable to structurally invisible,
while every check still reports green because the assertion was simply never sampled.

*** SO THE COMPRESSION FACTOR IS NOT A FREE PARAMETER OF THE MODEL. IT IS BOUNDED BY THE
OBSERVABILITY REQUIREMENTS OF THE ASSERTIONS BEING TESTED. ***

*** RESOLVED 2026-08-12: FULLY COMPUTABLE FROM CONSTRAINTS ALREADY IN THIS DOCUMENT, AND THE
RULE IS TAKE THE SAFE MINIMUM. ***

  (Naming note, and it is not pedantry: the compression factor is written `comp` throughout,
   never abbreviated to a capital-F-underscore form. In a Siemens project that prefix is the
   FAIL-SAFE marker, which hard rule 2 forbids the whole area of — so the obvious mathematical
   shorthand collides with a safety identifier. The repo's write-side guard blocked this
   section twice on exactly that, correctly, and the fix was to rename rather than bypass.)

    comp_min = T_plant / T_budget                 the LEAST compression that fits the wave

    comp_max = min of:
        per assertion   T_event / scan_period     if LATCHED     (*** 23.33 ms [M] ***)
                        T_event / poll_period     if SAMPLED     (*** K x RTT_p99, and
                                                                 >= 201 ms even at K=1 [M] ***)
        per timer       PT / (k x scan_period)    k ~ 5          (*** so PT must stay above
                                                                 116.7 ms, not 50 ms [D] ***)
        model           comp_stable               declared by the model (M3/M4 already
                                                  require the fidelity declaration)

    *** ALL THREE CONSTANTS CORRECTED 2026-08-13 — THEY READ ~10 ms AND ~100 ms, AND §12a
    DERIVATION 5 REPLACES THEM. THE TIMER TERM, WHICH THIS SECTION SAYS OFTEN BINDS FIRST, IS
    HALVED: *** on X-D's own 500 ms preset, `comp_max(timer)` falls from 500/50 = 10x to
    *** 500/116.7 = 4.3x ***. No verdict in the worked example flips — a 4-hour behaviour in a
    60 s budget needs 240x and is refused either way — but every marginal case moves toward
    REFUSE, and "use comp_min, not comp_max" is now carrying more weight than when it was
    written.

    RUNNABLE iff comp_min does not exceed comp_max. Otherwise REFUSE, SHOWING BOTH NUMBERS —
    that refusal is a MODEL TASK or a test-design task, and §7's DEFERRED bucket already
    carries the sub-case for exactly this.

*** A THIRD BOUND, ADDED 2026-08-12 FROM THE 0.4 SWEEP — RATIO DISTORTION, AND IT MAY BIND
BEFORE EITHER OF THE OTHERS. *** The terms above scale presets that are DATA. They say nothing
about presets that are LITERALS, which do not scale at all — and every corpus swept carries a
recognisable set of them (debounces, prestart requests, heartbeat ticks). Compress the
behaviours around an unchanged 500 ms debounce and it goes from 0.003% of a 4-hour interval to
2.5% of that interval compressed to 20 seconds. *** THE BLOCK THEN PASSES OR FAILS FOR REASONS
OF CHANGED PROPORTION RATHER THAN CHANGED LOGIC *** — a different failure from losing
observability, and one no term above catches. Bound the factor so the SHORTEST UNSCALED LITERAL
in the block under test stays negligible against the SHORTEST COMPRESSED behaviour. Measurement
and the accumulator finding: DB-12.

*** USE comp_min, NOT comp_max. *** Compression is a fidelity risk, so take the least that
meets the budget and bank the remainder as margin. Never run at the ceiling merely because the
ceiling permits it.

*** THE TIMER BOUND IS THE ONE NOBODY HAD, AND IT OFTEN BINDS FIRST. *** If presets are data
(DB-12's requirement) they are scaled by the factor too, and a preset scaled below a few scan
times stops behaving like a timer — it rounds toward zero, and the block then passes or fails
for reasons unrelated to its logic. Dwell presets are usually the shortest meaningful time in
a block, so this bound frequently bites before observability does.

*** AND THE SPREAD BETWEEN LATCHED AND SAMPLED MAKES OBSERVABILITY A THROUGHPUT LEVER, NOT
ONLY A CORRECTNESS ONE *** — a latch captures a one-scan event, where a sampled level must
still be present when the poll arrives. *** THE SPREAD IS 8.6x AT THE p99 AND 3.3x TYPICAL
[D, §12a] — NOT THE 10x THIS PARAGRAPH CLAIMED, AND IT SCALES WITH TENSOR WIDTH: at K slots the
sampled term is K x RTT, so the lever gets LONGER as a wave set gets wider, not shorter. *** The
same latch also removes the poll-width cap on the wave set entirely (O11, §12a derivation 2),
which is a second and larger throughput argument for the same choice.

................................................................................
16.5  X-E  *** EXCISION IS TRANSITIVE, AND IT CAN COST MORE THAN THE BOUNDARY IT AVOIDS ***
           RESOLVED 2026-08-12
................................................................................

*** RESTATED UNDER THE CORRECTED WAVE MODEL (D26a/D26b). *** This was first written when
packing was believed to decide tensor membership; under the correct model it is LESS severe in
two ways, WORSE in one, and it carries three consequences that were not visible before.

WORKED EXAMPLE. Wave set W1 admits five slots. `FB_Pump` CALLS `FB_Level` — that call is the
detail everything turns on:

    slot  agent  block                              tensor            length
    S1    A      FB_ValveCtrl                       {v0,v1,v2}          3
    S2    A      FB_ValveCtrl (2nd methodology)     {w0,w1}             2
    S3    B      FB_Level                           {x0,x1,x2,x3}       4
    S4    C      FB_Pump  -> CALLS FB_Level         {y0,y1}             2
    S5    D      FB_Flow                            {z0,z1,z2}          3

Wave length = max tensor length = 4 indices. At i=2, S2 and S4 are NULL (start bools low, held
inert). At i=3 only S3 runs. The download then raises an unhandled configuration, attributed
to `FB_Level` — agent B changed its DB interface.

*** WHAT BREAKS ***

  1. *** THE EXCISION IS TRANSITIVE, AND THAT IS THE FINDING. *** `FB_Level` cannot be excised
     alone: `FB_Pump` calls it, so the project stops compiling, and loop 2 requires the WHOLE
     project to compile before ANYBODY's download. The excision set is the TRANSITIVE CLOSURE
     OF DEPENDENTS over `converter cross-check`'s reference graph. *** S3 AND S4 BOTH DIE, AND
     AGENT C IS COLLATERAL — its block is fine and it did nothing wrong. ***
  2. Wave length changes: S3 held the longest tensor, so the wave now runs 3 indices, and the
     schedule every agent was quoted is stale.
  3. *** THE CO-RUNNING LOG BECOMES FALSE EVIDENCE. *** Generated from the PLANNED slot set,
     S1's results read "ran alongside S3 and S4" — naming slots that never executed. §7a's
     cause-4 attribution then points at a phantom, which is worse than having no log.
  4. *** THE VERSION REGISTER GOES STALE, AND THIS ONE HAS TEETH. *** The build hash is
     computed from the IR set ACTUALLY DOWNLOADED, and excision changes that set. So the
     constant must be recomputed and THE COPY LAYER REGENERATED. Excision is a REGENERATION
     STEP, not "drop a file from the download list". Computed at planning time, every
     post-download check fails against a stale expected value and looks like a failed download.

*** WHAT DOES NOT BREAK — two downgrades from the first statement of this gap ***

  5. *** THE MAP NEEDS NO RE-DERIVATION, AND MUST NOT GET ONE. *** Slots are fixed-size and
     independent, so an excised slot is simply ALLOCATED AND NULL AT EVERY INDEX — its start
     bool never rises and D33's inert holds. D26a's null mechanism already covers this exactly.
     Leaving the hole is not merely convenient, it is correct: *** IT KEEPS THE MAP HASH
     STABLE ***, which is precisely what DB-6's client-side protection keys on. Re-deriving
     would churn the hash, invalidate every client mirror, and buy nothing.
  6. *** DB-9's ATOMICITY SURVIVES, BECAUSE THE UNIT IS THE SLOT. *** The apparent contradiction
     — "submissions are atomic, yet excision shrinks one" — dissolves once a submission is ONE
     SLOT'S TENSOR rather than an agent's whole set. Excision withdraws WHOLE SLOTS; nothing is
     partially withdrawn. Under D26b agent A holds S1 and S2 independently, so losing one would
     not touch the other.
  7. RE-COLOURING IS AN OPTIMISATION, NOT A CORRECTNESS REQUIREMENT. Excision removes conflict
     edges, so slots deferred to W2 BECAUSE they conflicted with S3 or S4 could now join W1.
     Worth doing if cheap; entirely safe to skip.

*** THREE HOLES IN D32's LADDER THIS EXPOSES ***

  8. *** REPEATED EXCISION IS UNBOUNDED. *** After excising and re-downloading, another
     configuration can be raised, attributed and excised — dismantling the wave one block at a
     time, each step locally reasonable. BOUND IT AT TWO ATTEMPTS, then escalate.
  9. *** INFRASTRUCTURE CANNOT BE EXCISED. *** If the configuration is attributable to the copy
     layer, the mirror or a model, there is nothing to withdraw — removing it removes the test
     environment. Straight to the disruptive boundary or the human.
 10. *** EXCISION CAN COST MORE THAN THE THING IT AVOIDS. *** The closure here was 2 slots of 5.
     Had `FB_Level` been a shared UDT or a common utility FC, the closure could be 5 of 5 —
     excision achieves nothing and a re-download was spent learning that.

*** RESOLUTION — D32's LADDER GAINS A COMPARISON, NOT JUST AN ORDERING ***

    4. attribute
    5. attributable -> *** COMPUTE THE EXCISION CLOSURE *** (cross-check, transitive dependents)
           closure SMALL    -> excise WHOLE SLOTS; regenerate copy layer + version register;
                               re-download. THE MAP IS UNTOUCHED, excised slots go null.
           closure LARGE    -> prefer the disruptive boundary; excision buys nothing
           INFRASTRUCTURE   -> not excisable at all
    6. not attributable -> disruptive boundary (Class A only, D32 caveat 3)
    7. otherwise, OR more than TWO excision attempts -> TOTAL TEST ABORT, human

  THRESHOLD: start at *** MORE THAN HALF THE WAVE SET'S SLOTS *** and tune. Both numbers —
  closure size and wave-set size — are known at that moment, so this is a cheap comparison and
  never a runtime judgement call.

  *** PUBLISH THE CO-RUNNING LOG FROM EXECUTED START BOOLS, NEVER FROM THE PLAN. *** The bools
  are already registers; have the copy layer publish back WHICH WERE RAISED at each index. That
  makes the log MEASURED rather than DERIVED, kills failure 3 permanently, and costs one
  register.

  *** TELL THE WITHDRAWN AGENT, IN THESE TERMS: YOUR BLOCK WAS NEVER DOWNLOADED AND NOTHING
  ABOUT YOUR LOGIC WAS TESTED. *** WITHDRAWN-NOT-FAILED is a distinct outcome. An agent reading
  a withdrawal as a signal about its code will start editing correct logic — the exact failure
  §7a exists to prevent, and the one most likely to hit agent C, who never had a fault at all.

16.8  X-H  *** D28's PER-TEST MODEL INSTANCING IS WRONG WHERE THE PLANT GENUINELY SHARES ***
................................................................................

D28 instances models per test so the conflict graph does not go complete. Correct when the
sharing is an artefact of authoring — WRONG when the plant itself shares the thing: one header
tank feeding two units, one common supply, one shared conveyor. Instancing produces two
independent tanks where reality has one, and both tests pass against a plant that cannot exist.

*** WITHDRAWN AND REPLACED 2026-08-12 — THE GAP AS STATED CONFLATED TWO DIFFERENT THINGS, AND
THE OWNER CAUGHT IT. *** It claimed that where the plant physically shares a thing, per-slot
model instancing is wrong. That confuses *** THE MODEL REPRESENTING SHARED EQUIPMENT *** with
*** THE TEST DEPENDING ON THE SHARING ***, and only the second matters. Worked through:

  CASE 1 — TESTING THE SHARED EQUIPMENT'S OWN BLOCK. Two slots both test `FB_HeaderTank`. Each
    gets its own iDB and its own tank model. *** ENTIRELY CORRECT AND THE COMMON CASE *** —
    they exercise the same code with different values and never interact. Instancing is right
    and D28 is right. Nothing to fix.

  CASE 2 — TESTING A CONSUMER OF THE SHARED EQUIPMENT. Slot A tests `FB_UnitA`, slot B tests
    `FB_UnitB`, and both consume the header tank's level. *** STILL NO SHARING NEEDED. *** The
    tank is not under test here, it is ENVIRONMENT: the test drives the level as an input. "Does
    UnitA close its valve below level X" needs the level PARAMETRISED, not a tank shared with
    another slot. Per-slot instancing remains correct.

  CASE 3 — TESTING THE INTERACTION ITSELF. "When A and B both draw, the tank depletes faster and
    the low-level interlock trips." *** THIS IS NOT TWO TESTS. IT IS ONE TEST OF THE COUPLED
    SYSTEM, AND ITS SUBJECT IS THE SHARED LOGIC. *** So it belongs in ONE SLOT, with the units'
    demands as vector inputs and one tank model inside that slot. Nothing is shared ACROSS
    slots, because the coupling is inside a single slot's subject.

*** THE RULE, WHICH IS TEST-DESIGN GUIDANCE AND NOT A DEFECT IN D28: AN INTERACTION BETWEEN TWO
PIECES OF EQUIPMENT IS TESTED BY MAKING THE COUPLING THE SUBJECT OF ONE SLOT — NEVER BY SHARING
A MODEL ACROSS SLOTS. *** D28's per-slot instancing therefore stands UNCONDITIONALLY, with no
"physical sharing" exception and no declaration to make. That is a simplification, not a
loosening: there was never a case where cross-slot model sharing was the right answer.

RESIDUAL RISK, AND IT IS A TEST-DESIGN ERROR RATHER THAN A MECHANISM GAP: a designer writes
case 3 as two case-2 slots without realising the coupling is what matters. Both slots then pass
against two independent tanks, and the coupled behaviour was never exercised.

  TREATMENT — a WARNING, never a block, because case 1 is legitimate and common: when two slots
  in a wave set model THE SAME PHYSICAL EQUIPMENT INSTANCE, report it and ask whether the
  coupling is what is under test — if it is, it belongs in one slot. Equipment identity is
  available: per M1/M2 models are authored from the equipment-grounded physical analysis
  (rung A), so the P&ID item is already named.

16.9  X-I  *** MODELS ARE UNTESTED CODE THAT EVERY RESULT DEPENDS ON ***
................................................................................

§7a names "the model is wrong" as one of five causes of a red result, and M3/M4 require a
fidelity declaration — but NOTHING VERIFIES A MODEL. A model is IR like any other block,
authored by an agent from a written analysis, and every result is conditioned on it. A wrong
model does not produce one wrong test: it produces a consistent, plausible and wholly wrong
picture of a piece of equipment. §7a's own worked example — the pre-act offset engineered out
because the model had no in-flight mass — IS this failure, already written down.

*** RESOLVED 2026-08-12, AND WITH NO NEW MACHINERY AT ALL — THE OWNER'S ANSWER IS THE RIGHT
ONE: A MODEL GOES THROUGH ITS OWN TEST WAVE, LIKE ANY OTHER BLOCK. *** The proposed "analytic
self-checks at admission" was inventing a second, weaker test mechanism alongside the one that
already exists. A model is IR with inputs (its parameters) and outputs (its simulated values),
which is exactly what a slot tests. The self-checks simply BECOME TEST VECTORS: known inputs,
hand-computable expected outputs.

    A MODEL-TESTING SLOT IS SIMPLER THAN A BLOCK-TESTING ONE, not harder — it needs no model
    instance of its own, because its inputs ARE the vector.

FOUR RULES, and each is an existing rule applied rather than a new one:

  1. *** THE MODEL'S AUTHOR DOES NOT WRITE THE MODEL'S VECTORS *** — D6, unchanged. The
     correlated-check argument does not care whether the artifact is plant logic or a model.
  2. *** A MODEL MUST PASS BEFORE ANY SLOT THAT USES IT IS ADMITTED. *** This is a new
     ORDERING CONSTRAINT ON WAVE SETS and the one genuinely new thing here: model slots run in
     an EARLIER wave set than the slots depending on them. Run concurrently, a red result is
     ambiguous between the block and the model (§7a cause 1 versus cause 2) — which is the
     exact ambiguity §7a exists to remove. Enforced at admission (R6).
  3. *** COVERAGE APPLIES, WITH THE PHYSICAL ANALYSIS AS THE SPECIFICATION. *** §7's machinery
     transfers unchanged: assertions are enumerated from rung A's equipment-grounded analysis
     the way block assertions are enumerated from requirement clauses (D35). Same denominator
     rules, different spec document.
  4. Everything else — inert, start bools, the result package — is identical, because a model
     under test IS a block under test.

*** THE RESIDUAL, AND IT IS THE IMPORTANT PART: PASSING ITS OWN TESTS MAKES A MODEL FAITHFUL TO
ITS SPECIFICATION, NOT TO THE PLANT. *** §7a's worked example survives this entirely intact —
the fill model with no in-flight mass CORRECTLY IMPLEMENTS a specification that omits in-flight
mass, so it passes every test anyone would write from that specification, and it still engineers
a correct pre-act offset out of the block under test.

    *** SO MODEL TESTING CATCHES IMPLEMENTATION ERRORS AND CANNOT CATCH SPECIFICATION
    OMISSIONS. *** The sign error, the unit error, the transposed coefficient — caught. The
    physics nobody thought to include — not caught, not catchable this way, and still the
    thing most likely to produce a confident wrong answer. M3/M4's FIDELITY DECLARATION remains
    the only defence against it, and §7a cause 2 stays live.

16.11 X-K  *** A STOPPED CPU AND A DROPPED LINK LOOK THE SAME, AND THE API CANNOT TELL YOU ***
................................................................................

If the CPU goes to STOP mid-wave — a genuine fault, not a download — `MB_SERVER` stops serving
and the harness sees a dead connection, indistinguishable from a network fault. The escape
hatch is closed: it is MEASURED [M, in the probe's own online-mode reflection survey — NOT §13, which does
not record it] that `OnlineProvider` exposes NO CPU operating mode,
and that the download-configuration callback is the ONLY place a stop or start is expressible
in the public API. *** SO THE TOOLING CANNOT ASK WHETHER THE CPU IS RUNNING. ***

*** IT IS CLOSEABLE, AND THE CLOSER IS ALREADY IN THE TOOLCHAIN — CORRECTED 2026-08-12. *** The
claim that this gap is "external, not ours to close" was drawn from the Openness survey and
over-generalised from it: OPENNESS cannot report operating mode, which says nothing about the
other protocols this project already speaks.

  *** 1. SHARP7's `PlcGetStatus(ref int)` OVER CLASSIC S7comm — MEASURED AGAINST THE RIG
     2026-08-12 [M]. IT WORKS. *** Classic S7comm is served by the CPU's communication
     firmware, not by the user program, which is why TIA can go online to a stopped CPU. The
     optimized-block invisibility that constrains Sharp7 elsewhere does not apply — this is a
     system (SZL) request, not a DB read.

        method    : `Sharp7.S7Client.PlcGetStatus(Int32& Status)`   Sharp7 1.1.82.0
        constants : `Sharp7.S7Consts.S7CpuStatusUnknown = 0`
                    `Sharp7.S7Consts.S7CpuStatusStop    = 4`
                    `Sharp7.S7Consts.S7CpuStatusRun     = 8`
        measured  : rack 0 / slot 1, returned 8 = Run, twice, at 79 and 94 ms — matching the
                    SZL 0x0011 order-code round trip to within noise, so *** THE ANSWER CAME
                    FROM THE CPU AND WAS NOT RESOLVED LOCALLY. ***

     [CORRECTED: this section previously named `PlcStatus()` with the constants on `S7Client`.
      Neither exists. The method takes the status by reference and returns an rc; the constants
      live on `S7Consts`.]

     *** THE DECODE DETAIL THAT CHANGES HOW THIS MUST BE USED — READ OUT OF THE COMPILED IL. ***
     `PlcGetStatus` reads ONE BYTE at PDU offset 44 and maps 0 -> Unknown, 4 -> Stop, 8 -> Run,
     *** AND EVERYTHING ELSE -> Stop. *** So Stop is ALSO THE CATCH-ALL BUCKET: a `Run` reading
     is precise, a `Stop` reading is "4, or anything unrecognised".

        *** THEREFORE KEY EVERY DECISION ON `Status == 8` (RUN) AND TREAT EVERYTHING ELSE AS
        "NOT RUNNING". *** That degrades safely if the CPU ever returns an unmapped byte,
        where keying on `== 4` would read an unknown state as a confident STOP.

     *** AND THE PREDICTED FAILURE MODE DID NOT OCCUR: PUT/GET IS NOT A BLOCKER. *** The worry
     was that this needs PUT/GET communication, which is off by default on the S7-1200 and
     would have made X-K's closer a hardware-configuration change — STOP-class, deferred queue.
     The read succeeded regardless. PUT/GET gates S7 VARIABLE services (Read/Write Var); this
     is a userdata/SZL request, the same class as `GetOrderCode`, which has always worked here.
     *** X-K's closer costs a function call, not a disruptive boundary. ***
     [The rig's actual PUT/GET state remains UNKNOWN — the handover records it as unknown too —
      so today's success is consistent with either hypothesis. It no longer matters for X-K.]

     *** STOP HALF MEASURED 2026-08-12 [M] — X-K IS CLOSED, BOTH HALVES, AND WITHOUT A
     DOWNLOAD. *** The owner stopped the CPU at the machine, which is a cleaner signal than a
     stop occurring as a side effect of a transfer:

        connect   : ok, 440 ms, PDU requested 480 / negotiated 240 — IDENTICAL to RUN. *** THE
                    MECHANISM SURVIVES A STOPPED CPU; it is not merely reporting on a running
                    one. ***
        SZL 0x0011: `GetOrderCode` STILL ANSWERS in STOP, 79 ms, same order code. *** THIS IS
                    THE LOAD-BEARING CONFIRMATION — the userdata/SZL REQUEST CLASS AS A WHOLE
                    is served in STOP, which is the actual basis of the claim rather than
                    `PlcGetStatus` specifically. *** A raw `ReadSZL(0x0424)` — the identical
                    wire request — also succeeded, cross-confirming from a second code path.
        timing    : 69-95 ms in STOP against 79-94 ms in RUN. Materially unchanged; no timeout
                    re-tuning needed.

     *** AND THE FINDING THAT ONLY APPEARED BECAUSE THE RAW BYTE WAS DEMANDED: THIS CPU RETURNS
     0x03 FOR STOP, NOT 4. *** The out-param read `4` — but Sharp7 yields `4` from BOTH the
     pass-through arm and the default arm, so the out-param is AMBIGUOUS BY CONSTRUCTION and
     could never have shown this. The byte the decoder's switch actually consumed was `0x03`,
     read from the client's own reply buffer.

        THIS DEVICE ENCODES  :  RUN = 0x08,  STOP = 0x03
        `S7CpuStatusStop = 4`:  *** NEVER ACTUALLY RETURNED BY THIS CPU. ***

     `0x03` is a known S7 STOP encoding, and it is exactly what Sharp7's catch-all exists to
     absorb — so the ANSWER IS STILL CORRECT. But the route to it is the default arm, not a
     recognised constant.

     *** THREE RULES FOLLOW, AND THE SECOND IS A PROHIBITION THAT WOULD OTHERWISE HAVE SHIPPED
     SILENTLY: ***

       1. *** KEY ON `== S7CpuStatusRun (8)` VIA SHARP7's MAPPED OUT-PARAM. *** `Run` is
          reachable ONLY through the pass-through arm, so a Run verdict is exact. Everything
          else is "not running". This was recorded as a precaution; it is now the only
          empirically safe rule.
       2. *** DO NOT "TIGHTEN" THE DECODER, AND DO NOT HAND-ROLL ONE THAT MAPS ONLY {0,4,8}
          AND REJECTS THE REST. *** On this rig STOP is `3`, so a decoder testing the raw byte
          for `== 4`, or rejecting unknowns as invalid, WOULD REPORT "NOT STOPPED" FOR A
          STOPPED CPU — precisely the failure X-K exists to prevent. Sharp7's default-to-Stop
          arm is LOAD-BEARING. Carry this measurement as a comment beside the code so nobody
          later "fixes" it.
       3. A `Stop` verdict is high-confidence as *** "NOT RUNNING" *** and carries NO
          information about WHICH non-running state — it cannot separate STOP from
          STARTUP/HOLD/unrecognised, all of which land in the same arm.

     *** AND IT CLOSES R8's RESIDUAL BY A BETTER ROUTE THAN THE ONE R8 ASKED FOR. *** R8
     currently requires a person to confirm RUN by eye once, because TIA's `PLC_1 started.` is
     a REQUEST rather than a READING. That confirmation is now MECHANISABLE: read
     `PlcGetStatus` after a disruptive download and test `== 8`. Repeatable, automatic, and
     strictly better evidence than an eyeball. *** ONCE `ReadCpuStatus` EXISTS, R8's
     "confirm at the device once" REQUIREMENT IS SATISFIED BY THE HARNESS ITSELF *** and the
     first unattended disruptive boundary needs no person.

     *** BUILT 2026-08-12 — `IS7Client.ReadRunState` (commit 93835e8). *** One read member;
     `PlcStop`, `PlcHotStart` and `PlcColdStart` remain unreachable, so the interface's
     reduction property holds. `S7RunState` is `Unknown | Running | NotRunning` and *** HAS NO
     `Stopped` MEMBER *** — a pinning test fails if anyone adds one. Verified read-only against
     the stopped rig: `NotRunning (4)`, 78 ms, matching the measurement exactly.

       - *** AN rc FAILURE DECODES TO `Unknown`, NEVER TO `NotRunning`. *** A dead link and "the
         CPU did not answer RUN" are different facts, and separating them is the whole purpose
         of the read — flattening one into the other rebuilds the ambiguity it removes.
       - THE REGRESSION GUARD, which is the point of the exercise: a theory over 4, **3**, 0, 1,
         6, 7, 9, 0x10, 255 asserts every one is `NotRunning`, and a sweep of -1..255 asserts
         only 8 may be `Running`. Negative-tested by temporarily tightening the decoder to
         {0,4,8} — eight tests failed, including the `3` case.
       - *** HONEST LIMIT, DECLARED RATHER THAN PAPERED OVER: THE TRUE DEVICE BYTE IS NOT
         RECOVERABLE THROUGH THIS API. *** `PlcGetStatus` collapses it to {0,4,8} BEFORE the
         adapter sees it, so an unfamiliar byte arrives as 4 and is indistinguishable from a
         genuine 4. Surfacing it would need a raw request bypassing `PlcGetStatus`.

         *** CONSIDERED AND DELIBERATELY NOT BUILT (owner, 2026-08-12) — this is a DECISION,
         not an omission. *** The question raised was whether an unrecognised byte should decode
         to `Unknown` rather than `NotRunning`. It cannot: Sharp7 collapses it before we see it,
         so the case is unidentifiable at our layer — and folding it into `Unknown` would make
         that member ambiguous between "the link is dead" and "the CPU answered", destroying the
         distinction the read exists to provide. `NotRunning` is also not an overclaim, because
         `Running` is exact: 8 is the only value reaching it, so anything else genuinely is not
         RUN.
         THE ONE REAL RESIDUAL: if a future CPU or firmware used a DIFFERENT byte for RUN, it
         would collapse to 4 and the harness would report `NotRunning` against a healthy running
         CPU — permanently wave-fatal, and undiagnosable from this API. *** ACCEPTED, BECAUSE IT
         FAILS SAFE AND ESCALATES TO A PERSON, WHO CAN DIAGNOSE IT IN TIA PORTAL FAR BETTER THAN
         A RAW BYTE READ COULD. *** Build the raw path only if that failure is ever actually
         seen.
       - CALLER TRAP, recorded for whoever does build that raw path: `S7Client.ReadSZL` throws
         `ArgumentNullException` unless the caller PRE-ALLOCATES `S7SZL.Data`. `PlcGetStatus`
         has no such requirement.

     *** AND A LOOSE THREAD THE VERIFICATION PULLED, CAUSE NOT ESTABLISHED — DO NOT GUESS IT. ***
     On the STOPPED CPU, `GetOrderCode` (SZL) SUCCEEDED while `DBRead(38)` and `MBRead(0)` BOTH
     FAILED with `0x00040000`. Two candidate causes and the evidence does not separate them:

         (a) the STOP state refuses S7 VARIABLE access while still serving SZL, or
         (b) the pre-existing PUT/GET condition, which §16.11 records as UNKNOWN on this rig.

     *** IT REINFORCES THE X-K DESIGN CHOICE EITHER WAY: SZL ANSWERED WHERE VARIABLE ACCESS DID
     NOT, so keying the run-state read on SZL was correct and a `DBRead`-based status check
     would have failed exactly when it was needed. *** More generally: if the harness ever needs
     to read anything from a NON-RUNNING CPU, SZL may be the only channel available.

     WHY IT MATTERS BEYOND THAT: if the cause is (b), NO Sharp7 DB read works on this rig at
     all — which does not touch the Modbus mirror (that is a different protocol and a different
     port) but does affect the marker-DB identity path and anything else built on `DBRead`.

     *** SETTLED 2026-08-12 BY THE PAIRED RE-READ, WITH THE CPU BACK IN RUN [M]: IT IS (b).
     THE STOP STATE WAS NEVER THE CAUSE. *** In RUN, with `PlcGetStatus` confirming `Running
     (8)`:

         DBRead(38, 0, 104)  -> rc 0x00040000   FAILS
         DBRead(38, 0, 1)    -> rc 0x00040000   FAILS
         MBRead(0, 1)        -> rc 0x00040000   FAILS
         GetOrderCode (SZL)  -> ok              WORKS

     *** SO S7 VARIABLE ACCESS IS REFUSED CPU-WIDE, IN BOTH RUN AND STOP, WHILE SZL IS SERVED
     IN BOTH. *** The refusal is not the block's doing: an optimized or absent DB cannot affect
     `M` memory, and would in any case return an ITEM code (`0x00C00000` /`0x00900000`) rather
     than this. And `0x00040000` is not a local bug — verified against Sharp7's IL, it is set by
     `if (Length < 25)` AFTER `RecvIsoPacket()` has already SUCCEEDED, so a well-formed reply
     arrived that is too short to be a read response. *** THAT IS A NEGATIVE ACKNOWLEDGEMENT
     FROM THE CPU ***, and the elapsed times confirm it: each failure cost a full round trip
     rather than being rejected locally. Consistent with PUT/GET being DISABLED on this rig,
     which the handover has recorded as unknown throughout.

     *** AND IT DOES NOT MATTER, BY RULING (owner, 2026-08-12): READS OVER Sharp7/S7comm ARE NO
     LONGER PART OF THE DESIGN — ALL DATA READS GO OVER MODBUS TCP. *** So the one thing this
     would have blocked is already routed around, and enabling PUT/GET — a hardware-config
     change, and therefore STOP-class and deferred-queue work — is NOT needed.

     TWO CONSEQUENCES THAT DO SURVIVE, AND THEY ARE WORTH HOLDING:
       - *** THE MARKER-DB IDENTITY PATH DOES NOT WORK OVER S7comm ON THIS RIG *** — `rig-read`
         reports the identity check as unusable, and `DBRead` fails regardless. If a device
         identity check is wanted, it must come over MODBUS, alongside the version register
         (§9), which is already a Modbus read. Same mechanism, one channel.
       - *** X-K IS UNAFFECTED AND IS NOW CONFIRMED IN BOTH STATES. *** `PlcGetStatus` returned
         `Running (8)` here and `NotRunning` in STOP, while variable access failed in both. The
         run-state read rides SZL, which is served throughout. *** THIS IS THE THIRD TIME THE
         SZL-VERSUS-VARIABLE-ACCESS SPLIT HAS DECIDED SOMETHING IN OUR FAVOUR *** — a
         `DBRead`-based status check would have been dead on this rig from the start.

     UNTESTED AND WORTH KNOWING: connection-resource contention between this S7 session (TCP
     102) and the Modbus session (TCP 502) on a 1214C. Reserved PG/HMI resources make it
     unlikely to bite, but a status poll opening an S7 connection alongside a live Modbus wave
     is unproven.

  *** AND THE VERIFICATION IS FREE: FOLD IT INTO THE NEXT DISRUPTIVE DOWNLOAD. *** That
  download already stops and restarts the CPU (§9b). Read `PlcStatus()` before, during and
  after, and the result simultaneously closes this gap AND supplies the independent
  confirmation R8 requires before the first unattended disruptive boundary — the one thing R8
  currently needs a person for. One experiment, two answers.

  2. THE INTEGRATED WEB SERVER reports operating mode from firmware and also survives a STOP —
     but it is a poor fit HERE for two reasons: enabling it is a hardware-configuration change
     (STOP-class, deferred queue), and *** THIS ENGINEERING PC FAKES ALL TCP 80/443 CONNECTS,
     SO PROBES ON THOSE PORTS PROVE NOTHING *** (recorded environment fact). Viable from a
     different host; not from this one.

  3. ICMP is the crude discriminator and still worth having: a stopped S7-1200 keeps its

     though it cannot distinguish "CPU stopped" from "MB_SERVER broken while the CPU runs".

  4. A TCP connect to 502 REFUSED against a host answering at IP level says the same thing as
     (3) with slightly more precision.

UNTIL (1) IS VERIFIED, treat any of these as EVIDENCE rather than a verdict, and treat either

*** THE DESIGN HAS BEEN COUNTING OBJECTS AND NEVER BYTES. *** DB-4 budgets against the <=20
changed-objects-per-download limit [R], and §16.1 caps concurrent slots by the `%MW` mirror
size. Neither is the binding constraint if work memory runs out first — and on this program the
harness has roughly *** 46 KB OF WORK MEMORY AND 3.8 KB OF RETAIN *** to add itself into.

WHAT THE HARNESS ADDS, all of which lands somewhere in that budget: a per-slot instance DB
(D10), a model plus its instance DB per slot (D28, and D26b multiplies this by K slots per
agent), the copy layer with its latches and scan-stamps, and the `%MW` mirror. *** SO THE
PER-SLOT COST IS NOW A BYTE FIGURE, NOT AN OBJECT COUNT, AND NOBODY HAS MEASURED IT. ***

    WORKED, and it is the reason this is filed as a gap rather than a note: if a model plus its
    instance DB comes to ~2 KB, 46 KB of headroom is ~20 slots and the `%MW` ceiling (~20 slots
    at a 100-register slot, §16.1) binds at about the same place — comfortable. If it comes to
    ~8 KB, it is ~5 slots and *** WORK MEMORY BECOMES THE BINDING CONSTRAINT ON CONCURRENCY,
    ahead of conflict-freedom (D29), poll bandwidth (O11) and the mirror size. *** That would
    be a fourth bound, and the tightest one.

    *** AND IT IS MORE LIKELY TO BE THE BINDING ONE THAN THIS PARAGRAPH ASSUMED, BECAUSE POLL
    BANDWIDTH MOVED OUT OF THE WAY (2026-08-13, §12a derivation 2). *** O11's cap does not bind
    at all on a wave set whose observations are all LATCHED, and where it does bind it is a
    function of the declared sampled window rather than a fixed width. So of the four bounds,
    the two that are properties of the CPU — work memory and retain — are the ones that do not
    go away when the design is written well.

RETAIN IS THE SHARPER EDGE. 3,864 bytes free, and *** IT INTERACTS WITH SOMETHING ALREADY
DECIDED: *** R4 records that `DataBlockReinitialization` resets ALL data INCLUDING RETAIN [R],
and external gap G2 is precisely the unresolved question of what a structural DB change does to
retentives. A harness that consumes most of the remaining retain makes G2's answer matter far
more than it does today.

*** AND THE REQUIREMENT THE OWNER STATED, WHICH IS THE DURABLE HALF: THE TOOLING MUST NOT
HARD-CODE ONE CPU's FIGURES. *** These numbers are properties of a 1214C running one particular
program. The family varies (1211C/1212C/1214C/1215C/1217C, and the G2 line is a different
article number with different capabilities — CLAUDE.md's environment note already warns against
conflating them). So:

    - *** THE BUDGET IS READ, NEVER ASSUMED *** — per project and per CPU, at admission time.
    - A hard-coded 150 KB, 4 MB or 14 KB anywhere in the tooling is a DEFECT, not a shortcut.
    - The check belongs at ADMISSION (loop 2), where a slot can still be refused cheaply,
      rather than at download, where refusing costs a boundary.
    - *** IF THE FIGURES CANNOT BE READ, REFUSE RATHER THAN ASSUME A CEILING *** — "empty is
      not clean" (FI-44), and a guessed ceiling that is too generous fails at download time
      with the wave already committed.

*** SCOPED BY RULING (owner, 2026-08-12), AND IT COLLAPSES MOST OF WHAT FOLLOWS INTO
BACKGROUND: THE ONLY MEMORY RESTRICTION THE DESIGN CARRIES IS RETAIN. *** Work memory, load
memory and the block-count ceiling are NOT gated on — the governing rule instead is:

    *** KEEP WHAT IS ON THE PLC TO THE MINIMUM REQUIRED TO TEST FOR. ***

Which is a design discipline rather than a check, and a better one: a harness that adds only
what a test needs does not approach any of those three ceilings, and a harness that needs
policing against them has already gone wrong. So:

    RETAIN ....... *** A HARD RESTRICTION. Every harness-added object is explicitly
                   NON-RETENTIVE, and any retain increase is refused. *** 3,864 bytes free,
                   12x tighter than work memory, and it is the one budget that cannot be
                   recovered by tidying up later.
    WORK / LOAD /  NOT GATED. Governed by minimality. The measurements below stay recorded
    BLOCK COUNT    because they set expectations and because a future harness that DOES grow
                   will want them — not because anything checks them.

    ➜ THIS RETIRES the proposed 85%-of-work-memory gate, the per-object cost measurement as a
      GATE INPUT (it is still worth knowing, see plan task 0.1a), and the whole "read the
      budget at admission" apparatus for work and load. *** THE RETAIN RULE NEEDS NO
      MEASUREMENT AT ALL — "add nothing retentive" is checkable from the IR itself, before any
      device is involved. ***

    AND THE TRAP THAT MAKES THE RETAIN RULE NON-TRIVIAL IS UNCHANGED AND STILL BITES: retentive
    tags are per-tag on OPTIMIZED blocks but *** ALL-OR-NOTHING ON STANDARD-ACCESS ONES, so ONE
    retentive tag makes the WHOLE DB retentive *** — and the harness deliberately creates
    standard-access blocks for S7comm visibility (§6). That is exactly where an accidental
    retain increase would come from.

WHAT LIVES WHERE [R, System Manual V4.4 §5.1.5 + Table 1-2]: load memory is non-volatile and
holds the program, data and configuration; work memory is VOLATILE and holds the executing
subset, restored from load at power-up; retentive memory is non-volatile storage for a limited
quantity of WORK MEMORY VALUES. *** A DOWNLOAD DOES NOT CLEAR RETENTIVE MEMORY *** [R] — a
MEMORY RESET does.

WHAT A NEW OBJECT COSTS [R, Table 1-2 fn.1]: FB/FC/OB code, instance DBs and normal global DBs
are stored in work memory *** AND *** load memory, both. IEC timers cost 16 bytes each in a DB;
counters 3-12 bytes by type.

*** THE ONE THAT IS ACTIONABLE AND FREE — `Only store in load memory` [R]: AN UNLINKED DB TAKES
ZERO WORK MEMORY *** and may be up to 256 KB. That moves any harness data the PROGRAM does not
read with bit logic — expected-value tables, result archives, per-run captures — onto the 1.6 MB
nobody is using. Cost: `READ_DBL`/`WRIT_DBL` access only, no bit addressing, and it is almost
certainly invisible to Sharp7 as well [I], so it can be a STORE but never a MIRROR.

*** RETAIN IS THE SHARP EDGE AND THE DESIGN HAS NO ACCOUNT OF IT. *** What counts against it
[R]: retentive tags in global DBs and in FBs/instance DBs, retentive `M`, AND IEC timers and
counters explicitly. Per-tag on OPTIMIZED blocks; *** ALL-OR-NOTHING ON STANDARD-ACCESS ONES,
so ONE retentive tag makes the WHOLE DB retentive *** — and the harness deliberately creates
standard-access blocks for S7comm visibility (§6), which is exactly where that trap lives.
    ➜ *** MAKE EVERY HARNESS-ADDED OBJECT EXPLICITLY NON-RETENTIVE, AND CHECK IT. ***
    The limit is 10,240 bytes below firmware V4.5 and 14,336 from V4.5 [R], matching the
    measurement — and it varies by FIRMWARE, not by model. G2 is 20 KB.

WHERE EXHAUSTION SURFACES, WHICH DECIDES WHERE THE GATE GOES: *** COMPILE REPORTS, DOWNLOAD
ENFORCES. *** No compile-time hard gate on total work memory could be sourced. TIA shows usage
per block under Resources after compile [R]; the download refuses with "There is not enough
memory space on the CPU for this amount of data" [F] — reported failing at *** 98% *** usage,
because the OS itself consumes work memory for process images, diagnostics and communication.
    ➜ THE GATE BELONGS AT DOWNLOAD-PLAN TIME, and it must FAIL CLOSED WELL SHORT OF FULL.
      Recommended: 85% of work memory, and ANY retain increase at all.
